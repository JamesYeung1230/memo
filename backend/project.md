## 强制要求

### 1. 上下文加载
每次执行任务前，**必须先加载 [project.md](project.md)** 到上下文中，了解项目背景、当前阶段和技术栈。

### 2. 意图确认
收到任务后，**仔细分析用户意图**。如果存在以下情况，必须**反问用户确认**后再执行：
- 需求描述模糊，存在多种理解方式
- 与现有产品逻辑可能存在冲突
- 技术方案存在多种可选路径
- 任务的边界范围不清晰

### 3. Agent 协同
执行任务时，在可用的 Agent 配置中选取合适的 Agent。当任务可以拆分为多个独立子任务时，**协同调用多个 Agent 并行工作**，提升任务效率。

可用 Agent：
- `backend-architect` — 后端 API 设计、服务端架构
- `api-test-pro` — API 测试、性能测试、契约测试
- `performance-expert` — 性能分析、瓶颈定位
- `devops-architect` — CI/CD 配置、部署自动化
- `search` — 代码搜索与调研

### 4. Git 本地提交
**每次修改完成后必须维护 git 仓库**，将代码修改记录提交到本地仓库。提交信息需清晰描述本次变更内容。

### 5. 禁止擅自推送远程
**用户未主动要求，不得擅自提交到远程仓库。** 所有 git 操作仅限于本地仓库。

### 6. README 维护
在工作目录维护 [README.md](README.md)，说明该目录下项目内容的情况。项目结构或功能有变更时同步更新。

## 核心原则：纯后端项目

这是一个**纯粹的后端项目**（API 服务），不包含前端界⾯。

### 前端调用问题排查规范

在遇到前端调用后端接口出现问题时：
1. **严格依照后端 SDK ⽂档**进⾏排查
2. 如果发现后端 SDK ⽂档实现有问题：
   - **判定原因在后端**，需要进⾏后端修改
3. 如果排查发现前端调用**不符合 SDK ⽂档规范**：
   - **直接给出结论**，说明前端调用不符合规范
   - **不强制修改后端进⾏适配**
4. 后端接口设计应以 SDK ⽂档为唯⼀依据，前端应按文档规范调用

### API 设计规范

1. 所有 API 接口统一遵循 RESTful 设计规范
2. 接口文档为前后端协作的唯一契约标准
3. API 版本化管理（URL 前缀或 Header 版本号）
4. 统一错误码和响应格式
