## 项目定位

后端服务是「码上启航」平台的核心服务层，为**微信小程序**（C端学习用户）和 **Web 端管理后台**（B端运营者）提供统一的 REST API 接口，负责业务逻辑处理、数据持久化、用户认证、AI 内容生成与审核、文件存储等功能。

**API 调用链示例**

```
用户登录：
  小程序 → Auth(:8001) POST /login → 返回 JWT

用户提交笔记审核：
  小程序 → Core(:8000) [JWT] → Core 本地 shared/auth.py 验签
                              → Knowledge(:8002) 发起审核
                                  ├─ 敏感词过滤
                                  ├─ AI 内容审查 (arq 异步)
                                  └─ 高风险/低风险直接返回
                                  └─ 中风险进入人工复核队列

管理员登录：
  Web → Auth(:8001) POST /admin/login → 返回 JWT

管理员审批笔记：
  Web → Core(:8000) [JWT] → Core 本地验签 → Knowledge(:8002) 通过/驳回操作

管理员 AI 生成卡片：
  Web → Core(:8000) [JWT] → Core 本地验签 → Knowledge(:8002) 调用 DeepSeek 生成
```

**服务间通信规范**

| 项目 | 说明 |
|------|------|
| 协议 | HTTP/1.1 REST，JSON 格式 |
| 客户端 | httpx (async) |
| 调用关系 | Core → Knowledge（唯一内部调用链路） |
| 认证传递 | 客户端从 Auth 获取 JWT，携带 JWT 调 Core；Core 用 shared/auth.py 本地验证 |
| 超时 | 默认 30s，AI 生成类 120s |
| 重试 | 仅幂等 GET 请求重试最多 2 次 |
| 服务发现 | Docker Compose 内部 DNS（服务名即 hostname） |

> **端口暴露规则**：Auth(:8001) 对客户端暴露登录类端点；Core(:8000) 对客户端暴露全部业务端点；Knowledge(:8002) 仅 Docker 内部网络可访问。

### 选型决策要点

**为什么选 DeepSeek API 而非 OpenAI？**
- 国内网络可直接访问，无需代理
- 中文生成质量高，API 价格极低（个人项目友好）
- 兼容 OpenAI SDK 接口，支持结构化 JSON 输出
- 笔记审核场景 5 维度审查 + 风险评分

**为什么选 arq 而非 Celery？**
- arq 只依赖 Redis（项目已有），无需额外 message broker
- 与 FastAPI async/await 模式完全统一
- 配置极简，代码量少，个人项目维护成本低

**为什么本地存储而非直接上云 OSS？**
- Banner 图片量极小（≤5张，≤2MB/张），无并发压力
- 降低初期运维复杂度，后续可快速切换到 COS（预留 S3 兼容抽象层）

**为什么 PostgreSQL 而非 MySQL？**
- JSONB 字段天然适合运营配置（积分规则/Banner/主题色等灵活配置项）
- asyncpg 驱动在 Python 异步生态中性能最佳
- 窗口函数、聚合查询对数据看板统计更友好

**为什么共享数据库（Schema 隔离）而非独立数据库？**
- 个人项目运维成本是首要考量：1 个 PG 实例 vs 3 个，备份/监控/迁移大幅简化
- 数据看板需要跨域聚合（用户+学习+内容），共享 DB 直接 SQL JOIN 比 API 拼装高效
- Schema 隔离（auth / knowledge / core）提供足够的逻辑边界，每个服务只访问自己的 Schema
- 共享 DB 支持跨服务事务一致性（如积分消耗+解锁记录可原子提交）

**为什么 Auth 对外暴露 + Core 本地验 JWT？**
- Auth 暴露登录/刷新/密码修改端点（OAuth2 标准模式），客户端直接获取 JWT
- Core 用 shared/auth.py 本地解密验证 JWT，消除内部 HTTP 调用，零额外延迟
- Auth 和 Core 共享 JWT Secret，保证签发和验证的一致性

## 后端功能全景（按服务归属）

### ① 认证服务 (Auth Service) — port 8001 — DB: auth_db

| 功能 | 说明 | 消费端 |
|------|------|--------|
| 管理员登录 | 预设单一管理员账号，bcrypt 密码验证 → 签发 JWT（24h 有效期 + refresh token） | Web 管理端 |
| 管理员密码修改 | 旧密码验证 → bcrypt 哈希新密码 | Web 管理端 |
| 微信登录 | 接收 wx.login code → 调用微信接口换取 OpenID → 签发 JWT | 小程序 |
| Core 本地验 JWT | shared/auth.py 本地解密 + 校验过期 + 提取角色/OpenID（无需网络调用） | Core 服务 |
| Token 刷新 | refresh token 换新 access token | Web 管理端 + 小程序 |

## 核心原则：纯后端项目

这是一个**纯粹的后端项目**（API 服务），不包含前端界面。

### 前端调用问题排查规范

在遇到前端调用后端接口出现问题时：
1. **严格依照后端 SDK 文档**进行排查
2. 如果发现后端 SDK 文档实现有问题：
   - **判定原因在后端**，需要进行后端修改
3. 如果排查发现前端调用**不符合 SDK 文档规范**：
   - **直接给出结论**，说明前端调用不符合规范
   - **不强制修改后端进行适配**
4. 后端接口设计应以 SDK 文档为唯一依据，前端应按文档规范调用

### API 设计规范

1. 所有 API 接口统一遵循 RESTful 设计规范
2. 接口文档为前后端协作的唯一契约标准
3. API 版本化管理（URL 前缀或 Header 版本号）
4. 统一错误码和响应格式
