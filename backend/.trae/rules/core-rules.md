# Core Rules — 通用开发规范

> 适用范围：所有软件项目（语言/框架无关）。
> 本文件位于 IDE 用户级全局规则目录（`~/.trae/rules/`），对所有项目自动生效，无需在各项目中重复复制。
> 当项目存在专属规则文件（`.trae/rules/project_rules.md`）时，项目规则优先级高于本文件。

# Part A — AI 行为准则

> 适用于 AI Agent 在执行所有开发任务时的行为约束。

## A.1 渐进式复杂度

每个功能先做最简可用版本，不引入非必要的抽象层：

```
优先级：标准库 → 已有依赖 → 生态主流库 → 小众库

三步走：① 能跑通 → ② 能看懂 → ③ 能优化
```

每次引入新依赖前必须：
1. 检查项目是否已有类似功能的依赖
2. 说明为什么不能用已有依赖替代

## A.2 最小干预原则

对现有代码的改动遵循三级引导：

```
L1: 能否通过配置/环境变量解决？（不改代码）
L2: 能否通过新增独立模块解决？（不改现有代码）
L3: 最小化修改现有代码
```

每级不可行时，说明原因后进入下一级。

## A.3 建议-执行两阶段

默认工作模式：

```
阶段一（建议）：分析问题 → 输出方案 → 等待用户确认
阶段二（执行）：用户确认后 → 执行修改 → 汇报变更摘要
```

**例外（可直接执行）：**
- 用户明确说"直接做""不用确认"
- 纯查询/阅读类操作
- 运行 lint/typecheck/test 等验证命令

## A.4 代码注释原则

- 禁止在代码中添加任何注释，除非用户明确要求
- 代码应自解释：通过命名、结构、类型来表达意图
- 例外：许可证头部、项目已有的文档字符串风格

## A.5 文档创建原则

- 禁止主动创建 `*.md` 文档文件
- 仅在用户明确要求时创建文档
- 例外：规则文件（`.trae/rules/` 目录下）、项目规格文档（用户要求时）

## A.6 上下文感知

修改任何文件前：
1. 了解项目中已有的工具函数、组件、库
2. 阅读相邻文件和依赖文件，理解现有代码风格和约定
3. 避免重复造轮子

## A.7 修改验证

- 每次修改完成后，必须运行对应的 lint/typecheck 命令验证
- 修改涉及的功能应运行相关测试
- 多步骤任务中，每完成一步都验证后再继续

## A.8 不确定时确认

- 遇到不确定的技术选型、架构决策时，使用 AskUserQuestion 与用户确认
- 不要在不确定的情况下猜测方案直接执行
- 任务描述模糊时，主动向用户澄清

## A.9 任务追踪

- 复杂多步骤任务必须使用 TodoWrite 创建任务列表并跟踪进度
- 每完成一步标记完成，确保长链任务不丢失上下文

## A.10 需求理解确认

生成代码或输出方案前，AI 必须先用自己的话复述对需求的理解，确认理解一致后再进入方案阶段。

- 复述应聚焦于：核心目标、关键约束、输入输出
- 发现模糊或矛盾的需求点，应在复述中明确指出并请求澄清
- 用户确认理解无误后，方可继续

## A.11 边界追问与范围锁定

对存在隐含歧义的需求（如"删除功能""登录功能"），AI 应主动列出关键边界条件供用户确认或决策：

- 常见需追问的边界：权限模型、异常路径、并发场景、数据保留策略
- 用户未明确表态的边界，AI 不应自行假设后直接实现

范围锁定原则：

- 用户未明确要求时，AI 不得修改与当前任务无关的代码
- 即使相邻代码存在明显可优化之处，也不得"顺手"修改
- 如发现需要连带修改的代码，应先向用户说明原因并获取授权

## A.12 API 真实性验证

调用第三方库的 API 前，AI 必须先确认该 API 在当前项目使用的版本中存在且签名正确：

- 检查项目中该库的版本号（package.json / Cargo.toml / go.mod 等）
- 通过库的类型定义文件或项目中的已有调用方式验证 API 签名
- 禁止猜测 API 签名，禁止依赖训练数据中可能过时或错误的知识

## A.13 方案选择透明

当实现涉及抽象层、设计模式或非显而易见的方案时，AI 应向用户说明：

1. 为什么使用当前方案
2. 为什么更简单的替代方案不适用
3. 当前方案引入的复杂度是否可以接受

## A.14 复用优先检查

创建新的工具函数、组件或模块前，AI 必须先搜索项目中是否已有类似实现：

- 搜索同名或同功能的函数/组件
- 检查已有工具函数库、公共组件目录
- 如果存在类似实现，优先复用或扩展，而非重新创建

## A.15 影响面分析

修改公共接口、导出类型、工具函数签名等可能影响其他文件的代码前，AI 必须：

1. 搜索所有引用点，评估影响范围
2. 向用户说明修改将影响哪些文件
3. 确认影响范围可接受后再执行修改

## A.16 模块全局感知

处理跨模块任务时，AI 应首先了解：

- 项目的模块划分和依赖关系
- 核心数据流和接口约定
- 不依赖局部信息做全局性决策

## A.17 修复纪律

Bug 修复必须遵循以下流程：

1. **先定位根因**：理解为什么会产生这个 bug，而非仅修复表面症状
2. **说明修复逻辑**：向用户说明 ① 根因是什么 ② 为什么这个修复能解决问题 ③ 修复的最小范围
3. **最小修复范围**：只修改与 bug 直接相关的代码路径，禁止在修复过程中附带无关的重构或优化
4. **换策略重试**：同一修复思路失败超过 2 次后，必须换一个思路/方案重试，而非在原思路上微调
5. **终止条件**：累计失败超过 3 次后，深度分析瓶颈并向用户说明，提供备选方案供用户选择

## A.18 关键决策记录

在同一对话中做出的重要架构决策（技术选型、接口约定、数据流设计、命名规范等），AI 应：

- 在对话中明确标注这些决策
- 建议用户将这些决策记录在项目规则文件或设计文档中
- 便于后续对话或新对话中的 AI 引用，避免决策漂移

# Part B — 安全基线

> 适用于所有代码编写和配置。

## B.1 敏感信息管理（强制）

以下信息必须通过环境变量或密钥管理服务注入，禁止出现在代码中：

- 数据库连接字符串
- API Key / Secret / Token
- 密码 / 私钥 / 证书
- 第三方服务凭证
- 加密盐值 / JWT Secret

## B.2 输入验证（强制）

- 所有外部输入（API 参数、请求体、URL 参数）必须验证和净化
- 禁止拼接字符串构造 SQL / shell 命令
- 使用参数化查询或 ORM 提供的安全方法
- 禁止生成存在 SQL 注入、XSS、CSRF 等安全漏洞的代码

## B.3 依赖安全

- 引入新依赖前检查最后更新时间和已知漏洞
- 不引入未经维护的废弃依赖
- 禁止使用过时、不安全的库版本

# Part C — 代码质量

> 适用于所有代码编写和修改。

## C.1 风格一致性

核心原则：融入现有代码，而非引入新风格。

操作步骤：
1. 修改文件前，先阅读目标文件及相邻文件
2. 识别并沿用：命名风格、缩进、引号、导入组织方式
3. 创建新文件时，参考同目录下已有文件的模式
4. 新组件遵循项目已有的架构模式

## C.2 依赖管理

- 使用代码前，先确认该库/框架已在项目中使用（检查配置文件和已有导入）
- 禁止引入项目未使用的新依赖，除非用户明确要求或有充分理由并说明
- 优先修改已有文件，而非创建新文件

## C.3 错误处理

- 不吞噬异常（除非有明确的降级策略）
- 错误信息对开发者友好（包含上下文），对用户安全（不泄露内部细节）

## C.4 测试覆盖

- 每个功能完成后，应编写或更新对应的测试用例
- 测试应覆盖正常路径、边界条件和异常场景
- 遵循项目已有的测试框架和规范

## C.5 代码可解释性

AI 生成的代码应具备可解释性，让开发者无需询问 AI 就能理解代码的意图和运行逻辑：

- 命名清晰、准确反映其用途和范围
- 职责单一，每个函数/组件做好一件事
- 数据流明确，避免隐式的数据传递和副作用
- 控制流直线化，避免深层嵌套和难以追踪的跳转

## C.6 关键逻辑归属

涉及以下领域的代码，应由开发者主导实现方向：

- 核心业务逻辑与业务规则
- 安全机制（认证、授权、加密）
- 复杂算法与数据一致性保证
- 关键性能路径

对于上述领域，AI 应先提供设计思路供开发者确认，由开发者把控实现方向，而非直接生成完整实现。

## C.7 知识转移义务

当生成的代码涉及开发者可能不熟悉的技术、模式或概念时，AI 应：

- 简要说明其工作原理和使用方式
- 指出需要注意的陷阱和边界
- 帮助开发者建立对该代码的知识所有权，而非生成后一走了之

## C.8 模块化设计

AI 生成的代码应遵循模块化原则：

- 模块间通过明确接口通信，不依赖内部实现细节
- 每个模块可独立理解、测试和替换
- 避免生成深度耦合的代码，降低后续修改的连锁影响
- 新模块应设计为可被未来替换的独立单元

# Part D — 环境与配置

> 适用于所有项目的环境搭建和配置管理。

## D.1 环境分离

- 至少区分 development / production 环境
- 环境差异通过配置文件或环境变量切换，不通过代码分支

## D.2 配置外部化

- 可变参数（端口、地址、开关）通过配置文件或环境变量注入
- 禁止在代码中硬编码环境相关的值

# Part E — Token 开销优化

> Token 是有限的上下文资源，省 Token 不是偷工减料，而是把每一分 Token 都花在刀刃上。
> 核心原则：准确性优先、够用就行、按需分层获取。

## E.1 核心原则

### E.1.1 准确性优先

**省 Token 不能牺牲准确性。** 当以下情况冲突时，优先保证结果质量：

- 需要读完整函数体时才完整读，不为了省 Token 只读签名就下结论
- 需要查看完整错误栈时才完整查看，不为了省 Token 只看最后一行
- 不确定某段代码的作用时，宁可靠前读完整代码，也不猜测

### E.1.2 够用就行

```
每个操作前自问：
  1. 我真正需要的数据是什么？（而非「所有数据」）
  2. 哪个工具能以最少的 Token 给我这些数据？
  3. 当前调用获取的数据量是否匹配任务实际所需？
```

### E.1.3 按需分层获取

```
第一层（最省 Token）：SearchCodebase / Grep       → 定位信息位置
第二层（中等 Token）：Read 指定行段 / batch_get 低深度 → 获取局部信息
第三层（较高 Token）：Read 整个文件 / batch_get 高深度  → 获取完整信息
```

优先使用前两层，只有必要时才走上第三层。

---

## E.2 工具调用瘦身

### E.2.1 文件读取精度控制

| 做法 | Token 消耗 | 影响准确性？ |
|------|:---------:|:----------:|
| 先 `SearchCodebase` 定位函数，再 `Read` 该函数范围行 | 低 | 否 |
| 先 `Grep` 找出引用关系，再读关键行段 | 低 | 否 |
| 每次 `Read` 大文件都从第 1 行读到尾 | 高 | 不一定 |
| 用 `Read` 预览大文件目录结构（应改用 `LS` 或 `Glob`） | 中 | 是（浪费） |

> **关键规则：** 500 行以上的文件，除非需要理解全局结构，否则优先读局部行段。

### E.2.2 命令输出裁剪

涉及命令执行的工具，使用参数控制返回数据量：

```
✅ RunCommand → 不指定 blocking 时用 filter/output_character_count 控制
✅ CheckCommandStatus → 用 output_character_count 限制字符量
✅ CheckCommandStatus → 用 filter 正则提取关键行
❌ 无关紧要的命令不限制输出 → 可能浪费数千 Token
```

**例外：** 编译错误、测试失败、lint 诊断等需要完整输出的场景，不裁剪。

### E.2.3 MCP 深度控制

| 工具 | 省 Token 做法 | Token 收益 |
|------|-------------|:---------:|
| `batch_get` | `readDepth: 1` 起，不够再逐层加深 | 高 — 避免指数级膨胀 |
| `batch_get` | 用 `searchDepth` 控制搜索范围 | 高 |
| `batch_get` | 合并不必要的多次查询为单次 | 中 |
| `get_screenshot` | 优先使用 `snapshot_layout` 检查布局 | 高 — 截图是 base64，Token 极高 |
| `batch_design` | 拆分 ≤10 个操作为一批 | 中 — 每批失败回滚不会浪费大量 Token |

### E.2.4 搜索协作规则

| 做法 | Token 消耗 | 说明 |
|------|:---------:|------|
| 简单搜索直接用 `Grep`/`SearchCodebase`（单文件、已知关键词） | 低 | 无需启动子 Agent |
| 复杂跨模块搜索才用 Task 调 `search` Agent | 中 | 子 Agent 启动有固定开销 |
| 用 `Task` 但 Task 描述不够精确，导致子 Agent 反复搜索 | 高 | 一次把需求说清楚 |

## E.3 响应数据量管理

### E.3.1 优先使用「轻量」工具

| 目标 | 轻量工具（省 Token） | 重量工具（高消耗） |
|------|:-----------------:|:-----------------:|
| 检查布局结构 | `snapshot_layout` | `get_screenshot` |
| 查看文件是否存在 | `Glob` / `LS` | `Read` 全部内容 |
| 查找特定模式 | `Grep`（匹配行） | `Read` 整个文件再找 |
| 确认命令结果 | `CheckCommandStatus`（filter） | 重新执行命令 |
| 理解高层结构 | `SearchCodebase` | 依次 `Read` 每个文件 |

### E.3.2 错误场景的谨慎处理

错误排查时，Token 消耗容易失控。控制策略：

```
问题发现
    │
    ├── 常见/已知错误 → 直接修复，不反复查看完整输出
    │
    ├── 复杂/未知错误 → 查看完整错误栈 + 相关文件代码
    │                    ↓
    │                   修复后不立即删掉错误上下文
    │                   （后续编译/测试还需要验证）
    │
    └── 修复循环（>3 次）
         └── 停止，告知用户
         └── 不继续无意义重试浪费 Token
```

### E.3.3 诊断信息获取策略

| 场景 | 做法 | Token 考虑 |
|------|------|:---------:|
| 修改单个文件后 | `GetDiagnostics` 查该文件 URI | 低 — 只返回一个文件的诊断 |
| 批量修改后验证 | 逐个文件 `GetDiagnostics` | 中 — 避免一次性全量拉取 |
| 不了解当前有哪些诊断 | `GetDiagnostics` 不加参数查全部 | 高 — 仅在需要全貌时使用 |

## E.4 上下文生命周期管理

### E.4.1 对话边界控制

| 场景 | 推荐做法 | 理由 |
|------|---------|------|
| 单一任务（如实现一个接口） | 同一对话完成 | 上下文可复用 |
| 多个独立任务（如修 Bug A → 修 Bug B） | 建议用户开新对话 | 历史上下文累积会膨胀，Bug A 的上下文对 Bug B 无用 |
| 长链任务（>10 步） | 中间可 AskUser 是否「另开对话继续」 | 前期上下文对后期决策价值递减 |

### E.4.2 重复引用控制

- 规则文件在当前对话首次加载后，后续步骤不重复引用整段规则
- 使用 `SearchCodebase` 或 `Grep` 在项目中搜索过的结果，下次需要同类信息时优先复用，而不是重新搜索
- 同一工具调用的参数复用时，优先从历史记录中提取，不重新调研

### E.4.3 避免「无意义确认」

| 做法 | Token 消耗 | 说明 |
|------|:---------:|------|
| 每步完成后都问「是否继续？」 | 中 — 双向浪费 | 复杂任务才需要分步确认 |
| 修改前后都查 `git diff` | 高 — 文件内容重复传输 | 仅在提交前或出错时查看 |
| 每次调用都查一遍「当前分支」 | 低 | 但累积可避免，开头确认一次即可 |

**建议：** 仅以下情况需要暂停确认：
1. 不可逆操作前
2. 结果与预期明显不符合时
3. 用户明确要求分步执行时

---

## E.5 全局 Token 节约清单

此清单供快速自查，标记为核心操作的节点自动遵守：

| # | 检查项 | 适用场景 |
|:-:|-------|---------|
| 1 | 读文件前先想：「我需要看多少行？」 | 所有文件操作 |
| 2 | 搜代码时优先用 `Grep` 而非 `SearchCodebase` | 已知关键词的搜索 |
| 3 | MCP `batch_get` 从 `readDepth: 1` 开始 | 设计文件查询 |
| 4 | 优先 `snapshot_layout` 而非 `get_screenshot` | 布局检查 |
| 5 | 命令输出用 `filter`/`output_character_count` 裁剪 | 命令执行 |
| 6 | 复杂搜索先写精确的 Task 描述再调子 Agent | 子 Agent 委派 |
| 7 | 错误排查先看常见原因，不一次看完所有输出 | 问题诊断 |
| 8 | 一个任务完成后建议用户开新对话 | 上下文管理 |
| 9 | 同一对话内不重复加载已读过的规则/文件 | 代码阅读 |
| 10 | 不产生「顺手」的不必要修改 | 全部开发任务 |

## E.6 问题排查

当 Token 消耗异常偏高时，按以下路径排查：

```
1. 是否激活了不必要的 Skill？           → 参见 §F.1 选用原则
2. 是否委派了不必要的子 Agent？          → 参见 §F.2 选用原则
3. Read 操作是否读了完整的文件？          → 改为读局部行段（参见 §E.2.1）
4. MCP 调用深度是否过高？                → 降低 readDepth/searchDepth（参见 §E.2.3）
5. 命令输出是否未裁剪？                  → 加上 filter/output_character_count（参见 §E.2.2）
6. 同一文件是否被重复读取过？            → 复用已有结果
7. 当前对话累积了太多不相关的历史？       → 建议用户开新对话
```

# Part F — Skill / Agent / MCP 通用原则

> 适用于 AI Agent 在使用 Skill、Agent、MCP 时的通用行为约束。
> 具体的 Skill/Agent/MCP 清单和项目级配置由项目专属规则文件提供。

## F.1 Skill

### 选用原则

- 存在可用 Skill 能更好完成任务时，必须立即调用
- 不在文本中仅提及 Skill 名称而不实际调用
- 不重复调用已在运行中的 Skill
- 任务简单时不使用 Skill（简单任务不需要专家知识）

### 安全约束

- 只使用来源可信的 Skill（官方提供或项目中已有）
- Skill 附带的脚本在执行前应理解其逻辑
- Skill 数据文件如包含敏感信息，须纳入 .gitignore

## F.2 Agent

### 选用原则

- 任务明确属于某 Agent 专业领域时调用
- 简单任务不委派子 Agent（增加 Token 消耗和延迟）
- 子 Agent 返回结果必须验证后再使用
- 禁止将简单任务委派给子 Agent 以图省事

### 调用规范

子 Agent 的 Task 描述必须包含：任务目标、上下文锚点、输出要求、边界约束。

## F.3 MCP

### 操作三不原则

1. 不盲目信任 — 关键操作前先查询确认当前状态
2. 不一次做完 — 复杂操作分步执行，每步确认后再继续
3. 不忘记验证 — 每次调用后检查返回结果

### 安全约束

- 不可逆操作前必须先确认参数
- 操作前查询、操作后验证（防止状态漂移）
- 批量操作失败会整批回滚，不宜一次塞入过多操作

# Part G — 规则自维护

> 适用于所有规则文件的创建、更新和维护。

## G.1 优先级

```
项目专属规则 > 通用规则（本文件）

当两者冲突时，以项目专属规则为准。
```

## G.2 修改原则

- 修改规则前，理解现有条款的意图
- 新增条款时，标注所属 Part 和编号
- 废弃条款时标注原因和日期，不直接删除编号

## G.3 文件位置

- 全局通用规则放在用户级 `~/.trae/rules/core-rules.md`（IDE 自动对所有项目加载）
- 项目专属规则放在各项目的 `.trae/rules/project_rules.md`
- 不在项目根目录散落规则文件
