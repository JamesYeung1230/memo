## 1. 架构设计原则

| 原则 | 说明 |
|------|------|
| **单一职责** | 每个服务只负责一个业务域，Auth 只管认证、Knowledge 只管内容、Core 负责编排和业务聚合 |
| **依赖反转** | Core 服务依赖抽象（shared 库），不依赖具体服务的实现细节 |
| **内部调用最小化** | 内部 HTTP 链路仅 Core→Knowledge 一条，Auth 对外暴露后消除 Core→Auth 链路 |
| **本地验证优先** | JWT 验证在 Core 本地完成，不回调 Auth 服务，减少网络延迟 |
| **数据库共享但逻辑隔离** | 共享 PostgreSQL 实例，但通过 Schema 隔离，每个服务只能读写自己的 Schema |

### 2.2 认证与安全

| 组件 | 选型 | 说明 |
|------|------|------|
| 密码哈希 | bcrypt | 通过 passlib[bcrypt] 实现，salt 自动生成 |
| JWT 库 | PyJWT | HS256 签名，24h 有效期 + 7d refresh token |
| 管理员认证 | 预设账号 + bcrypt + JWT | 项目启动时初始化单一管理员 |
| 小程序认证 | wx.login → code2Session → JWT | 微信服务器换取 OpenID 后签发自定义 JWT |
| CORS | fastapi.middleware.cors | Web 管理端跨域支持 |
| 内部认证 | Docker 网络隔离 | Knowledge 服务不对外暴露端口 |

#### 2.2.1 微信小程序登录详解

**登录流程与时序**：

```
小程序客户端                      Auth 服务                     微信服务器
    │                              │                              │
    │ wx.login()                   │                              │
    │──── 获取临时 code ──────────►│                              │
    │   (有效期 5 分钟)            │                              │
    │                              │                              │
    │ POST /api/v1/login           │                              │
    │ { "code": "xxx" }            │                              │
    │─────────────────────────────►│                              │
    │                              │ GET https://api.weixin.qq.com│
    │                              │ /sns/jscode2session          │
    │                              │ ?appid=APPID&secret=SECRET   │
    │                              │ &js_code=code&grant_type=    │
    │                              │ authorization_code           │
    │                              │─────────────────────────────►│
    │                              │                              │
    │                              │◄─────────────────────────────│
    │                              │ {                            │
    │                              │   "openid": "oXXX...",       │
    │                              │   "session_key": "sk_...",   │
    │                              │   "unionid": "uXXX..."       │
    │                              │ }                            │
    │                              │                              │
    │                              │ ① 缓存 session_key 到 Redis  │
    │                              │    key: wx:session:{openid}  │
    │                              │    TTL: 7 天（不持久化）      │
    │                              │                              │
    │                              │ ② 查询或创建用户记录          │
    │                              │                              │
    │                              │ ③ 签发 JWT（sub=openid）     │
    │                              │                              │
    │◄─────────────────────────────│                              │
    │ {                             │                              │
    │   "access_token": "eyJ...",   │                              │
    │   "refresh_token": "eyJ...",  │                              │
    │   "is_new_user": false        │                              │
    │ }                             │                              │
```

**session_key 管理策略**：

| 维度 | 策略 | 说明 |
|------|------|------|
| **存储方式** | Redis 缓存，不写入 PostgreSQL | session_key 用于解密微信加密数据，不应持久化。Redis 崩溃后用户重新 login 即可 |
| **Key 格式** | `wx:session:{openid}` | 便于按用户维度和批量管理 |
| **TTL** | 7 天 | 匹配 refresh_token 有效期，用户 7 天内重新登录自动刷新 |
| **使用场景** | 解密 `wx.getUserInfo` 的加密数据、`wx.getPhoneNumber` 的手机号 | v1.0 暂不使用，预留扩展 |
| **更新时机** | 每次 wx.login 成功后覆盖更新 | 微信策略：每次调用 wx.login 都会刷新 session_key |

**安全性注意事项**：
| 风险 | 缓解措施 |
|------|----------|
| code 被截获重放 | code 一次性使用，微信服务器会校验。Auth 服务不缓存 code，每次请求都转发给微信 |
| session_key 泄露 | 不返回给客户端、不写入日志、Redis 中不持久化到磁盘 |
| wx.login 接口被滥用（耗尽微信 API 额度） | Auth 服务对 `/api/v1/login` 端点做限流：每个 IP 5 次/分钟、每个设备 10 次/分钟 |
| 用户信息窃取 | 不使用前端传递的 rawData 和 signature，只信任从 code2Session 返回的 openid |

**用户信息更新策略**：
```
用户在小程序端修改头像/昵称
  │
  ├── 小程序端本地展示（即时生效）
  │
  └── 可选方案（v1.0 暂不实现）：
       └── 用户触发"同步个人信息"操作
            └── POST /api/v1/users/profile
                 ├── 前端传入 encryptedData + iv
                 ├── Auth 用缓存的 session_key 解密
                 └── 更新 auth.user 表的 avatar_url / nickname
```

> **v1.0 简化**：用户信息更新功能在 v1.0 暂不实现。小程序端直接使用微信提供的 `wx.getUserInfo` 本地展示，无需同步到服务端。Auth 服务的 `user` 表只存储 openid 和 created_at，不存储昵称/头像，避免数据一致性问题。

### 2.3 AI 与异步任务

| 组件 | 选型 | 说明 |
|------|------|------|
| AI 大模型 | DeepSeek API | 通过 openai SDK（OpenAI 兼容接口）调用 |
| AI 封装层 | AIProvider 抽象类 + MockProvider | 接口：generate_card() / generate_question() / review_note()。MockProvider 在 `AI_MOCK_MODE=true` 时启用，返回预设测试数据，避免单元测试消耗 API 额度 |
| 异步任务 | arq | 基于 Redis，处理笔记 AI 审核等耗时任务 |
| 任务重试 | arq 内置重试 | 任务失败自动重试，最多 3 次，间隔 10s/30s/60s。3 次均失败后进入兜底策略（见下方） |

**任务失败兜底策略**：
```
arq 任务执行 → 失败 → 重试 #1 (10s) → 失败 → 重试 #2 (30s) → 失败 → 重试 #3 (60s)
                                                                        │
                                                                    仍失败
                                                                        │
                                                                        ▼
                                                               ┌──────────────────┐
                                                               │ 兜底处理          │
                                                               │ ① 笔记状态 →      │
                                                               │   pending_manual  │
                                                               │ ② 记录失败原因     │
                                                               │ ③ 运营看板标记异常  │
                                                               └──────────────────┘
```

**兜底处理详细说明**：

| 步骤 | 操作 | 实现方式 |
|:----:|------|----------|
| ① 状态降级 | 审核笔记状态自动设为 `pending_manual`（进入人工复核队列） | arq 任务最终异常处理中更新 DB |
| ② 失败记录 | 在 `review_audit_log` 表写入 `result=arq_max_retries_exceeded` + 错误堆栈 | `ctx['job'].exc_info` 记录到日志和 DB |
| ③ 审核队列标记 | 人工复核页面显示"AI 审核异常"标识，运营可直接人工审核 | `review_record` 表新增字段 `ai_status: normal|error` |

**arq 任务定义示例**：
```python
# services/knowledge/tasks/review_tasks.py
from arq import create_pool

async def ai_review_note(ctx, note_id: str, title: str, content: str):
    """AI 笔记审核任务 — 最多重试 3 次，失败后降级到人工"""
    try:
        provider = AIProvider()
        result = await provider.review_note(title, content)
        # ... 更新审核状态
    except Exception as e:
        # 第 3 次重试仍然失败时，arq 不再调用此函数
        # 在最终异常处理中兜底
        raise

async def handle_review_failure(job_ctx):
    """arq 任务最终失败回调 — 兜底逻辑"""
    note_id = job_ctx['args'][0]
    await mark_as_pending_manual(note_id, reason="ai_review_failed")
    await log_failure(job_ctx)
```

### 2.4 部署与运维

| 组件 | 选型 | 说明 |
|------|------|------|
| 容器编排 | Docker Compose | 统一管理 3 服务 + PostgreSQL + Redis |
| 服务编排 | depends_on + healthcheck | 控制容器启动顺序和依赖就绪检查（配置见下方） |
| 文件存储 | 本地磁盘 | Banner 图片存储于 /data/uploads/，FastAPI StaticFiles 挂载 |
| 环境配置 | python-dotenv + .env | 每个服务独立 .env，Docker Compose 传入环境变量 |
| 包管理 | pip-tools | requirements.in → requirements.txt 版本锁定 |

**服务依赖与健康检查配置**：

```yaml
# docker-compose.yml 核心配置示意
services:
  postgres:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5

  auth:
    build: ./services/auth
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8001/health"]
      interval: 30s
      timeout: 10s
      retries: 3

  knowledge:
    build: ./services/knowledge
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8002/health"]
      interval: 30s
      timeout: 10s
      retries: 3

  core:
    build: ./services/core
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
      knowledge:
        condition: service_started    # Core 启动时 Knowledge 只需已启动，无需完全健康
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
```

> **启动顺序说明**：
> 1. PostgreSQL 和 Redis 先启动，`condition: service_healthy` 确保数据库完全就绪后才启动应用服务
> 2. Auth 和 Knowledge 可并行启动（均只依赖 PG + Redis）
> 3. Core 在 Knowledge 启动后启动（`condition: service_started`），因为 Core 依赖 Knowledge 的 HTTP 接口
> 4. 每个应用服务自身提供 `/health` 端点供 Docker healthcheck 轮询

### 3.4 外部访问模型

Auth(:8001) 和 Core(:8000) 同时对外暴露，客户端需分别调用两个服务的 API。以下说明访问方式和部署策略。

#### 3.4.1 客户端配置

**小程序 / Web 管理端**需要配置两个 Base URL：

```javascript
// 客户端配置示例
const AUTH_BASE_URL = "https://api.example.com";      // → Auth :8001
const API_BASE_URL  = "https://api.example.com";      // → Core :8000
```

> **注意**：Auth 服务仅暴露登录（`POST /login`）、刷新 Token（`POST /refresh`）、修改密码（`PUT /password`）三个端点。其余全部业务 API 由 Core 提供。

**推荐方案**：
- **开发环境**：双端口直连（`localhost:8001` → Auth，`localhost:8000` → Core）
- **生产环境**：反向代理统一入口，Nginx 去除 `/auth/` 前缀后转发，使客户端两个服务的路径前缀一致（均为 `/api/v1/...`），降低前端接入成本

#### 3.4.2 部署策略

| 环境 | 策略 | 说明 |
|:----:|------|------|
| **开发环境** | 双端口直连 | `localhost:8001` → Auth，`localhost:8000` → Core。简单直接，方便调试。 |
| **生产环境** | 反向代理统一入口 | Nginx / Caddy 将 `/auth/*` 转发到 Auth:8001，其余转发到 Core:8000，对外统一为 `https://api.example.com`。 |

**生产环境 Nginx 配置示例**（路径重写，客户端无需感知 `/auth/` 前缀）：

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    # Auth 服务 — 客户端路径统一为 /api/v1/admin/login
    # Nginx 重写路径：/api/v1/admin/login → /api/v1/admin/login（透传）
    # 但转发到 auth:8001 而非 core:8000
    location /api/v1/admin/login {
        proxy_pass http://auth:8001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
    location /api/v1/admin/refresh {
        proxy_pass http://auth:8001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
    location /api/v1/admin/password {
        proxy_pass http://auth:8001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
    location /api/v1/login {
        proxy_pass http://auth:8001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
    location /api/v1/refresh {
        proxy_pass http://auth:8001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # Core 服务 — 全部业务 API + 静态文件
    location / {
        proxy_pass http://core:8000/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

> **设计说明**：Auth 服务仅 5 个端点（admin/login, admin/refresh, admin/password, login, refresh），在 Nginx 中逐条配置路径转发。客户端和 Core 服务的 API 路径前缀保持完全一致（`/api/v1/...`），前端只需配置一个 Base URL。如有新增端点，同步更新 Nginx 配置即可。

#### 3.4.3 Docker Compose 端口映射

```yaml
services:
  auth:
    ports:
      - "8001:8001"    # 开发环境暴露，生产环境移除
  core:
    ports:
      - "8000:8000"    # 始终暴露
  knowledge:
    ports:               # 不暴露任何宿主机端口
```

> **生产环境安全建议**：Auth 的 8001 端口只允许内网或反向代理访问，不直接暴露到公网。

## 4. 服务间通信规范

| 项目 | 规范 |
|------|------|
| **协议** | HTTP/1.1 REST，JSON 格式 |
| **内部客户端** | httpx（async/await）|
| **调用关系** | Core → Knowledge（**唯一**内部调用链路）|
| **认证传递** | 客户端从 Auth 获取 JWT → 携带 JWT 调用 Core → Core 本地 shared/auth.py 验签 |
| **默认超时** | 30s（普通查询），120s（AI 生成类）|
| **重试策略** | 幂等 GET 最多重试 2 次（exponential backoff），非幂等 POST/PUT/DELETE 不重试 |
| **服务发现** | Docker Compose 内部 DNS，服务名即 hostname（auth / knowledge / core）|
| **错误传递** | 内部服务返回自定义 JSON Error → Core 透传或包装 → 外部客户端 |

> **笔记存储策略说明**：
>
> `core.note` 表**仅存储已提交审核（submit-review）的笔记**，不存储用户的本地草稿。
> 这是遵循 PRD §2.1.3 "本地隐私默认"原则：
> - **未提交的笔记**：仅存在于小程序本地存储（wx.setStorage），服务端不感知
> - **提交审核的笔记**：通过 `POST /api/v1/notes/{note_id}/submit-review` 上传至服务端，
>   写入 `core.note` 表，状态设为 `pending_review`
> - **审核流程中的笔记**：状态流转在 `core.note` 表中通过 `status` 字段管理
>   （pending_review → screening → ai_review → pending_manual → approved / rejected）
> - **草稿不存在于服务端**：用户在小程序端编辑但未提交的笔记，卸载小程序后数据丢失
>   （PRD 明确的风险告知）
>
> **API 层约定**：`POST /api/v1/notes` 接口的调用时机需要小程序端配合——
> 小程序端先本地存储笔记，仅当用户点击"提交审核"时才调用此接口将笔记上传。
> 如果未来需要支持多端同步草稿，可考虑增加 `is_draft` 字段或独立的草稿同步接口，
> 但 v1.0 严格遵循 PRD 的本地优先策略。

**关联笔记在知识卡片被移除时的兜底策略**：

> **对应 PRD**：§2.1.3 "关联笔记在来源知识内容被移除时，保留笔记但去除关联链接"

当 Knowledge 服务删除某张知识卡片时，Core 侧关联的笔记（`core.note.card_id`）需要被置空。
这是一个跨服务的级联清理场景，采用 **懒清理（Lazy Cleanup）** 策略：

```
用户打开关联笔记详情
    │
    ├── Core 从 DB 读取 note.card_id（不为空）
    │
    ├── Core 调用 Knowledge API 校验卡片是否存在
    │   GET /api/v1/cards/{card_id}?fields=id
    │   ├── 返回 200 ✅ → 卡片存在，正常展示关联链接
    │   └── 返回 404 ❌ → 卡片已删除
    │
    └── 卡片已删除时：
        ├── 将 note.card_id 置为 NULL（异步 UPDATE）
        ├── 前端展示时关联链接区域隐藏
        └── 笔记正文内容不受影响
```

**实现规范**：

```python
# services/core/routes/notes.py

@router.get("/notes/{note_id}")
async def get_note_detail(note_id: str):
    note = await db.fetch_one("""
        SELECT id, title, content, card_id, status, ...
        FROM core.note WHERE id = :note_id
    """, {"note_id": note_id})

    # 懒清理：检查关联卡片是否仍有效
    card_info = None
    if note.card_id:
        try:
            card = await knowledge_client.get_card_detail(note.card_id)
            card_info = {"id": card["id"], "title": card["title"]}
        except KnowledgeNotFoundError:
            # 卡片已删除 → 异步置空 card_id
            asyncio.create_task(clear_note_card_id(note.id))
        except Exception:
            # 其他错误（如 Knowledge 服务熔断）→ 保留 card_id，下次再检查
            pass

    return {"data": {"note": dict(note), "related_card": card_info}}

async def clear_note_card_id(note_id: str):
    """后台任务：清除笔记的关联卡片 ID"""
    async with db.transaction():
        await db.execute("""
            UPDATE core.note SET card_id = NULL
            WHERE id = :note_id AND card_id IS NOT NULL
        """, {"note_id": note_id})
        await db.commit()
```

**为何选择懒清理而非主动通知**：

| 方案 | 复杂度 | 数据一致性 | 选用理由 |
|:----:|:------:|:---------:|----------|
| **主动通知**：Knowledge 删除卡片时回调 Core | 高：需添加回调端点 + 重试 + 幂等处理 | 强：立即清理 | ❌ 过度设计。关联笔记数量少，用户打开时清理完全可接受 |
| **被动清理**：Core 定时任务扫描 | 中：需定时扫描 + 批量查询 | 最终一致：T+1 清理 | ❌ 定时任务增加了不必要的查询开销 |
| **懒清理（本方案）**：用户打开笔记时按需清理 | 低：仅增加一次 Knowledge API 调用 | 最终一致：用户下次打开时清理 | ✅ 最简单，符合个人项目维护成本 |

SELECT 'issued'   AS type, COALESCE(SUM(points), 0) AS total
FROM core.points_record
WHERE points > 0
  AND DATE(created_at AT TIME ZONE 'Asia/Shanghai') = CURRENT_DATE
UNION ALL
SELECT 'consumed' AS type, COALESCE(SUM(ABS(points)), 0) AS total
FROM core.points_record
WHERE points < 0
  AND DATE(created_at AT TIME ZONE 'Asia/Shanghai') = CURRENT_DATE;

-- ④ 7 日留存率
-- 以 7 天前新增的用户为基数，统计今天仍有活跃记录的用户比例
WITH new_users_7d_ago AS (
    SELECT DISTINCT user_id
    FROM core.learning_record
    WHERE DATE(created_at AT TIME ZONE 'Asia/Shanghai') = CURRENT_DATE - INTERVAL '7 days'
),
active_today AS (
    SELECT DISTINCT user_id
    FROM core.learning_record
    WHERE DATE(created_at AT TIME ZONE 'Asia/Shanghai') = CURRENT_DATE
)
SELECT
    (SELECT COUNT(*) FROM new_users_7d_ago)                     AS cohort_size,
    (SELECT COUNT(*) FROM active_today WHERE user_id IN (SELECT user_id FROM new_users_7d_ago)) AS retained,
    ROUND(
        (SELECT COUNT(*) FROM active_today WHERE user_id IN (SELECT user_id FROM new_users_7d_ago))::numeric
        / NULLIF((SELECT COUNT(*) FROM new_users_7d_ago), 0) * 100, 1
    ) AS retention_rate_7day;

-- ⑤ 各行为积分获取占比
SELECT action_type,
       SUM(points)                    AS total_points,
       ROUND(SUM(points)::numeric / NULLIF(SUM(SUM(points)) OVER (), 0) * 100, 1) AS pct
FROM core.points_record
WHERE points > 0
  AND created_at >= NOW() - INTERVAL '7 days'
GROUP BY action_type
ORDER BY total_points DESC;

### 5.3 Redis 使用策略

| 用途 | Key 模式 | 说明 |
|------|---------|------|
| 敏感词缓存 | `sensitive:{match_type}` | Hash 结构，存储活跃敏感词 |
| 日上限计数器 | `daily:{user_id}:{action}` | 积分获取日上限，TTL=86400s。每 5 分钟持久化到 PostgreSQL，Redis 重启时从 DB 恢复计数（见下方持久化策略）|

**日上限原子性保证（Redis Lua 脚本）**：

积分获取必须满足：`当前累计值 + 本次积分 <= 日上限`，否则拒绝发放。使用 Redis Lua 脚本保证读取-判断-写入的原子性。

```lua
-- scripts/points_daily_limit.lua
-- KEYS[1] = daily:{user_id}:{action_type}   -- 日计数器 key
-- ARGV[1] = tostring( daily_limit )         -- 日上限（从配置读取）
-- ARGV[2] = tostring( points )              -- 本次应得积分
-- 返回值：-1 表示已达上限，>=0 表示增加后的累计值

local current = tonumber(redis.call('GET', KEYS[1]) or 0)
local limit = tonumber(ARGV[1])
local add = tonumber(ARGV[2])

-- 核心判断：current + add > limit 时拒绝，而非 current >= limit
-- 避免 current=8, add=5, limit=10 时错误允许超出上限
if current + add > limit then
    return -1
end

local new_value = redis.call('INCRBY', KEYS[1], add)
redis.call('EXPIRE', KEYS[1], 86400)
return new_value
```

> **设计要点**：
> - 使用 `current + add > limit` 而非 `current >= limit`：确保计数不会因单次积分超过上限
> - `EXPIRE` 在每个计数器 key 上设置，与 Lua 脚本同原子性，不存在 key 泄漏
> - 返回值 > 0 表示成功累加后的新累计值；返回 -1 表示已达上限

**Python 侧调用封装**（`services/core/services/points_service.py`）：

```python
from redis import Redis

LUA_SCRIPT = """
local current = tonumber(redis.call('GET', KEYS[1]) or 0)
local limit = tonumber(ARGV[1])
local add = tonumber(ARGV[2])
if current + add > limit then
    return -1
end
local new_value = redis.call('INCRBY', KEYS[1], add)
redis.call('EXPIRE', KEYS[1], 86400)
return new_value
"""

class PointsService:
    def __init__(self, redis: Redis):
        self._daily_limit_script = redis.register_script(LUA_SCRIPT)

    async def try_award_points(
        self, user_id: str, action: str, points: int, daily_limit: int
    ) -> bool:
        """原子性地尝试发放积分，达上限则返回 False"""
        key = f"daily:{user_id}:{action}"
        result = await self._daily_limit_script(
            keys=[key], args=[daily_limit, points]
        )
        if result == -1:
            return False
        return True
```

**日上限计数器持久化策略**：

```
Redis Lua 脚本原子写入（限流 + INCRBY + EXPIRE）
        │
        ▼
每 5 分钟 (APScheduler)
        │
        ├── 扫描所有 daily:* key（不删除 Redis key，双写共存）
        ├── 将 key/ttl/value 写入 PostgreSQL daily_counter_snapshot 表
        └── 使用 ON CONFLICT 避免重复写入
        │
        ▼
Redis 重启后
        │
        ├── 服务启动时从 daily_counter_snapshot 表恢复
        ├── 恢复逻辑：只恢复 TTL > 0 的记录（未过期）
        └── 恢复后清空快照表（防止下次重复恢复）
```

**持久化实现代码规范**：
```python
# services/core/tasks/points_persistence.py
from apscheduler.schedulers.asyncio import AsyncIOScheduler

PERSISTENCE_INTERVAL = 300  # 5 分钟

async def persist_daily_counters():
    """扫描 Redis daily:* 计数器，持久化到 PostgreSQL"""
    cursor = 0
    while True:
        cursor, keys = await redis.scan(cursor, match="daily:*", count=100)
        for key in keys:
            ttl = await redis.ttl(key)
            if ttl > 0:
                value = await redis.get(key)
                await db.execute("""
                    INSERT INTO daily_counter_snapshot (key_name, value, ttl, saved_at)
                    VALUES (:key, :value, :ttl, NOW())
                    ON CONFLICT (key_name) DO UPDATE SET value=:value, ttl=:ttl, saved_at=NOW()
                """, {"key": key, "value": value, "ttl": ttl})
        if cursor == 0:
            break
    await db.commit()

async def restore_daily_counters():
    """服务启动时从 PostgreSQL 恢复 Redis 计数器"""
    records = await db.fetch_all("SELECT * FROM daily_counter_snapshot WHERE ttl > 0")
    for record in records:
        remaining_ttl = record.ttl - (time.time() - record.saved_at.timestamp())
        if remaining_ttl > 0:
            await redis.set(record.key_name, record.value, ex=int(remaining_ttl))
    await db.execute("TRUNCATE daily_counter_snapshot")
    await db.commit()

@app.on_event("startup")
async def start_persistence():
    await restore_daily_counters()
    scheduler = AsyncIOScheduler()
    scheduler.add_job(persist_daily_counters, "interval", seconds=PERSISTENCE_INTERVAL)
    scheduler.start()
```
| 连续打卡 | `checkin:{user_id}` | 记录连续打卡天数 |
| arq 任务队列 | arq 自动管理 | 笔记审核异步任务 |
| 当日复习列表 | `review:{date}` | 缓存当日待复习卡片 ID 列表 |
| Token 黑名单 | `token:blacklist:{jti}` | 策略 B（简化版）：v1.0 不维护服务端黑名单，登出仅清除客户端 Token。JWT 有效期 24h，过期自动失效。如有安全审计需求可改为策略 A。 |

> **黑名单策略选型**：
> - **方案 A（Redis 实时黑名单）**：每次业务请求查 Redis 确认 token 是否被登出。增加 ~1ms/请求 的 Redis GET 延迟，但支持即时登出。适合安全要求高的场景。
> - **方案 B（客户端清除，本方案）**：登出只需客户端删除本地 Token。服务端不维护黑名单，已签发的 JWT 在其有效期内（24h）仍可使用，但前端已清除故用户无法感知。**个人项目推荐此方案**，开发成本低，零运行时开销。
>
> 如需切换为方案 A，在 Core 中间件中增加：`GET token:blacklist:{jti}` 检查，登出时 `SET token:blacklist:{jti} 1 EX 86400`。

**图片上传 API**（`services/core/routes/upload.py`）：
```python
import re
import uuid
import io
import magic
from pathlib import Path
from PIL import Image
from fastapi import UploadFile, File

ALLOWED_EXTENSIONS = {".jpg", ".jpeg", ".png", ".webp", ".gif"}
ALLOWED_MIME_TYPES = {"image/jpeg", "image/png", "image/webp", "image/gif"}
MAX_FILE_SIZE = 2 * 1024 * 1024  # 2MB
BANNER_WIDTH = 750
BANNER_HEIGHT = 300
UUID_PATTERN = re.compile(r'^[a-f0-9\-]{36}$')  # UUID v4 格式

@router.post("/admin/banners/{banner_id}/upload")
async def upload_banner_image(banner_id: str, file: UploadFile = File(...)):
    # ① 防止路径遍历：校验 banner_id 格式
    if not UUID_PATTERN.match(banner_id):
        raise HTTPException(400, detail="无效的 banner_id 格式")

    # ② 校验文件扩展名
    ext = Path(file.filename).suffix.lower()
    if ext not in ALLOWED_EXTENSIONS:
        raise HTTPException(400, detail="不支持的图片格式，仅允许 JPG/PNG/WebP/GIF")

    # ③ 读取内容并校验文件大小
    content = await file.read()
    if len(content) > MAX_FILE_SIZE:
        raise HTTPException(400, detail="图片大小超过 2MB 限制")

    # ④ MIME 类型校验（防止后缀名欺骗）
    mime_type = magic.from_buffer(content[:2048], mime=True)
    if mime_type not in ALLOWED_MIME_TYPES:
        raise HTTPException(400, detail="文件内容类型校验失败")

    # ⑤ 像素尺寸校验（确保 Banner 展示不变形）
    img = Image.open(io.BytesIO(content))
    actual_width, actual_height = img.size
    if actual_width != BANNER_WIDTH or actual_height != BANNER_HEIGHT:
        raise HTTPException(400, detail=f"Banner 图片尺寸必须为 {BANNER_WIDTH}×{BANNER_HEIGHT}px，"
                            f"当前为 {actual_width}×{actual_height}px")

    # ⑥ 生成唯一文件名，写入磁盘
    filename = f"{banner_id}_{uuid.uuid4().hex}{ext}"
    upload_dir = Path(settings.upload_dir) / "banners"
    upload_dir.mkdir(parents=True, exist_ok=True)

    # ⑦ 清理同一 banner_id 的旧文件（防止磁盘空间浪费）
    for old_file in upload_dir.glob(f"{banner_id}_*"):
        old_file.unlink()

    (upload_dir / filename).write_bytes(content)

    url = f"/static/banners/{filename}"
    return {"data": {"url": url}}
```

> **安全设计说明**：
> - **路径遍历防护**：使用正则 `UUID_PATTERN` 严格校验 `banner_id` 格式，阻止 `../` 等恶意输入
> - **MIME 校验**：通过 `python-magic` 库读取文件头的真实 MIME 类型，防止 `.jpg` 后缀的恶意文件
> - **尺寸校验**：通过 Pillow 读取图片实际像素尺寸，确保符合 `750×300px` 要求，防止小程序端拉伸变形
> - **旧文件清理**：同一业务 ID 重新上传时自动删除旧文件，避免磁盘空间被重复上传耗尽
> - **文件名随机化**：使用 `uuid.uuid4().hex` 生成随机后缀，防止文件名可预测导致的遍历攻击
>
> **依赖库**：需在 `requirements.txt` 中添加：
> - `python-magic`（或 Windows 下 `python-magic-bin==0.4.14`）— MIME 类型校验
> - `Pillow`（>=10.0.0）— 图片像素尺寸校验

**成就徽章上传**（接口类比）：

| 成就徽章图标 | `POST /api/v1/admin/achievements/{id}/upload` | `/data/uploads/achievements/` |

### 5.5 数据库初始化

#### 5.5.1 用户与 Schema 初始化

PostgreSQL 容器首次启动时自动执行 `init.sql`。由于 PostgreSQL 官方镜像的 `docker-entrypoint-initdb.d` 机制在容器**启动时（而非运行时）** 执行 SQL 脚本，无法直接读取 Docker Compose 的环境变量。

**解决方案**：使用 shell 脚本包装 `init.sql`，在脚本中读取环境变量并生成最终的 SQL：

```bash
#!/bin/bash
# docker-entrypoint-initdb.d/init.sh
# PostgreSQL 16+ 首次启动时自动执行
# 从环境变量读取数据库密码，生成 CREATE USER 语句

set -e

AUTH_PASSWORD="${AUTH_DB_PASSWORD:-auth_dev_password}"
KNOWLEDGE_PASSWORD="${KNOWLEDGE_DB_PASSWORD:-knowledge_dev_password}"
CORE_PASSWORD="${CORE_DB_PASSWORD:-core_dev_password}"

psql -v ON_ERROR_STOP=1 --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" <<-EOSQL
    -- ========== Auth 服务 ==========
    CREATE USER auth_user WITH PASSWORD '${AUTH_PASSWORD}';
    CREATE SCHEMA IF NOT EXISTS auth AUTHORIZATION auth_user;

    -- ========== Knowledge 服务 ==========
    CREATE USER knowledge_user WITH PASSWORD '${KNOWLEDGE_PASSWORD}';
    CREATE SCHEMA IF NOT EXISTS knowledge AUTHORIZATION knowledge_user;

    -- ========== Core 服务 ==========
    CREATE USER core_user WITH PASSWORD '${CORE_PASSWORD}';
    CREATE SCHEMA IF NOT EXISTS core AUTHORIZATION core_user;

    -- Core 对 auth 和 knowledge Schema 的只读权限（用于数据看板）
    GRANT USAGE ON SCHEMA auth TO core_user;
    GRANT SELECT ON ALL TABLES IN SCHEMA auth TO core_user;
    ALTER DEFAULT PRIVILEGES FOR USER auth_user IN SCHEMA auth
        GRANT SELECT ON TABLES TO core_user;

    GRANT USAGE ON SCHEMA knowledge TO core_user;
    GRANT SELECT ON ALL TABLES IN SCHEMA knowledge TO core_user;
    ALTER DEFAULT PRIVILEGES FOR USER knowledge_user IN SCHEMA knowledge
        GRANT SELECT ON TABLES TO core_user;
EOSQL
```

> **为什么使用 .sh 而非 .sql**：PostgreSQL 官方镜像的 `docker-entrypoint-initdb.d/` 目录同时支持 `.sql` 和 `.sh` 文件。`.sh` 脚本在容器启动时执行，可以访问 Docker Compose 注入的环境变量，动态生成 SQL 语句。

**Docker Compose 集成**（更新）：

```yaml
services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: codesail_db
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres_dev
      # 三个服务的数据库用户密码 — 与环境变量清单 §10.4 中的 DB_PASSWORD 保持一致
      AUTH_DB_PASSWORD: ${AUTH_DB_PASSWORD:-auth_dev_password}
      KNOWLEDGE_DB_PASSWORD: ${KNOWLEDGE_DB_PASSWORD:-knowledge_dev_password}
      CORE_DB_PASSWORD: ${CORE_DB_PASSWORD:-core_dev_password}
    volumes:
      - postgres_data:/var/lib/postgresql/data
      - ./docker/init.sh:/docker-entrypoint-initdb.d/init.sh  # 改用 .sh
    ports:
      - "5432:5432"

volumes:
  postgres_data:
```

> **生产环境密码管理**：生产环境中不要使用 `.env` 文件中的默认值。通过 Docker Compose 的 `--env-file` 参数或直接在 `environment` 中覆盖：
> ```bash
> # 生产环境启动命令
> AUTH_DB_PASSWORD="$(cat /run/secrets/db_auth_password)" \
> KNOWLEDGE_DB_PASSWORD="$(cat /run/secrets/db_knowledge_password)" \
> CORE_DB_PASSWORD="$(cat /run/secrets/db_core_password)" \
> docker compose up -d
> ```
>
> 密码变更时只需更新环境变量并重建容器（删除 volume 后重新初始化）：`docker compose down -v && docker compose up -d`。**所有服务的密码在 `environment` 中集中定义，不存在"多处修改"问题。**

    admin = await db.get(Admin, settings.admin_username)

> **注意**：Alembic 数据迁移和启动时初始化的边界：
> - **结构化种子数据（如知识领域）**：使用 Alembic 数据迁移（`data_migration`）。知识领域涉及名称、图标、免费/付费状态等多字段且存在章节→卡片的关联依赖，Alembic 迁移脚本可版本控制、支持回滚，适合这种有结构的数据初始化。
> - **简单配置值（如积分规则、主题色）**：使用启动时 `@app.on_event("startup")` 检查初始化。这些配置值独立、无关联依赖，启动时检查更灵活，无需先执行迁移脚本。
>
> 两种方式各有适用场景，按数据特征选择而非一刀切。各服务可独立检查自己负责的种子数据。

### 5.6 数据库连接池配置

三个服务共享同一个 PostgreSQL 实例，需合理配置连接池参数防止连接数超限。

#### 5.6.1 各服务连接池配置

| 参数 | Auth | Knowledge | Core | 说明 |
|:----|:----:|:---------:|:----:|------|
| `pool_size` | 5 | 10 | 15 | 最小维持连接数 |
| `max_overflow` | 3 | 5 | 5 | 超出 pool_size 的最大临时连接数 |
| `pool_timeout` | 30s | 30s | 30s | 等待连接的超时时间 |
| `pool_pre_ping` | true | true | true | 每次借用连接前检查是否可用 |
| `max_connections` | ~8 | ~15 | ~20 | 预估最大连接数（pool_size + max_overflow）|

> **三服务总连接估算**：8 + 15 + 20 = **约 43 个连接**，远低于 PostgreSQL 默认 `max_connections=100`，留有充足余量。

#### 5.6.2 代码配置示例

### 5.7 缓存策略

当前架构中 Core→Knowledge 的 HTTP 调用是唯一内部调用链路。对于变化频率低、读取频率高的数据，应在 Core 侧加 Redis 缓存，减少不必要的内部调用。

#### 5.7.1 缓存分层策略

```
客户端 → Core 业务逻辑层
              │
              ├── ① 查 Redis 缓存（读高频、写低频的数据）
              │      命中 → 直接返回
              │      未命中 → 走 Knowledge API → 写入 Redis → 返回
              │
              └── ② 直接查本地 DB（core schema 自有数据）
                       无需缓存或缓存穿透时兜底
```

#### 5.7.2 缓存数据清单

| 数据 | 缓存位置 | TTL | 失效触发 | 说明 |
|------|:-------:|:---:|----------|------|
| 知识领域列表 | Core Redis | 300s（5分钟）| 管理端修改领域后主动失效 | 变化频率天级，缓存命中率 > 99% |
| 章节列表（按领域）| Core Redis | 300s | 管理端修改章节后主动失效 | key: `chapters:{domain_id}` |
| 卡片列表（按章节）| Core Redis | 300s | 管理端修改卡片后主动失效 | key: `cards:{chapter_id}` |
| 卡片详情 | Core Redis | 600s（10分钟）| 管理端编辑卡片后主动失效 | key: `card:{card_id}` |
| Banner 列表 | Core Redis | 600s | 管理端修改 Banner 后主动失效 | 小程序首页每次打开都读 |
| 主题色配置 | Core Redis | 3600s（1小时）| 管理端修改后主动失效 | 变化频率极低（周级） |
| 积分规则 | Core Redis | 3600s | 管理端修改后主动失效 | 变化频率低（周级） |
| 解锁消耗配置 | Core Redis | 3600s | 管理端修改后主动失效 | 变化频率低 |
| 公告 | Core Redis | 300s | — | 短 TTL 自行失效即可 |

> **主动失效机制**：Web 管理端修改以上数据时，Core 在 Knowledge 修改成功后，`publish` 对应 key 到 Redis 的失效通道（`DEL key`）。不需要复杂的消息队列。

#### 5.7.3 缓存失效策略

```
Web 管理端修改领域/章节/卡片/Banner/配置
    │
    ├── Core → Knowledge API 执行修改
    │       修改成功
    │
    ├── Core DEL Redis 对应缓存 key
    │       立即失效
    │
    └── 下次读取 → Redis 未命中 → 回源 Knowledge API → 重新缓存
```

#### 5.7.4 Core 侧缓存封装

```python
# services/core/services/cache_service.py

CACHE_TTL = {
    "domains": 300,
    "chapters": 300,
    "cards": 300,
    "card_detail": 600,
    "banners": 600,
    "theme": 3600,
    "points_rules": 3600,
}

class CacheService:
    """统一缓存封装：读时回源，写时失效"""

    def __init__(self, redis, knowledge_client):
        self.redis = redis
        self.knowledge = knowledge_client

    async def get_or_fetch(
        self, cache_key: str, ttl: int, fetch_func
    ):
        """缓存优先，未命中则回源"""
        cached = await self.redis.get(cache_key)
        if cached:
            return json.loads(cached)

        data = await fetch_func()
        if data is not None:
            await self.redis.set(cache_key, json.dumps(data), ex=ttl)
        return data

    async def invalidate(self, cache_key: str):
        """主动失效"""
        await self.redis.delete(cache_key)
```

> **设计说明**：缓存策略的定位是**减少 Core→Knowledge HTTP 调用延迟**，而非缓存数据库查询。Core 自有数据（学习记录、积分明细等写密集型数据）不在此缓存范围内。

## 7. 安全设计

| 维度 | 方案 |
|------|------|
| **密码存储** | bcrypt（work_factor=12），通过 passlib 库 |
| **JWT 签名** | HS256，Secret 通过环境变量注入 |
| **JWT 有效期** | access_token: 24h，refresh_token: 7d |
| **刷新策略** | refresh token 每次使用时轮换（rotate），旧 token 失效 |
| **内部隔离** | Knowledge 服务不绑定宿主机端口，仅 Docker 内部网络可访问 |
| **数据库凭据** | 每个服务使用独立的数据库用户，授予最小必要权限 |
| **CORS** | 生产环境仅允许 Web 管理端域名 |
| **请求限流** | Auth 登录端点：5 次/分钟/IP；Core 业务端点：60 次/分钟/用户 |

#### 限流实现 — 滑动窗口计数器（Lua 脚本）

对敏感端点（登录、笔记提交等）采用 **滑动窗口计数器** 实现限流，保证时间窗口内的请求数不超过阈值。

```lua
-- scripts/rate_limit_sliding_window.lua
-- KEYS[1] = rate_limit:{endpoint}:{identifier}  -- 限流 key
--        示例：rate_limit:login:ip:192.168.1.1
--              rate_limit:submit:user:uuid
-- ARGV[1] = tostring(window_ms)      -- 时间窗口（毫秒），如 60000（1 分钟）
-- ARGV[2] = tostring(max_requests)   -- 窗口内最大请求数，如 5
-- ARGV[3] = tostring(now_ms)         -- 当前时间戳（毫秒）
-- 返回值：1 表示允许通过，0 表示限流拒绝

local window_ms = tonumber(ARGV[1])
local max_requests = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local window_start = now - window_ms

-- 移除窗口外的过期请求记录
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, window_start)

-- 统计当前窗口内请求数
local current = redis.call('ZCARD', KEYS[1])

if current >= max_requests then
    return 0  -- 限流拒绝
end

-- 记录本次请求，设置 TTL 防止内存泄漏
redis.call('ZADD', KEYS[1], now, now .. ':' .. math.random())
redis.call('EXPIRE', KEYS[1], math.ceil(window_ms / 1000))
return 1  -- 允许通过
```

**Python 侧调用封装**：

```python
# services/shared/rate_limiter.py
import time

SLIDING_WINDOW_SCRIPT = """
local window_ms = tonumber(ARGV[1])
local max_requests = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local window_start = now - window_ms
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, window_start)
local current = redis.call('ZCARD', KEYS[1])
if current >= max_requests then
    return 0
end
redis.call('ZADD', KEYS[1], now, now .. ':' .. math.random())
redis.call('EXPIRE', KEYS[1], math.ceil(window_ms / 1000))
return 1
"""

class RateLimiter:
    """滑动窗口限流器"""

    def __init__(self, redis):
        self._script = redis.register_script(SLIDING_WINDOW_SCRIPT)

    async def check_rate_limit(
        self, endpoint: str, identifier: str,
        max_requests: int = 5, window_seconds: int = 60
    ) -> bool:
        """
        检查请求是否被限流
        返回 True 表示允许通过，False 表示限流拒绝
        """
        key = f"rate_limit:{endpoint}:{identifier}"
        now_ms = int(time.time() * 1000)
        window_ms = window_seconds * 1000

        result = await self._script(
            keys=[key],
            args=[window_ms, max_requests, now_ms]
        )
        return result == 1
```

**限流配置清单**：

| 端点 | 限流维度 | 窗口 | 上限 | 说明 |
|:----:|:--------:|:----:|:----:|------|
| `POST /api/v1/login` | IP | 1 分钟 | 5 次 | 防止 wx.login 接口被滥用 |
| `POST /api/v1/admin/login` | IP | 1 分钟 | 5 次 | 防止暴力破解管理员密码 |
| `POST /api/v1/notes/{id}/submit-review` | 用户 | 1 分钟 | 3 次 | 防止恶意刷审核 |
| `GET /api/v1/notes/{id}/share-card` | note_id | 1 分钟 | 60 次 | 分享链接防刷 |
| 其余业务端点 | 用户 | 1 分钟 | 60 次 | 通用业务限流 |

> **限流维度说明**：
> - **IP 维度**：通过 `X-Forwarded-For` 或 `X-Real-IP` 请求头获取客户端真实 IP（反向代理场景），开发环境直接使用 `request.client.host`
> - **用户维度**：通过 JWT payload 中的 `sub`（openid）或 `role` 区分。未认证的请求回退到 IP 维度
> - **note_id 维度**：通过路径参数提取，按资源 ID 限流防止被针对

#### Refresh Token 并发保护（多代容忍窗口）

**问题**：客户端在 access_token 过期瞬间可能同时发起多个并发请求，每个都尝试用同一个 refresh_token 刷新。如果服务端每次刷新都使旧 token 立即失效，则只有一个请求会成功，其余因"旧 token 已失效"被拒绝，导致客户端被迫重新登录。

**解决方案（多代容忍窗口）**：

```
正常时序：
  客户端 → POST /refresh { refresh_token: "R1" }
      服务端验证 R1 有效 → 签发 R2 → 将 R1 加入"已使用"列表
      客户端后续使用 R2

并发场景：
  请求A → POST /refresh { refresh_token: "R1" }
  请求B（同时）→ POST /refresh { refresh_token: "R1" }
      服务端：R1 在"已使用"列表中不存在 → 两个都通过
      签发 R2（给请求A）和 R3（给请求B）
      将 R1 加入"已使用"列表

  问题：R1 被用了两次，但这是合法的并发刷新，不是重放攻击
```

**实现策略（短窗口容忍）**：

```python
# services/auth/services/auth_service.py

REFRESH_TOKEN_GRACE_WINDOW = 30  # 秒：旧 refresh_token 的容忍窗口

async def refresh_access_token(refresh_token: str) -> TokenResponse:
    """刷新 token — 带 30 秒多代容忍窗口"""

    # 1. 解析 JWT，验证签名和过期
    payload = verify_refresh_token(refresh_token)
    jti = payload["jti"]  # JWT ID

    # 2. 检查是否在"已使用"黑名单中
    used_key = f"refresh:used:{jti}"
    if await redis.get(used_key):
        # ⚠️ 在容忍窗口外复用 → 可能是 token 泄露
        ttl = await redis.ttl(used_key)
        remaining = await redis.ttl(f"refresh:family:{payload['sub']}")
        if ttl < REFRESH_TOKEN_GRACE_WINDOW and remaining > 0:
            # 容忍窗口已过 → 拒绝
            raise HTTPException(401, "refresh token 已过期")
        # 容忍窗口内 → 允许（视为并发刷新）

    # 3. 签发新的 refresh_token（新 jti）
    new_payload = {
        "sub": payload["sub"],
        "role": payload["role"],
        "type": "refresh",
        "jti": str(uuid.uuid4()),
        "exp": time.time() + 7 * 86400,
    }
    new_refresh_token = encode_jwt(new_payload)

    # 4. 将旧 jti 加入"已使用"列表，TTL = 容忍窗口 + 余量
    await redis.setex(used_key, REFRESH_TOKEN_GRACE_WINDOW + 10, "1")

    # 5. 签发新的 access_token
    access_token = create_access_token(payload["sub"], payload["role"])

    return TokenResponse(access_token=access_token, refresh_token=new_refresh_token)
```

> **设计要点**：
> - 容忍窗口（30秒）内，同一 refresh_token 可被多次使用——覆盖客户端并发刷新场景
> - 容忍窗口外复用同一 refresh_token → 拒绝（可能是 token 泄露或被截获重放）
> - `refresh:family:{user_id}` 记录用户当前有效的 refresh_token jti，用于撤销所有会话
> - 此方案在安全性和用户体验之间取得平衡，适合个人项目的安全需求

#### 权限校验规则

Core 服务的中间件按路径前缀执行角色校验：

```
所有请求 → JWT 签名验证（401 如果无效）
    │
    ├── 路径以 /api/v1/admin/* 开头 → 要求 role == "admin"
    │                                   不匹配则返回 403 FORBIDDEN

    ├── 路径以 /api/v1/config/* 开头 → 公开端点（无需 JWT）
    │                                   Banner/主题色/公告等配置查询
    │
    └── 其余 /api/v1/* 路径 → 要求 role == "user"
                                        不匹配则返回 403 FORBIDDEN
```

**例外情况**（无需认证的公开端点）：

| 端点 | 所属服务 | 说明 |
|------|:-------:|------|

#### Core 中间件实现规范

```python
# services/core/middleware/auth.py 伪代码

PUBLIC_PATHS = {"/api/v1/config/banners", "/api/v1/config/theme", ...}
ADMIN_PREFIX = "/api/v1/admin"

@app.middleware("http")
async def authorize(request: Request, call_next):
    # 1. 公开路径跳过认证
    if request.url.path in PUBLIC_PATHS or request.url.path == "/health":
        return await call_next(request)

    # 2. 解析 JWT
    token = extract_token(request.headers.get("Authorization", ""))
    payload = verify_jwt(token)  # shared/auth.py

    # 3. 角色校验
    if request.url.path.startswith(ADMIN_PREFIX):
        if payload.get("role") != "admin":
            return JSONResponse(status_code=403, content={"error": {"code": "FORBIDDEN", ...}})

    # 4. 注入用户信息到 request.state
    request.state.user = payload
    return await call_next(request)
```

#### 请求链路追踪

**原理**：在 Core 服务入口生成唯一 `X-Request-ID`，通过 httpx 请求头透传给 Knowledge 服务，两个服务的日志都记录此 ID，用于跨服务问题排查。

```
客户端请求
    │  无 X-Request-ID
    ▼
Core(:8000) ── 生成 UUID ──→ 记录日志 (request_id=xxx)
    │
    │  httpx 请求头携带 X-Request-ID: xxx
    ▼
Knowledge(:8002) ── 读取请求头 ──→ 记录日志 (request_id=xxx)
```

**实现规范**：

```python
# 核心：使用 contextvars 实现跨中间件/函数/httpx 调用的 request_id 透传
from contextvars import ContextVar
import uuid

request_id_var: ContextVar[str] = ContextVar("request_id", default="")

def get_current_request_id() -> str:
    """获取当前请求的 request_id（供 httpx 透传）"""
    return request_id_var.get()

# Core 入口中间件
@app.middleware("http")
async def add_request_id(request: Request, call_next):
    request_id = request.headers.get("X-Request-ID", str(uuid.uuid4()))
    request_id_var.set(request_id)  # ContextVar 设置当前请求上下文
    start = time.time()
    response = await call_next(request)
    elapsed = int((time.time() - start) * 1000)
    logger.bind(request_id=request_id).info("request completed", elapsed_ms=elapsed)
    response.headers["X-Request-ID"] = request_id
    return response

# Core → Knowledge 调用时透传
class KnowledgeClient:
    async def _request(self, method, path, **kwargs):
        headers = kwargs.get("headers", {})
        headers["X-Request-ID"] = get_current_request_id()  # 从 ContextVar 获取
        kwargs["headers"] = headers
        return await self.client.request(method, path, **kwargs)
```

> **关于 `contextlib.singleton_context` 的说明**：Python 标准库中**不存在** `contextlib.singleton_context` 这个函数。如果您在网络上看到相关代码，那可能是第三方库或 Python 未来版本的提案。本文档使用 `contextvars.ContextVar` 作为标准的跨异步上下文传递方案，它是 Python 3.7+ 内置的标准库，在 FastAPI/httpx 异步生态中工作稳定。

| 依赖 | Core | Knowledge | Auth |
|:----:|:----:|:---------:|:----:|
| PostgreSQL | ✅ 查询 `SELECT 1` | ✅ 查询 `SELECT 1` | ✅ 查询 `SELECT 1` |
| Redis | ✅ PING | ✅ PING | — |
| Knowledge 服务 | ✅ 调用 `/health`（仅记录降级，不影响 healthcheck 结果）| — | — |
| DeepSeek API | — | ❌ 可选检查（避免消耗额度） | — |

> **Docker HEALTHCHECK 配置策略**：
>
> ⚠️ **关键设计决策**：Docker HEALTHCHECK 只能区分"通过"和"不通过"两种状态。如果 `/health` 在非关键依赖（如 Knowledge 服务）不可用时返回 HTTP 503，Docker 会重启 Core 容器；如果 Knowledge 正在重启中，Core 反复重启就形成**级联宕机**。
>
> **原则**：Docker HEALTHCHECK **只检查关键依赖**（数据库连接 + 自身进程存活），非关键依赖仅降级不触发重启。
>
> 各服务的 `/health` 端点实现策略：
> ```
> Core /health 响应逻辑：
>   ├── 数据库可连接 + 服务存活 → HTTP 200 { status: "healthy" }
>   ├── 数据库可连接 + Knowledge 不可达 → HTTP 200 { status: "degraded" }
>   │                                       （仅降级，不标记为 unhealthy）
>   └── 数据库不可连接 → HTTP 503 { status: "unhealthy" }
>                          （触发 Docker 重启）
>
> Auth /health 响应逻辑：
>   ├── 数据库可连接 + 服务存活 → HTTP 200
>   └── 数据库不可连接 → HTTP 503
>
> Knowledge /health 响应逻辑：
>   ├── 数据库可连接 + 服务存活 → HTTP 200
>   └── 数据库不可连接 → HTTP 503
> ```
>
> **Docker HEALTHCHECK 指令**（三个服务通用，以 Core 为例）：
> ```dockerfile
> # Docker 仅检查：服务进程存活（HTTP 200）+ 关键依赖（数据库）
> # 非关键依赖（Knowledge 服务）的降级不触发重启
> HEALTHCHECK --interval=30s --timeout=10s --start-period=30s --retries=3 \
>     CMD curl -f http://localhost:8000/health || exit 1
> ```
> 由于 `/health` 端点在 Knowledge 不可用时返回 HTTP 200（degraded），`curl -f` 不会返回非零退出码，因此 Docker 不会重启 Core。只有当数据库不可用（返回 HTTP 503）时，healthcheck 才会失败触发重启。

## 9. 关键技术难点与解决方案

| 难点 | 解决方案 |
|------|----------|
| AI JSON 解析健壮性 | Pydantic 模型校验 + 自动重试 + fallback 默认值 |
| 积分日上限原子性 | Redis Lua 脚本保证读-判断-写原子操作 |
| 敏感词多模式匹配去重 | 四模式并行匹配 → 按敏感词 ID 去重合并 → 最高风险等级优先。Aho-Corasick 双缓冲自动机支持动态更新。|
| 间隔重复调度 | APScheduler 定时任务 + Redis 缓存。每日 00:05 由 Core 服务计算当日待复习列表，结果缓存到 Redis。用户修改复习节点仅对新学习的卡片生效。 |
| **服务熔断** | pybreaker 断路器：Core→Knowledge 调用连续失败 N 次后快速失败（fail fast），N/2 秒后半开重试。防止 Knowledge 故障时 Core 连接池被耗尽。 |

**间隔重复调度详细设计**：

> **时区策略**：所有时间统一使用北京时间（Asia/Shanghai，UTC+8）计算复习计划。
> 数据库存储 UTC 时间戳，应用层转换到北京时间后再计算日期边界。
> 理由：目标用户为中国大陆微信小程序用户，使用北京时间判断"今天"更符合用户感知。

**触发机制**：使用 APScheduler（AsyncIOScheduler）在 Core 服务启动时注册定时任务：

```python
# services/core/tasks/review_scheduler.py
from zoneinfo import ZoneInfo
from datetime import date, datetime
from apscheduler.schedulers.asyncio import AsyncIOScheduler

TZ = ZoneInfo("Asia/Shanghai")
scheduler = AsyncIOScheduler(timezone=TZ)  # 全局指定时区

async def calculate_daily_reviews():
    """每日北京时间 00:05 执行：计算当日待复习卡片并写入 Redis 缓存"""
    today = datetime.now(TZ).date()  # 时区感知的今天
    records = await db.execute("""
        SELECT user_id, card_id FROM learning_record
        WHERE $1 - learning_date::date = ANY(review_nodes)
    """, today)
    for user_id, card_ids in group_by_user(records):
        key = f"review:{today.isoformat()}:{user_id}"
        await redis.sadd(key, *card_ids)
        await redis.expire(key, 86400 * 2)  # TTL 2 天
    logger.info(f"每日复习计划已计算: {today} (TZ: Asia/Shanghai)")

@app.on_event("startup")
async def start_scheduler():
    scheduler.add_job(
        calculate_daily_reviews,
        trigger="cron",
        hour=REVIEW_CALC_HOUR,
        minute=REVIEW_CALC_MINUTE,
        timezone=TZ,  # 显式指定 cron 触发器时区
        id="daily_review_calc",
        misfire_grace_time=600
    )
    scheduler.start()
```

> **关于 `date.today()` 的陷阱**：Python 的 `date.today()` 返回服务器本地日期。如果服务器时区设为 UTC，在 UTC+8 时区的用户看来，"今天"的计算结果会偏差 8 小时。例如北京时间 08:05 对应 UTC 00:05，如果使用 `date.today()`（UTC），则在 UTC 00:05（北京 08:05）计算时的"今天"是 UTC 日期，比北京日期晚 8 小时。**解决方案**：始终使用 `datetime.now(TZ).date()` 获取时区感知的当前日期。

**复习节点变更规则**：
| 场景 | 行为 |
|------|------|
| 用户修改复习节点 | 仅对新学习的卡片生效，已排入复习计划的不受影响 |
| 新增学习记录 | 插入 `learning_record` 表，下次 `calculate_daily_reviews` 自动纳入计算 |
| 用户删除学习记录 | 删除 `learning_record`，当天缓存不变（T+1 自动失效）|

CORE_CALLBACK_URL = "http://core:8000/api/v1/notes/callback"

async def ai_review_note(ctx, note_id: str, title: str, content: str, callback_url: str):
    """AI 笔记审核任务 — 审核完成后回调 Core 更新状态"""
    import httpx
    try:
        provider = AIProvider()
        result = await provider.review_note(title, content)

        # 根据审核结果决定回调 payload
        payload = {
            "note_id": note_id,
            "risk_score": result.risk_score,
            "risk_labels": result.risk_labels,
        }
        if result.needs_manual_review:
            payload["status"] = "pending_manual"
        elif result.is_rejected:
            payload["status"] = "rejected"
            payload["reject_reason"] = result.reject_reason
        else:
            payload["status"] = "approved"

        # 回调 Core 更新状态
        async with httpx.AsyncClient() as client:
            await client.post(callback_url, json=payload, timeout=10)

    except Exception:
        raise  # arq 自动重试 3 次

async def handle_review_failure(job_ctx):

    note_id = job_ctx['args'][0]
    callback_url = job_ctx['args'][3]  # 从任务参数中获取
    await mark_as_pending_manual(note_id)
    async with httpx.AsyncClient() as client:
        await client.post(callback_url, json={
            "note_id": note_id,
            "status": "pending_manual",
            "risk_score": None,
            "risk_labels": ["ai_review_failed"],
            "reject_reason": "AI审核异常，已转入人工复核"

**敏感词多模式匹配引擎详细设计**：

```

    │
    ├── 模式① 精确匹配 → AC 自动机（O(n) 实时）

**去重合并策略**：
```python
# 去重合并核心逻辑
class SensitiveHitDeduplicator:
    def merge(self, results: list[HitResult]) -> MergeResult:
        """多模式匹配结果去重合并"""
        seen = {}  # word_id -> HitResult
        for hit in results:
            word_id = hit.word_id
            if word_id in seen:
                # 同词命中多模式 → 合并位置列表，取最高风险
                seen[word_id].positions.extend(hit.positions)
                seen[word_id].risk_level = max(seen[word_id].risk_level, hit.risk_level)
                seen[word_id].match_modes.add(hit.match_mode)
            else:
                seen[word_id] = hit
        
        return MergeResult(
            hit_words=[h.word_text for h in seen.values()],
            total_hits=len(seen),
            max_risk_level=max(h.risk_level for h in seen.values()) if seen else 0
        )
```

**双缓冲自动机（Double Buffer AC）**：
```python
class DoubleBufferAC:
    """支持动态更新的双缓冲 AC 自动机"""
    def __init__(self):
        self._active = ACAutomaton()   # 当前服务请求的自动机
        self._standby = ACAutomaton()  # 后台构建中的自动机
        self._lock = asyncio.Lock()
    
    async def reload(self, words: list[SensitiveWord]):
        """后台重建 standby，构建完成后原子切换"""
        standby = ACAutomaton()
        standby.build(words)
        async with self._lock:
            self._active, self._standby = standby, self._active
        logger.info(f"敏感词自动机已更新: {len(words)} 词")
    
    async def match(self, text: str) -> list[HitResult]:
        """使用当前 active 自动机匹配，不阻塞 reload"""
        async with self._lock:
            automaton = self._active
        return automaton.search(text)
```

**出题算法**：

```
每日挑战出题算法
    │
    │  输入：用户 ID，日期
    │  输出：5 道单选题
    │
    ├── 步骤① 获取用户已掌握的卡片（learning_record.status = 'mastered'）
    │         └── 从中随机选取 3 道对应题目（已学知识，巩固为主）
    │
    ├── 步骤② 获取用户未学习的卡片（覆盖生疏领域）
    │         └── 从中随机选取 2 道对应题目（激发学习兴趣）
    │
    ├── 步骤③ 合并 → 打乱选项和题目顺序
    │
    ├── 步骤④ 缓存到 Redis（key: daily_challenge:{date}:{user_id}, TTL: 86400s）
    │         确保一天内同一用户的每日挑战题目固定
    │
    └── 步骤⑤ 如果题库总量 < 5，剩余不足部分用已学题目补全

**核心实现代码规范**：

```python
# services/core/services/daily_challenge.py
import random
from datetime import date

class DailyChallengeService:
    """每日挑战出题服务"""

    async def generate_challenge(self, user_id: str, today: date) -> list[dict]:
        """为用户生成当日挑战题目"""
        # 检查是否已生成（防止重复生成导致题目不一致）
        cache_key = f"daily_challenge:{today.isoformat()}:{user_id}"
        cached = await redis.get(cache_key)
        if cached:
            return json.loads(cached)

        # ① 获取用户已掌握的卡片 ID 列表
        mastered = await db.fetch_all("""
            SELECT card_id FROM core.learning_record
            WHERE user_id = :uid AND status = 'mastered'
        """, {"uid": user_id})
        mastered_ids = [r.card_id for r in mastered]

        # ② 通过 KnowledgeClient API 获取所有已发布卡片
        #    不直接跨 Schema 查询 knowledge.card，遵循"每个服务只读写自己的 Schema"原则
        published_cards = await knowledge_client.get_published_cards()
        all_ids = [c["id"] for c in published_cards]
        unlearned_ids = list(set(all_ids) - set(mastered_ids))

        # ③ 按比例选题：已学 3 道 + 未学 2 道
        known_pool = mastered_ids if mastered_ids else all_ids
        new_pool = unlearned_ids if unlearned_ids else all_ids

        selected_ids = list(random.sample(known_pool, min(3, len(known_pool))))
        selected_ids += list(random.sample(new_pool, min(2, len(new_pool))))

        # ④ 若不足 5 道，用已学补全
        if len(selected_ids) < 5:
            remaining = [c for c in all_ids if c not in selected_ids]
            selected_ids += list(random.sample(remaining, 5 - len(selected_ids)))

        # ⑤ 从题库中加载完整题目并打乱
        questions = await self._load_questions(selected_ids)
        random.shuffle(questions)

        # ⑥ 缓存题目到 Redis
        await redis.set(cache_key, json.dumps(questions), ex=86400)

        # ⑦ 持久化题目 ID 列表到 DB（Redis 丢失后可恢复）
        await db.execute("""
            INSERT INTO core.daily_challenge
                (user_id, challenge_date, total_count, status, question_ids)
            VALUES (:uid, :today, :total, 'incomplete', :qids)
            ON CONFLICT (user_id, challenge_date) DO UPDATE
                SET question_ids = EXCLUDED.question_ids
        """, {
            "uid": user_id, "today": today,
            "total": len(questions), "qids": selected_ids
        })
        await db.commit()

        return questions

    async def submit_challenge(
        self, user_id: str, answers: list[AnswerSubmit]
    ) -> ChallengeResult:
        """提交每日挑战答案并计算积分"""
        today = date.today()

        # 从 Redis 缓存获取题目
        cache_key = f"daily_challenge:{today.isoformat()}:{user_id}"
        questions_raw = await redis.get(cache_key)

        if not questions_raw:
            # ⚠️ Redis 缓存丢失 — 从 DB 恢复当日题目
            challenge = await db.fetch_one("""
                SELECT question_ids, total_count FROM core.daily_challenge
                WHERE user_id = :uid AND challenge_date = :today
            """, {"uid": user_id, "today": today})
            if not challenge:
                return ChallengeResult(error="challenge_not_found")
            questions = await self._load_questions(challenge.question_ids)
        else:
            questions = json.loads(questions_raw)

        correct = 0
        details = []
        for q, ans in zip(questions, answers):
            is_correct = q["correct_option"] == ans.selected_option
            if is_correct:
                correct += 1
            details.append({"question_id": q["id"], "correct": is_correct})

        all_correct = correct == len(questions)

        # 更新挑战记录
        await db.execute("""
            UPDATE core.daily_challenge
            SET status = 'completed',
                correct_count = :correct,
                all_correct = :all_correct
            WHERE user_id = :uid AND challenge_date = :today
        """, {
            "correct": correct, "all_correct": all_correct,
            "uid": user_id, "today": today
        })

        # 全对时才发放积分
        points_earned = 0
        if all_correct:
            points_earned = await self._award_points(user_id, "daily_challenge")
            await db.commit()

        return ChallengeResult(
            total=len(questions),
            correct=correct,
            all_correct=all_correct,
            points_earned=points_earned,
            details=details,
        )
```

```

    │   └── 其他 → 仅打卡，无额外积分

```python
# services/core/services/checkin_service.py

class ContinuousCheckinService:
    """连续打卡服务"""

    async def checkin(self, user_id: str, today: date) -> CheckinResult:
        """每日打卡：记录打卡、计算连续天数、发放里程碑积分"""

        # ① 检查是否已打卡（防止重复触发）
        existing = await db.fetch_one("""
            SELECT 1 FROM core.continuous_checkin
            WHERE user_id = :uid AND checkin_date = :today
        """, {"uid": user_id, "today": today})
        if existing:
            return CheckinResult(already_checkin=True)

        # ② 查询前一天打卡记录判断连续性
        yesterday = today - timedelta(days=1)
        prev = await db.fetch_one("""
            SELECT streak_count FROM core.continuous_checkin
            WHERE user_id = :uid AND checkin_date = :yesterday
        """, {"uid": user_id, "yesterday": yesterday})

        streak_count = (prev.streak_count + 1) if prev else 1

        # ③ 检查里程碑
        milestone = None
        milestone_points = 0
        if streak_count == 3:
            milestone = "day3"
            milestone_points = 15
        elif streak_count == 7:
            milestone = "day7"
            milestone_points = 30
        elif streak_count == 14:
            milestone = "day14"
            milestone_points = 60

        # ④ 写入打卡记录
        await db.execute("""
            INSERT INTO core.continuous_checkin
                (user_id, checkin_date, streak_count, milestone,
                 milestone_awarded)
            VALUES (:uid, :today, :streak, :milestone,
                    :awarded)
        """, {
            "uid": user_id, "today": today,
            "streak": streak_count,
            "milestone": milestone,
            "awarded": milestone_points > 0
        })

        # ⑤ 发放里程碑积分
        if milestone_points > 0:
            await self._award_milestone(user_id, milestone, milestone_points)

        await db.commit()

        return CheckinResult(
            streak_count=streak_count,
            milestone=milestone,
            milestone_points=milestone_points,
        )

    async def _award_milestone(
        self, user_id: str, milestone: str, points: int
    ):
        """发放里程碑积分（独立于每日挑战积分，不受日上限影响）"""
        await db.execute("""
            INSERT INTO core.points_record
                (user_id, points, action_type, description)
            VALUES (:uid, :points, :action, :desc)
        """, {
            "uid": user_id,
            "points": points,
            "action": f"checkin_milestone_{milestone}",
            "desc": f"连续打卡{milestone}天里程碑奖励"
        })
```

# services/core/services/achievement_service.py

class AchievementService:
    """成就徽章兑换服务"""

    async def exchange(
        self, user_id: str, achievement_id: str
    ) -> ExchangeResult:
        # ① 查询徽章信息
        achievement = await knowledge_client.get_achievement(achievement_id)
        if not achievement or achievement.status != "published":
            return ExchangeResult(success=False, reason="not_found")

        # ② 检查是否已拥有
        existing = await db.fetch_one("""
            SELECT 1 FROM core.user_achievement
            WHERE user_id = :uid AND achievement_id = :aid
        """, {"uid": user_id, "aid": achievement_id})
        if existing:
            return ExchangeResult(success=False, reason="already_owned")

        # ③ 检查积分余额
        balance = await points_service.get_balance(user_id)
        if balance < achievement.exchange_points:
            return ExchangeResult(success=False, reason="insufficient_points")

        # ④ 原子扣减 + 写入兑换记录
        async with db.transaction():
            await db.execute("""
                INSERT INTO core.points_record
                    (user_id, points, action_type, description)
                VALUES (:uid, :points, 'exchange_achievement', :desc)
            """, {
                "uid": user_id,
                "points": -achievement.exchange_points,
                "desc": f"兑换成就徽章「{achievement.name}」"
            })
            await db.execute("""
                INSERT INTO core.user_achievement
                    (user_id, achievement_id, source)
                VALUES (:uid, :aid, 'exchange')
            """, {"uid": user_id, "aid": achievement_id})
            await db.commit()

        return ExchangeResult(
            success=True,
            achievement_name=achievement.name,
            points_spent=achievement.exchange_points,
        )

**服务熔断（Circuit Breaker）详细设计**：

> **问题**：Core→Knowledge 是唯一内部调用链路。Knowledge 服务挂掉或响应变慢时，Core 的 httpx 调用会等待超时（默认 30s，AI 生成类 120s），耗尽 Core 的 asyncio 任务池，影响所有用户请求。

**解决方案**：引入 `pybreaker` 断路器库，对 KnowledgeClient 的 HTTP 调用进行熔断保护。

**熔断状态机**：

```
pybreaker 断路器三状态
    │
    ┌──────────┐     连续失败 N 次     ┌──────────┐
    │  CLOSED  │ ───────────────────► │   OPEN   │
    │  (正常)   │                      │  (熔断)   │
    └──────────┘                      └──────────┘
         ▲                               │
         │      成功 1 次                 │ N/2 秒后
         │                               ▼
         │                          ┌──────────┐
         └───────────────────────── │ HALF-OPEN│
              （半开重试成功）        │  (半开)   │
                                   └──────────┘
```

| 状态 | 行为 | 说明 |
|:----:|------|------|
| **CLOSED** | 正常转发请求 | 连续失败计数器递增，成功时重置 |
| **OPEN** | 直接返回熔断异常，不发起 HTTP 调用 | 连续失败达到阈值（默认 5 次）后进入 |
| **HALF-OPEN** | 允许 1 个请求通过探测 | 熔断 N/2 秒后自动进入（默认 2.5 秒）。探测成功 → CLOSED，失败 → OPEN |

**实现代码规范**：

```python
# services/core/clients/knowledge_client.py
import pybreaker
import httpx

# 熔断器配置：连续 5 次失败开启熔断，熔断持续 2.5 秒
# 注意：超时异常不排除在熔断之外——当 Knowledge 响应变慢导致超时时，
# 熔断器及时切断调用，防止 Core 的 httpx 连接池和 asyncio 任务池被慢请求耗尽。
knowledge_breaker = pybreaker.CircuitBreaker(
    fail_max=5,
    reset_timeout=2.5,
)

class KnowledgeClient:
    """带熔断保护的 Knowledge 服务客户端"""

    def __init__(self, base_url: str):
        self.base_url = base_url
        self.client = httpx.AsyncClient(timeout=30.0)

    @knowledge_breaker
    async def _request(self, method: str, path: str, **kwargs) -> dict:
        """内部请求方法 — 由 pybreaker 装饰器自动熔断"""
        url = f"{self.base_url}{path}"
        try:
            resp = await self.client.request(method, url, **kwargs)
            resp.raise_for_status()
            return resp.json()
        except httpx.HTTPStatusError as e:
            raise KnowledgeClientError(e.response.status_code, e.response.text)
        except httpx.TimeoutException:
            # 超时计入熔断计数，防止慢请求耗尽 asyncio 连接池
            raise KnowledgeTimeoutError(path)

    async def get_published_cards(self) -> list[dict]:
        """获取已发布卡片列表"""
        return await self._request("GET", "/api/v1/cards?status=published")

    async def get_domains(self) -> list[dict]:
        """获取知识领域列表"""
        return await self._request("GET", "/api/v1/domains")

    # ... 其他 API 方法类似
```

**断路器与 `/health` 降级策略的关系**：

```
Knowledge 服务故障时间线：
    │
    ├── t=0s    Knowledge 进程崩溃
    ├── t=+1s   Core 调用 Knowledge 超时 → 断路器计数 +1
    ├── t=+3s   Core 再次调用 → 超时 → 计数 +2
    ├── t=+10s  连续 5 次失败 → 断路器 OPEN
    │           从此 Core 不再调用 Knowledge，直接返回降级响应
    ├── t=+15s  断路器 HALF-OPEN → 放行 1 个探测请求
    │           (Knowledge 已重启) → 成功 → 断路器 CLOSED
    └── t=+20s  正常恢复
```

**熔断期间的用户体验**：

| 场景 | 熔断期间的行为 | 用户体验 |
|------|---------------|----------|
| 知识卡片学习 | 返回空列表或本地缓存数据 | 仍可看到已缓存的领域/章节列表 |
| 提交笔记审核 | 返回 "审核服务暂时不可用，请稍后再试" | 不影响笔记本地保存 |
| AI 生成卡片（管理端）| 返回 "AI 服务暂时不可用" | 管理员可稍后重试 |
| 答题/积分/笔记 CRUD（不依赖 Knowledge）| 完全正常 | 不受影响 |

> **为什么选择 pybreaker 而非自研**：
> - pybreaker 是成熟库（500+ GitHub stars），支持 Python 3.12+ async
> - 装饰器模式（`@knowledge_breaker`）对现有代码侵入极小
> - 支持通过 `exclude` 参数按需排除特定异常类型（当前配置中超时异常不排除，确保慢请求也能触发熔断）
> - 个人项目不需要引入 Hystrix 等重量级框架

## 10. 配置管理规范

### 10.1 配置体系分层

| 层级 | 文件 | 职责 | 使用方式 |
|------|------|------|----------|
| **基础层** | `shared/config.py` | 提供与具体服务无关的基础配置工具函数 | 三服务通用 `import` |
| **服务层** | `services/*/config.py` | 定义本服务特有的 Pydantic Settings 类 | 各服务内部使用 |

### 10.2 `shared/config.py` — 基础配置工具函数

```python
# shared/config.py 职责：提供工具函数，不定义具体配置项

from dotenv import load_dotenv
import os

def load_env(env_file: str = ".env") -> None:
    """加载 .env 文件，各服务在启动入口调用"""
    load_dotenv(env_file)

def get_database_url(schema: str = "core") -> str:
    """根据环境变量组装带 Schema 的数据库 URL

    ⚠️ 使用 urllib.parse.quote_plus 对密码编码，避免密码中
       包含 @ / : 等特殊字符破坏 URL 解析。
    """
    from urllib.parse import quote_plus
    user = os.environ["DB_USER"]
    password = os.environ["DB_PASSWORD"]
    host = os.environ.get("DB_HOST", "localhost")
    port = os.environ.get("DB_PORT", "5432")
    db = os.environ["DB_NAME"]
    return (f"postgresql+asyncpg://{quote_plus(user)}:{quote_plus(password)}"
            f"@{host}:{port}/{db}?options=-c%20search_path={schema}")

def get_redis_url() -> str:
    """组装 Redis URL（支持密码验证）

    密码通过 REDIS_PASSWORD 环境变量传入。
    有密码时使用 redis://:password@host:port 格式。
    """
    host = os.environ.get("REDIS_HOST", "localhost")
    port = os.environ.get("REDIS_PORT", "6379")
    password = os.environ.get("REDIS_PASSWORD", "")
    if password:
        return f"redis://:{password}@{host}:{port}"
    return f"redis://{host}:{port}"

def get_env(key: str, default: str | None = None) -> str:
    """获取环境变量，不存在时抛出明确错误"""
    value = os.environ.get(key, default)
    if value is None:
        raise RuntimeError(f"缺失必需的环境变量: {key}")
    return value
```

> **设计原则**：`shared/config.py` **不导入任何第三方库**（除 python-dotenv），仅使用 Python 标准库，确保在任何服务中引入都不会产生依赖冲突。具体配置项类型校验由各服务的 Settings 类完成。

### 10.3 各服务 `config.py` — 服务专用 Settings 类

各服务使用 **Pydantic BaseSettings** 定义本服务的配置类，继承或调用 `shared/config.py` 的工具函数：

```python
# services/auth/config.py 示例
from pydantic_settings import BaseSettings
from shared.config import get_database_url, get_redis_url

class Settings(BaseSettings):
    """Auth 服务专用配置，通过 .env 或环境变量注入"""
    # 数据库
    database_url: str = get_database_url(schema="auth")

    # Redis
    redis_url: str = get_redis_url()

    # JWT
    jwt_secret: str = "dev-secret-change-in-production"
    jwt_algorithm: str = "HS256"
    jwt_access_expire: int = 86400       # 24h
    jwt_refresh_expire: int = 604800     # 7d

    # 管理员预设
    admin_username: str = "admin"
    admin_password_hash: str = ""        # bcrypt hash

    # 微信小程序
    wx_appid: str = ""
    wx_secret: str = ""

    model_config = {"env_file": ".env", "env_file_encoding": "utf-8"}


settings = Settings()
```

### 10.4 三服务配置项清单

| 配置项 | 类型 | 所属服务 | 对应 env | 说明 |
|--------|:----:|:--------:|----------|------|
| `database_url` | str | 三服务 | `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME` | 各服务自动追加对应 Schema |
| `redis_url` | str | 三服务 | `REDIS_HOST`, `REDIS_PORT` | — |
| `jwt_secret` | str | Auth + Core | `JWT_SECRET` | Core 仅用于验签，不签发 |
| `jwt_algorithm` | str | Auth + Core | — | 固定 HS256 |
| `jwt_access_expire` | int | Auth | `JWT_ACCESS_EXPIRE` | — |
| `jwt_refresh_expire` | int | Auth | `JWT_REFRESH_EXPIRE` | — |
| `admin_username` | str | Auth | `ADMIN_USERNAME` | — |
| `admin_password_hash` | str | Auth | `ADMIN_PASSWORD_HASH` | 启动时预设 |
| `wx_appid` | str | Auth | `WX_APPID` | — |
| `wx_secret` | str | Auth | `WX_SECRET` | — |
| `deepseek_api_key` | str | Knowledge | `DEEPSEEK_API_KEY` | — |
| `deepseek_base_url` | str | Knowledge | `DEEPSEEK_BASE_URL` | — |
| `knowledge_service_url` | str | Core | `KNOWLEDGE_SERVICE_URL` | 默认为 `http://knowledge:8002` |
| `upload_dir` | str | Core | `UPLOAD_DIR` | Banner 图片等，默认 `/data/uploads` |
| `ai_mock_mode` | bool | Knowledge | `AI_MOCK_MODE` | 单元测试时设为 `true` |

### 10.5 配置加载顺序

```
① 系统环境变量（最高优先级，适合 Docker Compose 注入）
② .env 文件（开发环境使用，不上传到 Git）
③ Settings 类中的默认值（最低优先级，仅开发调试用）
```

各服务在 `main.py` 启动入口调用：

```python
# services/auth/main.py
from shared.config import load_env
load_env()  # 加载 .env → 环境变量

from config import settings  # Pydantic 从环境变量读取配置
```

> **注意**：`load_env()` 必须在 `from config import settings` 之前调用，确保环境变量已就绪。
