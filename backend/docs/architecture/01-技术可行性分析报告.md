## 2. 模块级可行性分析

### 2.1 AI 内容生成与审核 — 最高风险模块

#### 技术可行性：✅ 可行，需工程化设计

| 风险点 | 描述 | 缓解措施 |
|--------|------|----------|
| **DeepSeek JSON 格式不稳定** | 大模型生成的 JSON 偶尔缺少字段或格式错误 | 统一 AIProvider 响应解析层：先用 `response.choices[0].message.content` 取原始文本，再 `json.loads()` + Pydantic 模型校验，失败时自动重试(最多 2 次) |
| **API 限流与延迟** | DeepSeek 免费/低价 API 存在 QPS 限制，批量生成(10 个主题)可能耗时 > 30s | arq 异步任务队列 + 前端轮询结果；批量生成时串行调用 + 间隔 500ms |
| **笔记审核维度准确度** | 5 维度（违规广告/色情低俗/暴力谩骂/政治敏感/虚假信息）审查不够精准 | Prompt Engineering 精细调优 + 人工复核兜底（中风险进入人工队列） |
| **敏感词匹配性能** | 敏感词库数量增长后，过滤延迟增加 | 敏感词加载到 Redis（Hash 结构），每匹配模式一个独立 key；增量更新而非全量重载 |

#### 备选方案

| 主方案 | 备选方案 | 切换条件 |
|--------|----------|----------|
| DeepSeek API | 通义千问 Qwen（OpenAI 兼容接口，AIProvider 抽象层切换成本低） | DeepSeek 连续不可用或价格大幅上涨 |
| arq 异步任务队列 | Celery + Redis | arq 社区停止维护或功能不满足 |

### 2.2 间隔重复调度算法 — 中等风险模块

#### 技术可行性：✅ 可行

**核心算法**：

```
给定学习时间 T₀，复习节点配置 N = [n₁, n₂, ..., nₖ]
复习时间 Tᵢ = T₀ + nᵢ 天

每日待复习列表 = SELECT card_id FROM learning_records 
                WHERE 今天属于复习节点之一
```

**风险点**：
| 风险 | 缓解措施 |
|------|----------|
| 大量用户同一天复习导致查询压力 | Redis 缓存当日复习列表，T+1 失效 |
| 用户修改复习节点后旧列表未更新 | 只对新学习的卡片生效，已排入的不受影响（PRD 规定如此）|

### 2.3 积分体系 — 中等风险模块

#### 技术可行性：✅ 可行

**关键竞争条件**：

```python
# 场景：用户同时触发多次积分获取（如并发网络请求）
# 核心问题：原子性增减 + 日上限控制

# 方案：Redis Lua 脚本原子操作
redis.eval("""
    local daily_key = KEYS[1]   -- "points:daily:{user_id}:{action_type}"
    local daily_limit = ARGV[1] -- 从配置读取的日上限
    local points = ARGV[2]      -- 本次应得积分
    
    local current = redis.call('GET', daily_key) or 0
    if tonumber(current) >= tonumber(daily_limit) then
        return -1  -- 已达上限
    end
    redis.call('INCRBY', daily_key, points)
    redis.call('EXPIRE', daily_key, 86400)
    return points
""", 1, daily_key, daily_limit, points)
```

**风险点**：
| 风险 | 缓解措施 |
|------|----------|
| 并发请求导致超发 | Redis Lua 脚本保证原子性 |
| 服务重启后 Redis 计数丢失 | 定时（每 5 分钟）将 Redis 计数持久化到 PostgreSQL，重启时恢复 |

### 2.4 敏感词多模式匹配 — 低风险模块

#### 技术可行性：✅ 可行

**匹配引擎架构**：
```
输入文本
    │
    ├── 精确匹配 → Aho-Corasick 自动机（O(n) 时间复杂度）
    ├── 拼音匹配 → pypinyin 库转拼音 + 精确匹配
    ├── 谐音匹配 → 内置映射表（需维护）+ 精确匹配
    └── 正则匹配 → Python re 库逐条匹配
    │
    ▼
返回命中词列表 + 位置
```

**性能预估**：
- 精确匹配（AC 自动机）：1000 个敏感词匹配 5000 字文本 < 5ms
- 拼音匹配：增加拼音转换时间 ~10ms
- 正则匹配：每 100 条正则约 20ms（应限制正则数量 ≤ 100）

### 2.5 数据看板跨 Schema 聚合 — 低风险模块

#### 技术可行性：✅ 可行

使用 PostgreSQL Schema 限定查询：

```sql
-- 跨 Schema JOIN 示例
SELECT 
    u.openid,
    COUNT(lr.card_id) as learn_count,
    d.name as domain_name
FROM auth.user u
JOIN core.learning_record lr ON u.id = lr.user_id
JOIN knowledge.domain d ON lr.domain_id = d.id
GROUP BY u.openid, d.name;
```

> 仅需确保 Core 服务的数据库连接用户具有 `auth` 和 `knowledge` Schema 的只读权限即可。
