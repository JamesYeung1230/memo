# Part A — Git 工作流规范

> 适用于所有 Git 操作，包括开发者和 AI Agent 的自动提交。

## A.1 唯一 Git 仓库

所有 git 操作统一在 `<项目根目录名>/` 根目录下执行，子项目内部不初始化独立的 git 仓库。

## A.2 提交隔离原则

每次提交只包含**一个子项目**的变更，或仅包含根目录文件（`README.md`、`.trae/` 等）的变更。不对其他平级子项目的文件做任何处理。

## A.3 默认提交（Agent 自动行为）

Agent 完成用户指令并修改文件后，**必须默认执行一次本地提交**。无论用户当前打开的是 `<项目根目录名>/` 还是其下任意子项目，本规则均生效。

## A.4 父子目录分离提交

当根目录文件（`README.md`、`.trae/` 下规则文件等）与子项目文件**同时**存在修改时，**必须拆分为两次独立提交**：

| 顺序 | 提交内容 | 示例命令 |
|------|---------|---------|
| 先提交 | 子项目文件 | `git add <子项目目录>/ && git commit -m "..."` |
| 再提交 | 根目录文件 | `git add README.md .trae/ && git commit -m "..."` |

> 分开提交的目的是让每次 commit 的 scope 清晰明确，避免一个 commit 同时包含子项目和根目录两种 scope。

若仅修改了根目录文件（如更新规则），则只需一次 `docs(root):` 提交。
若仅修改了子项目文件，则只需一次对应 scope 的提交。

**提交命令模板：**

```bash
# 仅子项目
cd /d/workspace/<项目根目录名>
git add <子项目目录>/
git commit -m "<type>(<scope>): <描述>"

# 仅根目录
cd /d/workspace/<项目根目录名>
git add README.md .trae/   # 按实际变更文件添加
git commit -m "<type>(root): <描述>"
```

## A.5 提交信息规范

采用 Conventional Commits 格式：

```
<type>(<scope>): <简短描述>

<详细说明（可选）>
```

- `type`: feat / fix / refactor / style / docs / chore / test
- `scope`: root / <子项目1> / <子项目2> / ...（按实际子项目填写）
- 描述使用中文

**示例：**
```
feat(webapp): 新增用户登录页面
fix(backend): 修复接口超时问题
docs(root): 更新项目规则文件
```

## A.6 分支策略

- `develop` — **默认开发分支**，所有 Agent 自动提交和日常开发工作均在 develop 分支上进行
- `master` — **稳定发布分支**，仅从 develop 合并，用于保存经过验证的稳定版本
- Agent 在开始任务前应确认当前在 `develop` 分支，若不在则自动切换

## A.7 禁止事项

- 禁止在单次提交中混入多个子项目的文件变更
- 禁止在一次提交中同时包含根目录文件和子项目文件（必须拆分）
- 禁止提交根目录下 `README.md` 和 `.trae/` 以外的根目录文件（`.gitignore` 除外）
- 禁止在子项目内部执行 `git init` 或 `git add` 操作

# Part B — AI 编程行为规范

> 适用于 AI Agent 在执行所有开发任务时的行为约束。

## B.1 上下文感知

- Agent 在修改任何文件前，必须先使用 SearchCodebase 或相关搜索工具获取项目上下文
- 了解项目中已有的工具函数、组件、库后再进行编码，避免重复造轮子
- 修改代码前，先阅读相邻文件和依赖文件，理解现有代码风格和约定

## B.2 修改验证

- 每次修改完成后，必须运行对应的 lint/typecheck 命令进行验证（如 `npm run lint`、`npm run typecheck`、`ruff` 等）
- 修改涉及的功能应运行相关测试确认不破坏已有逻辑
- 多步骤任务中，每完成一步都应验证后再继续下一步

## B.3 依赖管理

- 禁止引入项目未使用的新依赖（npm包、pip包、gem等），除非用户明确要求
- 使用新依赖前，先检查 `package.json`、`requirements.txt` 或 `Gemfile` 等文件中是否已有替代方案
- 不得使用过时、废弃或不安全的库版本

## B.4 安全红线

- 禁止在代码中硬编码任何密钥、Token、密码或敏感信息
- 禁止生成存在 SQL 注入、XSS、CSRF 等安全漏洞的代码
- 涉及认证、鉴权、支付等敏感功能时，必须使用安全的实现方式

## B.5 文件创建约束

- 禁止生成文档类 `.md` 文件（README、CHANGELOG 等），除非用户明确要求
- 优先修改已有文件，而非创建新文件
- 除非绝对必要，否则不要创建新文件

## B.6 测试覆盖

- 每个功能完成或修复后，必须编写或更新对应的测试用例
- 测试应覆盖正常路径、边界条件和异常场景
- 遵循项目已有的测试框架和规范

## B.7 不确定时确认

- 遇到不确定的技术选型、架构决策或需求分歧时，使用 AskUserQuestion 与用户确认
- 不要在不确定的情况下「猜」一个方案直接执行
- 当任务描述模糊时，主动向用户澄清具体需求

## B.8 任务追踪

- 复杂多步骤任务必须使用 TodoWrite 工具创建任务列表并跟踪进度
- 确保长链任务不丢失上下文，每一步都清晰可追踪

# Part C — Skill 管理规范

> 适用于 AI Agent 在使用或创建 Skill 时的行为约束。
> Skill 是 Trae IDE 的专家能力扩展机制，激活后 AI Agent 会按照 Skill 预定义的角色和流程执行任务。

## C.1 Skill 选用原则

| 条件 | 是否使用 |
|------|---------|
| 任务与 Skill 核心能力高度匹配 | ✅ 使用 |
| 任务简单，不需要专家知识 | ❌ 不使用 |
| 不明确是否该用 | ❌ 不使用，或用 AskUserQuestion 询问用户 |
| 同一对话中已完成 Skill 相关任务 | ❌ 后续不再调用 |

**激活前必须三问：**
1. 这个任务是否需要该 Skill 领域的专业知识？
2. 使用 Skill 带来的收益是否大于上下文 Token 的消耗？
3. 有没有更简单的方式完成？（如直接 Prompt 或参考 Part B 的规则）

## C.2 本项目可用 Skill 及适用场景

> ⚠️ 此表为示例格式，请根据实际安装的 Skill 替换内容。

| Skill | 所属范围 | 核心能力 | 使用场景 | 禁止场景 |
|-------|---------|---------|---------|---------|
| `<skill-name>` | `<全局/子项目>` | `<核心能力描述>` | `<使用场景>` | `<禁止场景>` |

### 默认可用 Skill（Trae IDE 内置）

以下 Skill 通常开箱可用，无需额外安装：

| Skill | 核心能力 | 使用场景 | 禁止场景 |
|-------|---------|---------|---------|
| `skill-creator` | 创建新的自定义 Skill | 用户明确要求创建 Skill 时 | 非创建 Skill 的任何任务 |

## C.3 使用约束

### C.3.1 单次激活
- 一次只激活**一个**最相关的 Skill
- 禁止同时激活多个 Skill，避免规则冲突

### C.3.2 上下文管理
- Skill 激活会消耗上下文窗口（尤其是带数据文件和脚本的 Skill），简单任务不应激活
- Skill 完成相关任务后，后续不相关的任务不再调用该 Skill

### C.3.3 安全红线
- 只使用来源可信的 Skill（官方提供或项目中已有）
- Skill 附带的脚本在执行前应理解其逻辑
- Skill 数据文件如包含敏感信息，必须纳入 `.gitignore` 管理
- 禁止从不可信来源加载 Skill

### C.3.4 不干扰项目规则
- Skill 的执行不得违反本文件中 Part A、Part B 以及各子项目规则文件的约束
- Skill 与项目规则冲突时，以本文件和各子项目规则文件为准

## C.4 Skill 创建规范

当需要创建自定义 Skill 时，必须遵循以下要求：

### C.4.1 创建前提
符合以下条件的任务才值得创建 Skill：
- 该任务每周至少执行 2-3 次
- 任务步骤固定、可脚本化、流程清晰
- 任务涉及大量上下文或领域专业知识
- 一次性任务不值得创建

### C.4.2 创建要求
- **职责单一**：一个 Skill 只做一件事，职责清晰
- **Prompt 精简**：SKILL.md 规则明确，不给 AI 过多歧义空间
- **数据独立**：Skill 依赖的数据文件与规则文件分离存放
- **脚本安全**：附带的脚本必须逻辑透明，无安全风险
- **命名规范**：使用 kebab-case 命名，如 `api-test-helper`

### C.4.3 目录结构规范

```
.trae/skills/<skill-name>/
├── SKILL.md              # Skill 规则定义（必需）
├── data/                 # 数据文件目录（可选）
│   └── *.csv / *.json
└── scripts/              # 脚本文件目录（可选）
    └── *.py / *.js
```

### C.4.4 禁止事项
- 禁止在 Skill 脚本中硬编码任何密钥、Token 或敏感信息
- 禁止 Skill 数据文件包含生产环境的真实数据
- 禁止创建与其他 Skill 职责重叠的 Skill
- 创建后必须经过实际任务验证方可投入使用

## C.5 Skill 维护规范

### C.5.1 定期审查
- 项目规范变更时，同步更新相关 Skill 的规则 Prompt
- 设计系统或知识库更新时，同步更新 Skill 数据文件
- IDE 版本更新时，检查 Skill 附带的脚本兼容性

### C.5.2 版本管理
- Skill 目录下的所有文件必须纳入 Git 版本管理
- Skill 数据文件体积过大时（>1MB），应考虑外部存储方案
- Skill 变更的提交信息必须清晰描述变更内容和影响范围

### C.5.3 清理淘汰
- 不再使用的 Skill 应及时从项目中移除
- 被新 Skill 替代的旧 Skill 应归档或删除
- Skill 长期不维护导致规则过时的，应标记为「已废弃」或移除

## C.6 问题排查

当 AI 行为不符合预期时，按以下路径排查 Skill 相关问题：

```
1. 当前是否激活了 Skill？            → 检查最近是否调用了 Skill 工具
2. Skill 规则是否与用户需求冲突？     → 检查 SKILL.md 内容
3. Skill 数据文件是否过时？           → 检查数据文件时间戳
4. Skill 脚本是否存在 Bug？          → 检查脚本逻辑
5. 是否需要临时禁用 Skill？          → 停止调用 Skill 工具
```

# Part D — 规则维护指南

> 适用于所有规则文件（根目录 + 所有子项目）的创建、更新和维护。
> 后续所有对规则文件的修改，包括 Agent 自动更新和用户手动更新，均须遵守本指南。

## D.1 文件架构总览

### 文件分布

> ⚠️ 根据实际子项目结构调整下表。

| 文件位置 | 职责 | 包含板块 |
|---------|------|---------|
| `.trae/rules/project_rules.md`（根） | 项目全局规则 | Part A（Git）、Part B（AI 通用）、Part C（Skill）、Part D（维护指南）、Part E（MCP 规范）、Part F（Agent 规范）、附录 |
| `<子项目1>/.trae/rules/project_rules.md` | 子项目 1 AI 行为扩展（可选） | Part B 扩展 |
| `<子项目2>/.trae/rules/project_rules.md` | 子项目 2 AI 行为扩展（可选） | Part B 扩展 |
| `...` | 更多子项目 | — |

### 职责分工

| 层级 | 管理内容 | 特点 |
|------|---------|------|
| **根规则** | Git 工作流、AI 通用行为、Agent 选用规范、Skill 管理、MCP 调用、维护指南 | 全局适用，所有子项目共享 |
| **子项目规则** | 领域特定的 AI 行为约束 | 对根规则 Part B 的补充和细化，不重复根规则已有内容 |

### 核心原则

1. **根规则统管全局**：Part A（Git 工作流）、Part C（Skill 管理）、Part E（MCP 规范）和 Part F（Agent 规范）全局适用，子项目不重复定义
2. **子项目按需扩展**：子项目只补充 Part B 的领域特定条款，不重复根规则已有内容
3. **子项目规则独立编号**：各子项目使用独立的 Part B 扩展编号区间，互不影响

## D.2 编号体系

### 板块编号

| 层级 | 格式 | 示例 |
|------|------|------|
| Part | `# Part X — 标题` | `# Part B — AI 编程行为规范` |

### 扩展规则编号

新增规则时的编号接续规则：

| 位置 | 当前末位编号 | 新增编号 |
|------|:----------:|:--------:|
| 根规则 Part A | A.7 | A.8, A.9 … |
| 根规则 Part B | B.8 | B.21, B.22 … |
| 根规则 Part C | C.6 | C.7, C.8 … |
| 根规则 Part D | D.5 | D.6, D.7 … |
| 根规则 Part E | E.6 | E.7, E.8 … |
| 根规则 Part F | F.7 | F.8, F.9 … |
| 根规则 Part G | G.6 | G.7, G.8 … |
| <子项目1> 子项目 | B.14 | B.15, B.16 … (上限 B.20) |
| <子项目2> 子项目 | B.14 | B.15, B.16 … (上限 B.20) |

> 子项目使用 B.9~B.20 区间，与根规则 Part B 的 B.1~B.8 自然衔接，形成一个完整的编号序列。B.9~B.20 为子项目保留区间（共 12 个编号），根规则扩展从 B.21 开始。
>
> **编号冲突防护**：根规则 Part B 未来新增条款时从 B.21 开始编号，与子项目使用的 B.9~B.20 完全隔离。同理，根规则其他 Part 扩展时也应避开子项目可能使用的编号区间。各子项目之间不共享编号空间，互不影响。

3. 用户明确要求创建

## D.4 更新规则文件的规范

### D.4.1 添加新条款

1. 先确定属于哪个 Part（A/B/C/D/E/F/G/附录）

3. 同步更新导读索引表（如有）
4. 涉及跨文件引用时同步更新相关文件

### D.4.2 修改现有条款

1. 修改后同步检查关联文件的交叉引用是否一致
2. 涉及子项目的修改需确认子项目规则文件中的对应条款是否需要同步
3. 如需废弃条款，不直接删除编号，标注「已废弃」并附上原因和日期

**废弃标注格式：**
```

```

### D.4.3 关于文件拆分

如规则文件超过 400 行或内容涵盖多个不相关主题，可考虑拆分。拆分需遵循：
1. 保持根规则的 Part A / Part C 不拆分（全局适用）
2. Part B 可拆分为多个文件（如 `ai-coding-base.md` + `ai-coding-advanced.md`）
3. 拆分后必须在导读索引中注明文件分布

# Part E — MCP 服务调用规范

> 适用于 AI Agent 在调用 MCP（Model Context Protocol）服务时的行为约束。
> MCP 服务让 AI Agent 能通过标准化协议与外部系统交互，执行 Bug 管理、设计操作、自动化测试等实际任务。
> MCP 调用会对外部系统产生真实影响，必须比普通对话更加谨慎。

## E.1 MCP 核心原则

### 操作三不原则

1. **不盲目信任** — MCP 返回的数据可能是过时的，关键操作前先查询确认当前状态
2. **不一次做完** — 复杂操作必须分步执行，每步确认结果后再继续
3. **不忘记验证** — 每次 MCP 调用后必须检查返回结果，确认操作成功

### 调用前必须三问

1. 这个操作是否可逆？（不可逆操作必须格外谨慎）
2. 我掌握的最新状态是否与外部系统一致？（状态漂移检查）
3. 本次调用的返回数据量是否可能打爆上下文窗口？

## E.2 本项目可用 MCP 服务清单

> ⚠️ 此表为示例格式，请根据实际配置的 MCP 服务替换内容。

### MCP 服务总览

| MCP 服务 | 所属范围 | 核心能力 | 涉及子项目 |
|---------|---------|---------|-----------|
| `<MCP 服务名>` | `<全局/子项目>` | `<能力描述>` | `<子项目>` |

按以下格式填写每个 MCP 工具：

```
| 工具 | 用途 | 使用场景 | 注意事项 |
|------|------|---------|---------|
| `<工具名>` | `<功能>` | `<场景>` | `<注意点>` |
```

## E.3 调用流程规范

### E.3.1 标准调用流程

```
┌─────────────────────┐
│  1. 查询当前状态     │  ← 先通过 list/query 获取最新状态
├─────────────────────┤
│  2. 规划操作步骤     │  ← 复杂操作拆分为多个原子操作
├─────────────────────┤
│  3. 执行操作         │  ← 按规划顺序执行
├─────────────────────┤
│  4. 验证返回结果     │  ← 检查返回的 status/error 字段
├─────────────────────┤
│  5. 确认结果一致性   │  ← 再次查询确认外部系统状态已更新
└─────────────────────┘
```

### E.3.2 分步执行原则

对于涉及多个 MCP 调用的复杂任务，必须分步执行：

```
✅ 正确做法：
  第1步：查询当前状态
  第2步：分析返回数据
  第3步：确认后执行操作
  第4步：查询确认状态已更新

❌ 错误做法：
  一次执行操作后不验证
```

### E.3.3 避免上下文溢出

- 查询工具的 depth 参数优先使用低值（1~2），需要更多数据时逐层深入
- 截图类 MCP 仅在需要视觉验证时使用
- 大批量操作拆分为多个小批次执行

## E.4 安全约束

### E.4.1 不可逆操作保护

以下 MCP 操作一旦执行无法恢复，**必须先确认参数再执行**：

> ⚠️ 根据实际 MCP 服务填写不可逆操作列表。

### E.4.2 状态漂移防护

状态漂移指 AI 认知与外部系统实际状态不一致的情况。防护措施：

1. **操作前查询**：任何修改操作前，先调用查询工具确认当前状态
2. **操作后验证**：修改后再次查询，确认变更已生效
3. **跨对话注意**：新对话开始时，不要假设上个对话中 MCP 的状态仍然有效

### E.4.3 数据安全

- MCP 上报的信息不应包含用户个人隐私
- 操作外部系统时，注意不要误删他人创作的内容
- 禁止通过 MCP 操作未经授权的资源（如其他项目的资源）

### E.4.4 频率控制

- 避免在短时间内重复调用同一个 MCP 工具
- 连续调用之间留出合理的间隔，避免服务端限流
- 批量操作优先使用批量接口，而非逐个调用

## E.5 错误处理规范

### E.5.1 错误分类与应对

| 错误类型 | 可能原因 | 应对策略 |
|---------|---------|---------|
| 参数错误 | 工具入参格式不正确 | 检查参数后再试（不使用相同参数重试） |
| 资源不存在 | 引用的 ID 已被删除 | 先查询确认后再操作 |
| 权限不足 | 无对应资源的操作权限 | 告知用户，停止操作 |
| 网络超时 | 服务端响应慢或网络问题 | 等待后重试（最多 2 次） |
| 状态冲突 | 操作的目标状态与当前状态冲突 | 重新查询最新状态后调整方案 |

### E.5.2 失败处理流程

```
MCP 调用失败
    │
    ├── 参数错误 → 修正参数 → 重试
    │
    ├── 资源不存在 → 重新查询 → 调整方案
    │
    ├── 网络超时 → 等待 → 重试（最多 2 次）
    │                      ↓
    │                   仍失败 → 告知用户
    │
    └── 其他错误 → 记录错误信息 → 告知用户
```

### E.5.3 批量操作回滚感知

如果 MCP 服务支持事务性回滚（如 Pencil MCP 的 `batch_design`）：
- 如果某个操作失败，整个批次的**所有操作**都会回滚
- 不要在同一个批量调用中放入过多操作（一般不超过 10 个）
- 将大型修改拆分为多个批次，降低单次回滚的影响范围

## E.6 问题排查

当 MCP 调用不符合预期时，按以下路径排查：

```
1. MCP 服务是否正常运行？           → 检查服务进程是否启动
2. 工具参数是否正确？               → 检查入参格式和必填字段
3. 当前操作是否在资源权限范围内？    → 确认是否有操作权限
4. 返回结果中是否有错误信息？        → 解析返回的 error 字段
5. 外部系统状态是否已变更？          → 重新查询确认
6. 是否需要告知用户手动介入？        → 无法自动恢复时及时告知
```

## F.3 Agent 选用原则

### 选用判断流程

```
任务来临时
    │
    ├── 简单任务（单步操作）→ 直接执行，不调子 Agent
    │   例：修改一个函数、修复一个 lint 错误
    │
    ├── 中等任务（2~5 步）→ 主 Agent 自行执行
    │   例：实现一个 API 接口、创建一个页面组件
    │
    └── 复杂任务（多步骤/跨领域）→ 考虑调子 Agent
        例：实现完整用户模块（需前端+后端+测试）
```

### 选用规则

| 条件 | 做法 |
|------|------|
| 任务明确属于某个 Agent 的专业领域 | 调用对应子 Agent |
| 任务涉及多个专业领域 | 主 Agent 拆分后分别委派 |
| 简单搜索任务 | 直接使用 Grep/SearchCodebase，**不调子 Agent** |
| 不明确用哪个 Agent | 先使用 `search` 做调研，或 AskUserQuestion 询问用户 |

### 禁止事项

- 禁止使用 `frontend-architect` 做后端任务
- 禁止使用 `backend-architect` 修改前端代码
- 禁止因懒惰将简单任务委派为子 Agent（增加 Token 消耗和延迟）
- 子 Agent 返回的结果必须验证后再使用，禁止直接采纳

## F.4 执行规范

### F.4.1 任务规划阶段

每项任务执行前必须完成：

```
□ 理解任务目标与边界
   ├── 确认任务要「做什么」和「不做什么」
   ├── 需求模糊时使用 AskUserQuestion 澄清
   └── 确认当前分支为 develop

□ 加载锚点文档
   ├── 根规则 project_rules.md（全部 Part）
   ├── 对应子项目的 project.md 和 .trae/rules/project_rules.md
   └── 涉及的设计文档/PRD

□ 输出执行计划（复杂任务）
   ├── 拆分为可验证的子步骤
   ├── 每步标注预期结果
   └── 明确哪些步骤可并行
```

### F.4.2 任务执行阶段

**核心：不得擅自扩大任务范围。**

- 发现「顺手的问题」时：记录到 TodoWrite 的备注中，**不立即处理**
- 如果「顺手的问题」阻塞了当前任务：先 AskUserQuestion 征求用户同意
- 每完成一个子步骤，验证结果后再继续下一步

**修改出错的回滚策略：**

当修改导致错误时，按以下顺序尝试恢复：

```
1. git diff -- <file>     → 查看具体修改内容
2. git restore <file>     → 撤销未提交的文件修改
3. git stash              → 暂存当前所有修改，回到干净状态
4. git restore --staged <file> → 撤销已暂存的修改
5. git checkout -- <file> → 回退到上一个提交版本（备用方案）
```

> 如果已提交但需要撤销，使用 `git revert HEAD`（不修改历史）。禁止使用 `git reset --hard` 丢弃提交历史。

**发现偏离时的纠正流程：**

```
当前步骤完成
    │
    ├── 步骤结果与计划一致 → 继续下一步
    │
    └── 步骤结果偏离计划
         ├── 偏离在可接受范围内 → 记录偏离，继续
         │
         └── 偏离超出可接受范围
              ├── 能自行回退 → 回退到上一个已验证状态
              └── 不能自行回退 → 告知用户，协商修复方案
```

### F.4.3 任务完成阶段

```
□ 全面审查
   ├── 检查 diff，确认修改范围 = 任务范围
   ├── 确认没有「顺手」的额外修改
   └── 确认没有创建不必要的文件（参见 §B.5）

□ 全面验证
   ├── 运行 lint/typecheck 验证
   ├── 运行相关测试
   └── 验证通过后标记 todo 完成

□ 提交
   ├── 按 Part A Git 规范执行提交
   └── 提交信息准确描述变更内容
```

## F.5 子 Agent 调用规范

### F.5.1 调用原则

```
✅ 应该调子 Agent 的场景：
   - 任务需要该 Agent 的领域专业知识
   - 多个子任务可并行执行时
   - 需要 Agent 调用特定工具/MCP 时

❌ 不应该调子 Agent 的场景：
   - 简单搜索（直接用 Grep/SearchCodebase）
   - 只需一步完成的修改
   - 子 Agent 没有该任务所需的专业知识
```

### F.5.2 委派规范

调用子 Agent 时，Task 描述必须包含：

| 要素 | 说明 | 示例 |
|------|------|------|
| **任务目标** | 清晰的单一任务描述 | 「查询项目中的所有 API 路由」 |
| **上下文锚点** | 子 Agent 需要加载的文件 | 「请先加载 project.md」 |
| **输出要求** | 期望返回什么信息 | 「返回路由列表及对应的文件路径」 |
| **边界约束** | 什么不能做 | 「只做查询，不做代码修改」 |

### F.5.3 结果验证

子 Agent 返回结果后，主 Agent 必须：

1. **检查结果完整性** — 子 Agent 是否返回了所有需要的信息
2. **检查结果准确性** — 结果是否与已知信息矛盾
3. **检查结果安全性** — 结果中是否包含不应修改的建议
4. **确认后再使用** — 验证通过后才将结果用于后续步骤

## F.6 常见风险与应对

### F.6.1 任务漂移

**现象**：Agent 在执行中偏离原始任务，做了「顺手」的事。

**应对措施**：
1. 复杂任务必须先输出计划，计划中明确任务边界
2. 每步完成后检查是否仍在任务范围内
3. 发现偏离时，先记录待办，不立即处理
4. 偏离严重时回退步骤，重新对齐任务目标

### F.6.2 过度修改

**现象**：Agent 做了比需求更多的实现（过度工程）。

**应对措施**：
1. **最小实现原则**：先做最简实现，用户要求扩展时再补充
2. 文件创建必须受 §B.5 约束
3. 新增依赖必须受 §B.3 约束
4. 完成后审查 diff，移除不必要的变更

### F.6.3 修复循环

**现象**：Agent 在修复-验证中陷入死循环，每次修复引入新问题。

**应对措施**：
1. 设置重试上限（同一问题最多修复 3 次）
2. 第 3 次仍失败时，停止自动修复，告知用户
3. 每次修复前先确认是否回归了之前已修复的问题
4. 如果修复循环持续超过 5 步，应回退到上一个稳定状态重新分析

### F.6.4 幻觉延续

**现象**：Agent 在前一步生成了错误代码，后续步骤基于错误继续构建。

**应对措施**：
1. 每步完成后必须运行 lint/typecheck 验证
2. 修复错误时要确认是「修复了根因」还是「打补丁掩盖了问题」
3. 对修复方案进行回归检查
4. 验证通过后再进行下一步

### F.6.5 子 Agent 上下文丢失

**现象**：子 Agent 因没有完整的项目上下文，生成了不符合项目规范的代码。

**应对措施**：
1. Task 描述中必须包含足够的上下文锚点
2. 要求子 Agent 在修改前先阅读相关文件
3. 子 Agent 返回结果后必须验证后再使用

### F.6.6 修改无法回退

**现象**：Agent 修改文件后发现错误，但不清楚如何撤销修改，导致错误代码被提交。

**应对措施**：
1. 未提交的修改使用 `git restore <file>` 撤销（参见 F.4.2 回滚策略）
2. 已暂存的修改使用 `git restore --staged <file>` 取消暂存
3. 已提交的修改使用 `git revert HEAD` 生成反向提交
4. **禁止**使用 `git reset --hard` 丢弃提交历史
5. 如果多个文件混乱，先使用 `git stash` 暂存所有修改，从干净状态重新分析
6. 不确定回滚操作影响时，先 AskUserQuestion 询问用户

## F.7 问题排查

当 Agent 行为不符合预期时，按以下路径排查：

```
1. 任务规划是否清晰？               → 检查任务目标和边界是否明确
2. 上下文是否完整？                 → 检查锚点文档是否已加载
3. 选择的 Agent 是否正确？          → 对照 F.2 Agent 选择矩阵检查
4. 是否发生了任务漂移？             → 检查当前步骤是否偏离原始计划
5. 是否陷入了修复循环？             → 检查是否超过 3 次重试仍未成功
6. 子 Agent 返回的结果是否验证？     → 检查是否直接采纳了未验证的结果
7. 是否需要人工介入？               → 无法自行恢复时告知用户
```

# Part G — Token 开销优化规范

> 适用于 AI Agent 在执行所有开发任务时，在不影响结果质量和执行准确性的前提下，合理控制 Token 消耗。
> Token 是有限的上下文资源，**省 Token 不是偷工减料，而是把每一分 Token 都花在刀刃上**。
> 核心原则：「先问要不要，再问要多少。」

---

## G.1 核心原则

### G.1.1 准确性优先

**省 Token 不能牺牲准确性。** 当以下情况冲突时，优先保证结果质量：

- 需要读完整函数体时才完整读，不为了省 Token 只读签名就下结论
- 需要查看完整错误栈时才完整查看，不为了省 Token 只看最后一行
- 不确定某段代码的作用时，宁可靠前读完整代码，也不猜测

### G.1.2 够用就行

```
每个操作前自问：
  1. 我真正需要的数据是什么？（而非「所有数据」）
  2. 哪个工具能以最少的 Token 给我这些数据？
  3. 当前调用获取的数据量是否匹配任务实际所需？
```

### G.1.3 按需分层获取

```
第一层（最省 Token）：SearchCodebase / Grep       → 定位信息位置
第二层（中等 Token）：Read 指定行段 / 查询工具低深度 → 获取局部信息
第三层（较高 Token）：Read 整个文件 / 查询工具高深度  → 获取完整信息
```

优先使用前两层，只有必要时才走上第三层。

---

## G.2 工具调用瘦身

### G.2.1 文件读取精度控制

| 做法 | Token 消耗 | 影响准确性？ |
|------|:---------:|:----------:|
| 先搜索定位函数，再 `Read` 该函数范围行 | 低 | 否 |
| 先 `Grep` 找出引用关系，再读关键行段 | 低 | 否 |
| 每次 `Read` 大文件都从第 1 行读到尾 | 高 | 不一定 |
| 用 `Read` 预览大文件目录结构（应改用 `LS` 或 `Glob`） | 中 | 是（浪费） |

> **关键规则：** 500 行以上的文件，除非需要理解全局结构，否则优先读局部行段。

### G.2.2 命令输出裁剪

涉及命令执行的工具，使用参数控制返回数据量：

```
✅ RunCommand → 不指定 blocking 时用 filter/output_character_count 控制
✅ CheckCommandStatus → 用 output_character_count 限制字符量
✅ CheckCommandStatus → 用 filter 正则提取关键行
❌ 无关紧要的命令不限制输出 → 可能浪费数千 Token
```

**例外：** 编译错误、测试失败、lint 诊断等需要完整输出的场景，不裁剪。

### G.2.3 查询工具深度控制

如果项目中配置了支持深度参数的查询 MCP 工具：

| 做法 | Token 收益 |
|------|:---------:|
| depth 参数从 1 起，不够再逐层加深 | 高 — 避免指数级膨胀 |
| 合并不必要的多次查询为单次 | 中 |
| 文本布局检查优先于截图检查 | 高 — 截图是 base64，Token 极高 |
| 批量操作拆分 ≤10 个为一批 | 中 — 每批失败回滚不会浪费大量 Token |

### G.2.4 搜索协作规则

| 做法 | Token 消耗 | 说明 |
|------|:---------:|------|
| 简单搜索直接用 `Grep`/`SearchCodebase`（单文件、已知关键词） | 低 | 无需启动子 Agent |
| 复杂跨模块搜索才用 Task 调子 Agent | 中 | 子 Agent 启动有固定开销 |
| 用 `Task` 但描述不够精确，导致子 Agent 反复搜索 | 高 | 一次把需求说清楚 |

---

## G.3 响应数据量管理

### G.3.1 轻量工具优先

| 目标 | 轻量工具（省 Token） | 重量工具（高消耗） |
|------|:-----------------:|:-----------------:|
| 检查布局结构 | `snapshot_layout`（如可用） | 截图工具 |
| 查看文件是否存在 | `Glob` / `LS` | `Read` 全部内容 |
| 查找特定模式 | `Grep`（匹配行） | `Read` 整个文件再找 |
| 确认命令结果 | `CheckCommandStatus`（filter） | 重新执行命令 |
| 理解高层结构 | `SearchCodebase` | 依次 `Read` 每个文件 |

### G.3.2 错误场景的谨慎处理

```
问题发现
    │
    ├── 常见/已知错误 → 直接修复，不反复查看完整输出
    │
    ├── 复杂/未知错误 → 查看完整错误栈 + 相关文件代码
    │                    ↓
    │                   修复后不立即删掉错误上下文
    │                   （后续编译/测试还需要验证）
    │
    └── 修复循环（>3 次）
         └── 停止，告知用户
         └── 不继续无意义重试浪费 Token
```

---

## G.4 上下文生命周期管理

### G.4.1 对话边界控制

| 场景 | 推荐做法 | 理由 |
|------|---------|------|
| 单一任务（如实现一个接口） | 同一对话完成 | 上下文可复用 |
| 多个独立任务（如修 Bug A → 修 Bug B） | 建议用户开新对话 | 历史上下文累积会膨胀 |
| 长链任务（>10 步） | 中间询问是否另开对话继续 | 前期上下文对后期决策价值递减 |

### G.4.2 重复引用控制

- 规则文件在当前对话首次加载后，后续步骤不重复引用整段规则
- 同一对话内搜索过的结果，下次需要同类信息时优先复用
- 同一工具调用的参数复用时，优先从历史记录中提取

### G.4.3 避免无意义确认

| 做法 | Token 消耗 | 说明 |
|------|:---------:|------|
| 每步完成后都问「是否继续？」 | 中 — 双向浪费 | 复杂任务才需要分步确认 |
| 修改前后都查 `git diff` | 高 — 文件内容重复传输 | 仅在提交前或出错时查看 |
| 每次调用都查一遍「当前分支」 | 低 | 但累积可避免，开头确认一次即可 |

**建议：** 仅以下情况需要暂停确认：
1. 不可逆操作前
2. 结果与预期明显不符合时
3. 用户明确要求分步执行时

---

## G.5 全局 Token 节约清单

| # | 检查项 | 适用场景 |
|:-:|-------|---------|
| G.5.1 | 读文件前先想：「我需要看多少行？」 | 所有文件操作 |
| G.5.2 | 搜代码时优先用 `Grep` 而非 `SearchCodebase` | 已知关键词的搜索 |
| G.5.3 | 查询工具从低深度参数开始 | 外部工具查询 |
| G.5.4 | 优先文本布局检查而非截图 | 布局检查 |
| G.5.5 | 命令输出用 `filter`/`output_character_count` 裁剪 | 命令执行 |
| G.5.6 | 复杂搜索先写精确的 Task 描述再调子 Agent | 子 Agent 委派 |
| G.5.7 | 错误排查先看常见原因，不一次看完所有输出 | 问题诊断 |
| G.5.8 | 一个任务完成后建议用户开新对话 | 上下文管理 |
| G.5.9 | 同一对话内不重复加载已读过的规则/文件 | 代码阅读 |
| G.5.10 | 不产生「顺手」的不必要修改 | 全部开发任务 |

---

## G.6 问题排查

当 Token 消耗异常偏高时，按以下路径排查：

```
1. 是否激活了不必要的 Skill？           → 参见 §C.1 选用原则
2. 是否委派了不必要的子 Agent？          → 参见 §F.3 选用判断流程
3. Read 操作是否读了完整的文件？          → 改为读局部行段
4. 查询工具深度是否过高？                → 降低 depth 参数
5. 命令输出是否未裁剪？                  → 加上 filter/output_character_count
6. 同一文件是否被重复读取过？            → 复用已有结果
7. 当前对话累积了太多不相关的历史？       → 建议用户开新对话
```

# 附录 — .gitignore 说明

`.gitignore` 文件决定了哪些文件和目录不被 Git 追踪。建议采用白名单模式（先全部忽略再逐项放行）或黑名单模式（默认追踪特定类型文件），根据项目需求选择。

**白名单模式示例：**
```
/*                    # 先忽略根目录下所有内容
!/<子项目1>/          # 放行子项目 1
!/<子项目2>/          # 放行子项目 2
!/README.md           # 放行根目录 README
```
