# Memo 项目规范

> 本文档是项目的核心规则锚点，所有开发工作（包括人和 AI）均须遵守。
> 文档采用板块化结构，AI Agent 和开发者在执行对应操作时查阅相关板块即可。

---

## 适用范围

以下规则在 Trae IDE 打开 `memo/` 或其下任意子项目（`backend/`、`miniapp/`、`test/`、`webapp/`）时均生效。

### 仓库结构

```
memo/                     # Git 仓库根目录（唯一仓库）
├── .gitignore            # 白名单模式，控制追踪范围
├── README.md             # 全局说明文档
├── .trae/rules/          # 规则文件目录（本文件所在目录）
├── backend/              # 后端子项目
├── miniapp/              # 小程序子项目
├── test/                 # 测试子项目
└── webapp/               # Web 应用子项目
```

### 板块导读

| 板块 | 内容 | 适用对象 | 适用时机 |
|------|------|---------|---------|
| **Part A** — Git 工作流规范 | 仓库结构、分支策略、提交规范、禁止事项 | 开发者 + AI Agent | 提交代码时 |
| **Part B** — AI 编程行为规范 | 上下文感知、修改验证、依赖管理、安全红线、教学导向等 | AI Agent | 执行开发任务时 |
| **Part C** — Skill 管理规范 | Skill 选用、创建、维护、问题排查 | AI Agent | 使用或创建 Skill 时 |
| **Part D** — 规则维护指南 | 文件架构、编号体系、创建/更新规范、跨文件引用 | AI Agent + 开发者 | 修改规则文件时 |
| **Part E** — MCP 服务调用规范 | MCP 调用流程、项目 MCP 清单、安全约束、排查指南 | AI Agent | 调用 MCP 服务时 |
| **Part F** — Agent 选用与执行规范 | Agent 选用原则、任务执行规范、子 Agent 调用、风险应对 | AI Agent | 执行开发任务时 |

# Part A — Git 工作流规范

> 适用于所有 Git 操作，包括开发者和 AI Agent 的自动提交。

## A.1 唯一 Git 仓库

所有 git 操作统一在 `memo/` 根目录下执行，子项目内部不初始化独立的 git 仓库。

## A.2 提交隔离原则

每次提交只包含**一个子项目**的变更，或仅包含根目录文件（`README.md`、`.trae/` 等）的变更。不对其他平级子项目的文件做任何处理。

## A.3 默认提交（Agent 自动行为）

Agent 完成用户指令并修改文件后，**必须默认执行一次本地提交**。无论用户当前打开的是 `memo/` 还是其下任意子项目，本规则均生效。

## A.4 父子目录分离提交

当 memo 根目录文件（`README.md`、`.trae/` 下规则文件等）与子项目文件**同时**存在修改时，**必须拆分为两次独立提交**：

| 顺序 | 提交内容 | 示例命令 |
|------|---------|---------|
| 先提交 | 子项目文件 | `git add <子项目目录>/ && git commit -m "..."` |
| 再提交 | 根目录文件 | `git add README.md .trae/ && git commit -m "..."` |

> 分开提交的目的是让每次 commit 的 scope 清晰明确，避免一个 commit 同时包含 `webapp` 和 `root` 两种 scope。

若仅修改了根目录文件（如更新规则），则只需一次 `docs(root):` 提交。
若仅修改了子项目文件，则只需一次对应 scope 的提交。

**提交命令模板：**

```bash
# 仅子项目
cd /d/workspace/memo
git add <子项目目录>/
git commit -m "<type>(<scope>): <描述>"

# 仅根目录
cd /d/workspace/memo
git add README.md .trae/   # 按实际变更文件添加
git commit -m "<type>(root): <描述>"
```

## A.5 提交信息规范

采用 Conventional Commits 格式：

```
<type>(<scope>): <简短描述>

<详细说明（可选）>
```

- `type`: feat / fix / refactor / style / docs / chore / test
- `scope`: webapp / backend / miniapp / test / root
- 描述使用中文

**示例：**
```
feat(webapp): 新增用户登录页面
fix(backend): 修复接口超时问题
docs(root): 更新项目规则文件
```

## A.6 分支策略

- `develop` — **默认开发分支**，所有 Agent 自动提交和日常开发工作均在 develop 分支上进行
- `master` — **稳定发布分支**，仅从 develop 合并，用于保存经过验证的稳定版本
- Agent 在开始任务前应确认当前在 `develop` 分支，若不在则自动切换

## A.7 禁止事项

- 禁止在单次提交中混入多个子项目的文件变更
- 禁止在一次提交中同时包含根目录文件和子项目文件（必须拆分）
- 禁止提交 `memo/README.md` 和 `.trae/` 以外的根目录文件（`.gitignore` 除外）
- 禁止在子项目内部执行 `git init` 或 `git add` 操作

# Part B — AI 编程行为规范

> 适用于 AI Agent 在执行所有开发任务时的行为约束。

## B.1 上下文感知

- Agent 在修改任何文件前，必须先使用 SearchCodebase 或相关搜索工具获取项目上下文
- 了解项目中已有的工具函数、组件、库后再进行编码，避免重复造轮子
- 修改代码前，先阅读相邻文件和依赖文件，理解现有代码风格和约定

## B.2 修改验证

- 每次修改完成后，必须运行对应的 lint/typecheck 命令进行验证（如 `npm run lint`、`npm run typecheck`、`ruff` 等）
- 修改涉及的功能应运行相关测试确认不破坏已有逻辑
- 多步骤任务中，每完成一步都应验证后再继续下一步

## B.3 依赖管理

- 禁止引入项目未使用的新依赖（npm包、pip包、gem等），除非用户明确要求
- 使用新依赖前，先检查 `package.json`、`requirements.txt` 或 `Gemfile` 等文件中是否已有替代方案
- 不得使用过时、废弃或不安全的库版本

## B.4 安全红线

- 禁止在代码中硬编码任何密钥、Token、密码或敏感信息
- 禁止生成存在 SQL 注入、XSS、CSRF 等安全漏洞的代码
- 涉及认证、鉴权、支付等敏感功能时，必须使用安全的实现方式

## B.5 文件创建约束

- 禁止生成文档类 `.md` 文件（README、CHANGELOG 等），除非用户明确要求
- 优先修改已有文件，而非创建新文件
- 除非绝对必要，否则不要创建新文件

## B.6 测试覆盖

- 每个功能完成或修复后，必须编写或更新对应的测试用例
- 测试应覆盖正常路径、边界条件和异常场景
- 遵循项目已有的测试框架和规范

## B.7 不确定时确认

- 遇到不确定的技术选型、架构决策或需求分歧时，使用 AskUserQuestion 与用户确认
- 不要在不确定的情况下「猜」一个方案直接执行
- 当任务描述模糊时，主动向用户澄清具体需求

## B.8 任务追踪

- 复杂多步骤任务必须使用 TodoWrite 工具创建任务列表并跟踪进度
- 确保长链任务不丢失上下文，每一步都清晰可追踪

## B.21 教学导向开发

- AI 在生成代码时必须同时解释"为什么这么做"，不只是"做了什么"
- 每个新引入的概念（装饰器、依赖注入、异步编程等）首次出现时必须附带简短说明
- 遇到可简可繁的方案时，优先选择更易理解的实现，并指出优化的方向和后续可深入学习的关键词
- 在每次任务完成时，总结本次任务涉及的知识点清单
- AI 遇到需要决策的问题时，先给出思路和选项让用户选择，确认后再实现

## B.22 渐进式复杂度

- 每个功能先做最简可用版本，不引入非必要的抽象层
- 遵循"三步走"：① 能跑通 → ② 能看懂 → ③ 能优化
- 禁止在实现基础功能时同时引入高级特性（如缓存、消息队列、读写分离等）
- 重构或抽象必须建立在"当前代码已能正确运行"的基础上
- 每次复杂度升级前，先 AskUserQuestion 确认用户是否准备好学习该概念，而非直接替用户做决定
- 示例：
  - ✅ 先写同步路由函数，再逐步引入 async def
  - ✅ 先写单文件，再教项目模块拆分
  - ❌ 第一次就生成完整 MVC 架构 + 依赖注入 + 多层抽象

## B.23 最小干预原则

- 用户遇到错误时，AI 按三层递进方式引导，而非直接给出答案：
  - 第一层：指出错误类型和位置，让用户自己尝试分析
  - 第二层：给出排查思路（如"你可以先检查这个变量是否为 None"）
  - 第三层：如果用户反复尝试仍无法解决（同一问题 3 次以上），再给出具体方案
- 用户主动提问时，AI 先反问确认他的当前理解，再针对性解释
- 对于"能不能这样写"类问题，优先回答"你可以试试看并观察结果"，而非直接否决
- 修改代码前，先等用户给出修改思路，AI 负责验证正确性而非直接代劳
- 需区分"试错学习"与"卡住"：如果用户明显卡在同一个问题上超过 10 分钟，或反复尝试相同错误方向 3 次以上，AI 应主动介入给出明确指引

# Part C — Skill 管理规范

> 适用于 AI Agent 在使用或创建 Skill 时的行为约束。
> Skill 是 Trae IDE 的专家能力扩展机制，激活后 AI Agent 会按照 Skill 预定义的角色和流程执行任务。

## C.1 Skill 选用原则

| 条件 | 是否使用 |
|------|---------|
| 任务与 Skill 核心能力高度匹配 | ✅ 使用 |
| 任务简单，不需要专家知识 | ❌ 不使用 |
| 不明确是否该用 | ❌ 不使用，或用 AskUserQuestion 询问用户 |
| 同一对话中已完成 Skill 相关任务 | ❌ 后续不再调用 |

**激活前必须三问：**
1. 这个任务是否需要该 Skill 领域的专业知识？
2. 使用 Skill 带来的收益是否大于上下文 Token 的消耗？
3. 有没有更简单的方式完成？（如直接 Prompt 或参考 Part B 的规则）

## C.2 本项目可用 Skill 及适用场景

| Skill | 所属子项目 | 核心能力 | 使用场景 | 禁止场景 |
|-------|-----------|---------|---------|---------|
| `bugpack-usage` | 全局 | BugPack 部署、配置、Bug 管理 | Bug 创建/查看/状态更新、BugPack MCP 配置 | 普通开发任务、代码修改 |
| `skill-creator` | 全局 | 创建新的自定义 Skill | 用户明确要求创建 Skill 时 | 非创建 Skill 的任何任务 |
| `ui-ux-pro-max` | miniapp | UI/UX 设计智能化 | 页面/组件 UI 设计、颜色/字体/图标推荐、设计系统参考 | 纯逻辑开发、后端/测试任务 |

## C.3 使用约束

### C.3.1 单次激活
- 一次只激活**一个**最相关的 Skill
- 禁止同时激活多个 Skill，避免规则冲突

### C.3.2 上下文管理
- Skill 激活会消耗上下文窗口（尤其是带数据文件和脚本的 Skill），简单任务不应激活
- Skill 完成相关任务后，后续不相关的任务不再调用该 Skill

### C.3.3 安全红线
- 只使用来源可信的 Skill（官方提供或项目中已有）
- Skill 附带的脚本在执行前应理解其逻辑
- Skill 数据文件如包含敏感信息，必须纳入 `.gitignore` 管理
- 禁止从不可信来源加载 Skill

### C.3.4 不干扰项目规则
- Skill 的执行不得违反本文件中 Part A、Part B 以及各子项目规则文件的约束
- Skill 与项目规则冲突时，以本文件和各子项目规则文件为准

## C.4 Skill 创建规范

当需要创建自定义 Skill 时，必须遵循以下要求：

### C.4.1 创建前提
符合以下条件的任务才值得创建 Skill：
- 该任务每周至少执行 2-3 次
- 任务步骤固定、可脚本化、流程清晰
- 任务涉及大量上下文或领域专业知识
- 一次性任务不值得创建

### C.4.2 创建要求
- **职责单一**：一个 Skill 只做一件事，职责清晰
- **Prompt 精简**：SKILL.md 规则明确，不给 AI 过多歧义空间
- **数据独立**：Skill 依赖的数据文件与规则文件分离存放
- **脚本安全**：附带的脚本必须逻辑透明，无安全风险
- **命名规范**：使用 kebab-case 命名，如 `api-test-helper`

### C.4.3 目录结构规范

```
.trae/skills/<skill-name>/
├── SKILL.md              # Skill 规则定义（必需）
├── data/                 # 数据文件目录（可选）
│   └── *.csv / *.json
└── scripts/              # 脚本文件目录（可选）
    └── *.py / *.js
```

### C.4.4 禁止事项
- 禁止在 Skill 脚本中硬编码任何密钥、Token 或敏感信息
- 禁止 Skill 数据文件包含生产环境的真实数据
- 禁止创建与其他 Skill 职责重叠的 Skill
- 创建后必须经过实际任务验证方可投入使用

## C.5 Skill 维护规范

### C.5.1 定期审查
- 项目规范变更时，同步更新相关 Skill 的规则 Prompt
- 设计系统或知识库更新时，同步更新 Skill 数据文件
- IDE 版本更新时，检查 Skill 附带的脚本兼容性

### C.5.2 版本管理
- Skill 目录下的所有文件必须纳入 Git 版本管理
- Skill 数据文件体积过大时（>1MB），应考虑外部存储方案
- Skill 变更的提交信息必须清晰描述变更内容和影响范围

### C.5.3 清理淘汰
- 不再使用的 Skill 应及时从项目中移除
- 被新 Skill 替代的旧 Skill 应归档或删除
- Skill 长期不维护导致规则过时的，应标记为「已废弃」或移除

## C.6 问题排查

当 AI 行为不符合预期时，按以下路径排查 Skill 相关问题：

```
1. 当前是否激活了 Skill？            → 检查最近是否调用了 Skill 工具
2. Skill 规则是否与用户需求冲突？     → 检查 SKILL.md 内容
3. Skill 数据文件是否过时？           → 检查数据文件时间戳
4. Skill 脚本是否存在 Bug？          → 检查脚本逻辑
5. 是否需要临时禁用 Skill？          → 停止调用 Skill 工具
```

# Part D — 规则维护指南

> 适用于所有规则文件（根目录 + 所有子项目）的创建、更新和维护。
> 后续所有对规则文件的修改，包括 Agent 自动更新和用户手动更新，均须遵守本指南。

## D.1 文件架构总览

### 文件分布

| 文件位置 | 职责 | 包含板块 |
|---------|------|---------|
| `~/.trae/rules/project_rules.md`（**全局**） | **用户全局规则**（自动对所有项目生效） | Part B（AI 通用）、Part C（Skill 通用原则）、Part E（MCP 通用原则）、Part F（Agent 规范） |
| `.trae/rules/project_rules.md`（根） | 项目全局规则（本文件） | Part A（Git）、Part B（AI 通用）、Part C（Skill）、Part D（维护指南）、Part E（MCP 规范）、Part F（Agent 规范）、附录 |
| `.trae/rules/token-efficiency.md` | Token 开销优化规范（Part G 独立拆分） | Part G（Token 优化） |
| `.trae/rules/template.project_rules.md` | **通用规则模板** | 剥离项目特定内容的通用版，新项目可直接拷贝使用 |
| `backend/.trae/rules/project_rules.md` | 后端子项目 AI 行为扩展 | Part B 扩展 |
| `miniapp/.trae/rules/project_rules.md` | 小程序子项目 AI 行为扩展 | Part B 扩展 |
| `test/.trae/rules/project_rules.md` | 测试子项目 AI 行为扩展 | Part B 扩展 |
| `webapp/.trae/rules/project_rules.md` | Web 管理端完整规范 | Part A（项目 Git）+ Part B（AI 扩展）+ 项目特定规范（§一~§十六） |

### 职责分工

| 层级 | 管理内容 | 特点 |
|------|---------|------|
| **根规则** | Git 工作流、AI 通用行为、Agent 选用规范、Skill 管理、MCP 调用、维护指南、Token 优化 | 全局适用，所有子项目共享 |
| **子项目规则** | 领域特定的 AI 行为约束 | 对根规则 Part B 的补充和细化，不重复根规则已有内容 |

### 核心原则

1. **根规则统管全局**：Part A（Git 工作流）、Part C（Skill 管理）、Part E（MCP 规范）和 Part F（Agent 规范）全局适用，子项目不重复定义
2. **子项目按需扩展**：子项目只补充 Part B 的领域特定条款（如 backend 的数据安全、miniapp 的 UI 还原）
3. **webapp 特殊处理**：因已有 §一~§十六的完整项目规范，AI 行为扩展作为 §十七存在，不强制改为 Part 编号

# Part E — MCP 服务调用规范

> 适用于 AI Agent 在调用 MCP（Model Context Protocol）服务时的行为约束。
> MCP 服务让 AI Agent 能通过标准化协议与外部系统交互，执行 Bug 管理、设计操作、自动化测试等实际任务。
> MCP 调用会对外部系统产生真实影响，必须比普通对话更加谨慎。

## E.1 MCP 核心原则

### 操作三不原则

1. **不盲目信任** — MCP 返回的数据可能是过时的，关键操作前先查询确认当前状态
2. **不一次做完** — 复杂操作必须分步执行，每步确认结果后再继续
3. **不忘记验证** — 每次 MCP 调用后必须检查返回结果，确认操作成功

### 调用前必须三问

1. 这个操作是否可逆？（不可逆操作必须格外谨慎）
2. 我掌握的最新状态是否与外部系统一致？（状态漂移检查）
3. 本次调用的返回数据量是否可能打爆上下文窗口？

## E.2 本项目可用 MCP 服务清单

### MCP 服务总览

| MCP 服务 | 所属范围 | 核心能力 | 涉及子项目 |
|---------|---------|---------|-----------|
| **BugPack MCP** | 全局（test 项目强制使用） | Bug 创建、查询、状态管理、截图、修复说明 | test |
| **Pencil MCP** | 全局（miniapp/webapp 涉及设计） | 设计文件读写、编辑、截图导出 | miniapp, webapp |

### BugPack MCP 工具详情

| 工具 | 用途 | 使用场景 | 注意事项 |
|------|------|---------|---------|
| `list_bugs` | 查询 Bug 列表 | 任务开始时了解当前 Bug 状态 | 可配合 project/status 参数过滤 |
| `get_bug_context` | 获取 Bug 完整上下文 | 修复 Bug 前查看详情和修复说明 | 返回数据量较大 |
| `get_bug_screenshot` | 获取 Bug 截图 | 理解 Bug 视觉表现 | 截图消耗 Token 较多 |
| `mark_bug_status` | 更新 Bug 状态 | Bug 修复后标记状态 | **不可逆操作**，确认后再执行 |
| `add_fix_note` | 添加修复说明 | Bug 修复后记录修复方案 | 追加写入，不会覆盖已有内容 |

### Pencil MCP 工具详情

| 工具 | 用途 | 使用场景 | 注意事项 |
|------|------|---------|---------|
| `batch_design` | 批量编辑设计文件 | 创建/修改/删除设计节点 | **任一操作失败则整批回滚**，不宜一次塞入过多操作 |
| `batch_get` | 批量读取设计节点 | 查询设计元素和组件 | readDepth/searchDepth 过大时返回数据量巨大 |
| `get_screenshot` | 获取设计截图 | 验证视觉还原效果 | **高 Token 消耗**，优先使用 snapshot_layout |
| `snapshot_layout` | 检查布局结构 | 验证布局和元素位置 | 低 Token 消耗，适合结构检查 |
| `find_empty_space` | 查找空白区域 | 在画布上定位可放置新元素的位置 | 需提供准确的尺寸和方向参数 |
| `get_variables` / `set_variables` | 管理设计变量 | 全局颜色/字体/间距变量管理 | 需遵循 .pen schema 的变量格式 |
| `search_all_unique_properties` / `replace_all_matching_properties` | 批量属性操作 | 全局替换/搜索设计属性 | 影响范围大，谨慎使用 |

## E.3 调用流程规范

### E.3.1 标准调用流程

```
┌─────────────────────┐
│  1. 查询当前状态     │  ← 先通过 list/query 获取最新状态
├─────────────────────┤
│  2. 规划操作步骤     │  ← 复杂操作拆分为多个原子操作
├─────────────────────┤
│  3. 执行操作         │  ← 按规划顺序执行
├─────────────────────┤
│  4. 验证返回结果     │  ← 检查返回的 status/error 字段
├─────────────────────┤
│  5. 确认结果一致性   │  ← 再次查询确认外部系统状态已更新
└─────────────────────┘
```

### E.3.2 分步执行原则

对于涉及多个 MCP 调用的复杂任务，必须分步执行：

```
✅ 正确做法：
  第1步：list_bugs → 获取当前 Bug 列表和状态
  第2步：get_bug_context → 查看具体 Bug 详情
  第3步：确认后 → mark_bug_status → 更新状态
  第4步：list_bugs → 确认状态已更新

❌ 错误做法：
  一次调用 mark_bug_status → 更新状态后不验证
```

### E.3.3 避免上下文溢出

- `batch_get` 的 `readDepth` 和 `searchDepth` 参数优先使用低值（1~2），需要更多数据时逐层深入
- `get_screenshot` 和 `get_bug_screenshot` 仅在需要视觉验证时使用
- 大批量操作拆分为多个小批次执行

## E.4 安全约束

### E.4.1 不可逆操作保护

以下 MCP 操作一旦执行无法恢复，**必须先确认参数再执行**：

| MCP 服务 | 不可逆操作 | 执行前必须 |
|---------|-----------|-----------|
| BugPack | `mark_bug_status` | 确认 Bug ID、目标状态、项目名正确 |
| BugPack | `add_fix_note` | 确认 Fix Note 内容完整准确 |
| Pencil | `batch_design` 中的 D（删除）操作 | 确认删除的节点 ID 正确 |
| Pencil | `replace_all_matching_properties` | 确认替换范围 and 新值正确 |

### E.4.2 状态漂移防护

状态漂移指 AI 认知与外部系统实际状态不一致的情况。防护措施：

1. **操作前查询**：任何修改操作前，先调用查询工具确认当前状态
2. **操作后验证**：修改后再次查询，确认变更已生效
3. **跨对话注意**：新对话开始时，不要假设上个对话中 MCP 的状态仍然有效

### E.4.3 数据安全

- BugPack MCP 上报的 Bug 信息不应包含用户个人隐私
- Pencil MCP 操作设计文件时，注意不要误删他人创作的内容
- 禁止通过 MCP 操作未经授权的资源（如其他项目的 Bug）

### E.4.4 频率控制

- 避免在短时间内重复调用同一个 MCP 工具
- 连续调用之间留出合理的间隔，避免服务端限流
- 批量操作优先使用批量接口（如 `batch_design`、`batch_get`），而非逐个调用

## E.5 错误处理规范

### E.5.1 错误分类与应对

| 错误类型 | 可能原因 | 应对策略 |
|---------|---------|---------|
| 参数错误 | 工具入参格式不正确 | 检查参数后再试（不使用相同参数重试） |
| 资源不存在 | 引用的 ID 已被删除 | 先查询确认后再操作 |
| 权限不足 | 无对应资源的操作权限 | 告知用户，停止操作 |
| 网络超时 | 服务端响应慢或网络问题 | 等待后重试（最多 2 次） |
| 状态冲突 | 操作的目标状态与当前状态冲突 | 重新查询最新状态后调整方案 |

### E.5.2 失败处理流程

```
MCP 调用失败
    │
    ├── 参数错误 → 修正参数 → 重试
    │
    ├── 资源不存在 → 重新查询 → 调整方案
    │
    ├── 网络超时 → 等待 → 重试（最多 2 次）
    │                      ↓
    │                   仍失败 → 告知用户
    │
    └── 其他错误 → 记录错误信息 → 告知用户
```

### E.5.3 批量操作回滚感知

Pencil MCP 的 `batch_design` 支持事务性回滚：
- 如果某个操作失败，整个批次的**所有操作**都会回滚
- 不要在同一个 `batch_design` 调用中放入过多操作（一般不超过 10 个）
- 将大型修改拆分为多个批次，降低单次回滚的影响范围

## E.6 问题排查

当 MCP 调用不符合预期时，按以下路径排查：

```
1. MCP 服务是否正常运行？           → 检查服务进程是否启动
2. 工具参数是否正确？               → 检查入参格式和必填字段
3. 当前操作是否在资源权限范围内？    → 确认是否有操作权限
4. 返回结果中是否有错误信息？        → 解析返回的 error 字段
5. 外部系统状态是否已变更？          → 重新查询确认
6. 是否需要告知用户手动介入？        → 无法自动恢复时及时告知
```

# Part F — Agent 选用与执行规范

> 适用于 AI Agent 在执行开发任务时的选用、执行和风险应对。
> Agent 是 Trae IDE 的核心执行单元，能够自主规划任务、调用工具、委派子 Agent。
> 与 Skill（影响 AI 思考方式）和 MCP（扩展 AI 行动能力）不同，Part F 聚焦 Agent 本身的行为质量管控。

## F.1 Agent 核心概念

### F.1.1 Agent 的能力边界

| 能力 | 说明 | 对应工具/机制 |
|------|------|-------------|
| 自主规划 | 拆解复杂任务为子步骤 | TodoWrite、Task |
| 工具调用 | 读写文件、执行命令、搜索代码 | Read、Write、RunCommand、Grep、SearchCodebase |

### F.1.2 Agent 的类型

## F.3 Agent 选用原则

### 选用判断流程

```
任务来临时
    │
    ├── 简单任务（单步操作）→ 直接执行，不调子 Agent
    │   例：修改一个函数、修复一个 lint 错误
    │
    ├── 中等任务（2~5 步）→ 主 Agent 自行执行
    │   例：实现一个 API 接口、创建一个页面组件
    │
    └── 复杂任务（多步骤/跨领域）→ 考虑调子 Agent
        例：实现完整用户模块（需前端+后端+测试）
```

### 选用规则

| 条件 | 做法 |
|------|------|
| 任务明确属于某个 Agent 的专业领域 | 调用对应子 Agent |
| 任务涉及多个专业领域 | 主 Agent 拆分后分别委派 |
| 简单搜索任务 | 直接使用 Grep/SearchCodebase，**不调子 Agent** |
| 不明确用哪个 Agent | 先使用 `search` 做调研，或 AskUserQuestion 询问用户 |

### 禁止事项

- 禁止使用 `frontend-architect` 做后端任务
- 禁止使用 `backend-architect` 修改前端代码
- 禁止因懒惰将简单任务委派为子 Agent（增加 Token 消耗和延迟）
- 子 Agent 返回的结果必须验证后再使用，禁止直接采纳

## F.4 执行规范

### F.4.1 任务规划阶段

每项任务执行前必须完成：

```
□ 理解任务目标与边界
   ├── 确认任务要「做什么」和「不做什么」
   ├── 需求模糊时使用 AskUserQuestion 澄清
   └── 确认当前分支为 develop

□ 加载锚点文档
   ├── 根规则 project_rules.md（全部 Part）
   ├── 对应子项目的 project.md 和 .trae/rules/project_rules.md
   └── 涉及的设计文档/PRD

□ 输出执行计划（复杂任务）
   ├── 拆分为可验证的子步骤
   ├── 每步标注预期结果
   └── 明确哪些步骤可并行

□ 两阶段检查
   ├── 当前处于哪个阶段？（建议/执行）
   ├── 建议阶段 → 输出建议报告 → 等待用户确认
   ├── 执行阶段 → 严格按已确认的方案执行
   └── 如果用户反馈了新的想法 → 回到建议阶段
```

### F.4.2 任务执行阶段

**核心：不得擅自扩大任务范围。**

- 发现「顺手的问题」时：记录到 TodoWrite 的备注中，**不立即处理**
- 如果「顺手的问题」阻塞了当前任务：先 AskUserQuestion 征求用户同意
- 每完成一个子步骤，验证结果后再继续下一步

**修改出错的回滚策略：**

当修改导致错误时，按以下顺序尝试恢复：

```
1. git diff -- <file>     → 查看具体修改内容
2. git restore <file>     → 撤销未提交的文件修改
3. git stash              → 暂存当前所有修改，回到干净状态
4. git restore --staged <file> → 撤销已暂存的修改
5. git checkout -- <file> → 回退到上一个提交版本（备用方案）
```

> 如果已提交但需要撤销，使用 `git revert HEAD`（不修改历史）。禁止使用 `git reset --hard` 丢弃提交历史。

**发现偏离时的纠正流程：**

```
当前步骤完成
    │
    ├── 步骤结果与计划一致 → 继续下一步
    │
    └── 步骤结果偏离计划
         ├── 偏离在可接受范围内 → 记录偏离，继续
         │
         └── 偏离超出可接受范围
              ├── 能自行回退 → 回退到上一个已验证状态
              └── 不能自行回退 → 告知用户，协商修复方案
```

### F.4.3 任务完成阶段

```
□ 全面审查
   ├── 检查 diff，确认修改范围 = 任务范围
   ├── 确认没有「顺手」的额外修改
   └── 确认没有创建不必要的文件（参见 §B.5）

□ 全面验证
   ├── 运行 lint/typecheck 验证
   ├── 运行相关测试
   └── 验证通过后标记 todo 完成

□ 提交
   ├── 按 Part A Git 规范执行提交
   └── 提交信息准确描述变更内容
```

## F.5 子 Agent 调用规范

### F.5.1 调用原则

```
✅ 应该调子 Agent 的场景：
   - 任务需要该 Agent 的领域专业知识
   - 多个子任务可并行执行时
   - 需要 Agent 调用特定工具/MCP 时

❌ 不应该调子 Agent 的场景：
   - 简单搜索（直接用 Grep/SearchCodebase）
   - 只需一步完成的修改
   - 子 Agent 没有该任务所需的专业知识
```

### F.5.2 委派规范

调用子 Agent 时，Task 描述必须包含：

| 要素 | 说明 | 示例 |
|------|------|------|
| **任务目标** | 清晰的单一任务描述 | 「查询 backend 项目中的所有 API 路由」 |
| **上下文锚点** | 子 Agent 需要加载的文件 | 「请先加载 backend/project.md」 |
| **输出要求** | 期望返回什么信息 | 「返回路由列表及对应的文件路径」 |
| **边界约束** | 什么不能做 | 「只做查询，不做代码修改」 |

### F.5.3 结果验证

子 Agent 返回结果后，主 Agent 必须：

1. **检查结果完整性** — 子 Agent 是否返回了所有需要的信息
2. **检查结果准确性** — 结果是否与已知信息矛盾
3. **检查结果安全性** — 结果中是否包含不应修改的建议
4. **确认后再使用** — 验证通过后才将结果用于后续步骤

## F.6 常见风险与应对

### F.6.1 任务漂移

**现象**：Agent 在执行中偏离原始任务，做了「顺手」的事。

**应对措施**：
1. 复杂任务必须先输出计划，计划中明确任务边界
2. 每步完成后检查是否仍在任务范围内
3. 发现偏离时，先记录待办，不立即处理
4. 偏离严重时回退步骤，重新对齐任务目标

### F.6.2 过度修改

**现象**：Agent 做了比需求更多的实现（过度工程）。

**应对措施**：
1. **最小实现原则**：先做最简实现，用户要求扩展时再补充
2. 文件创建必须受 §B.5 约束
3. 新增依赖必须受 §B.3 约束
4. 完成后审查 diff，移除不必要的变更

### F.6.3 修复循环

**现象**：Agent 在修复-验证中陷入死循环，每次修复引入新问题。

**应对措施**：
1. 设置重试上限（同一问题最多修复 3 次）
2. 第 3 次仍失败时，停止自动修复，告知用户
3. 每次修复前先确认是否回归了之前已修复的问题
4. 如果修复循环持续超过 5 步，应回退到上一个稳定状态重新分析

### F.6.4 幻觉延续

**现象**：Agent 在前一步生成了错误代码，后续步骤基于错误继续构建。

**应对措施**：
1. 每步完成后必须运行 lint/typecheck 验证
2. 修复错误时要确认是「修复了根因」还是「打补丁掩盖了问题」
3. 对修复方案进行回归检查
4. 验证通过后再进行下一步

### F.6.5 子 Agent 上下文丢失

**现象**：子 Agent 因没有完整的项目上下文，生成了不符合项目规范的代码。

**应对措施**：
1. Task 描述中必须包含足够的上下文锚点
2. 要求子 Agent 在修改前先阅读相关文件
3. 子 Agent 返回结果后必须验证后再使用

### F.6.6 修改无法回退

**现象**：Agent 修改文件后发现错误，但不清楚如何撤销修改，导致错误代码被提交。

**应对措施**：
1. 未提交的修改使用 `git restore <file>` 撤销（参见 F.4.2 回滚策略）
2. 已暂存的修改使用 `git restore --staged <file>` 取消暂存
3. 已提交的修改使用 `git revert HEAD` 生成反向提交
4. **禁止**使用 `git reset --hard` 丢弃提交历史
5. 如果多个文件混乱，先使用 `git stash` 暂存所有修改，从干净状态重新分析
6. 不确定回滚操作影响时，先 AskUserQuestion 询问用户

## F.7 问题排查

当 Agent 行为不符合预期时，按以下路径排查：

```
1. 任务规划是否清晰？               → 检查任务目标和边界是否明确
2. 上下文是否完整？                 → 检查锚点文档是否已加载
3. 选择的 Agent 是否正确？          → 对照 F.2 Agent 选择矩阵检查
4. 是否发生了任务漂移？             → 检查当前步骤是否偏离原始计划
5. 是否陷入了修复循环？             → 检查是否超过 3 次重试仍未成功
6. 子 Agent 返回的结果是否验证？     → 检查是否直接采纳了未验证的结果
7. 是否需要人工介入？               → 无法自行恢复时告知用户
```

## F.8 建议-执行两阶段原则

> 本条款适用于 `memo/` 下所有子项目（backend、miniapp、webapp、test），前端和后端开发均须遵守。

### F.8.1 默认工作流

所有任务默认走两阶段流程：先建议，后执行。除非用户明确说了"直接做"或"不用问我"。

```
┌─────────────────────────────────────┐
│          每个任务 = 两个阶段           │
├─────────────────────────────────────┤
│                                     │
│  阶段一：建议 (Suggest)               │
│  ┌─────────────────────────────┐    │
│  │ ① 分析问题 / 阅读上下文     │    │
│  │ ② 制定方案（含多个选项）    │    │
│  │ ③ 给出推荐方案及理由        │    │
│  │ ④ 提交给用户审核           │    │
│  └─────────────────────────────┘    │
│               ↓                      │
│       用户确认 or 反馈                │
│               ↓                      │
│  阶段二：执行 (Execute)              │
│  ┌─────────────────────────────┐    │
│  │ ① 按确认的方案执行修改      │    │
│  │ ② 每步完成后验证            │    │
│  │ ③ 最终汇报变更摘要          │    │
│  │ ④ 等待用户指令后再提交      │    │
│  └─────────────────────────────┘    │
│                                     │
└─────────────────────────────────────┘
```

### F.8.2 建议阶段的行为规范

- 建议阶段**不做任何代码修改**（包括修复 lint 错误、调整格式等"顺手"操作）
- 建议报告必须包含：问题分析、可选方案（≥2 个）、推荐方案及理由、预估影响范围
- 建议报告中使用开放式问题而非"是否执行"的封闭式问题（如"这三个方案你觉得哪个更合适？"而非"要执行方案一吗？"）

### F.8.3 执行阶段的约束

- 仅当用户明确确认后才进入执行阶段
- 执行阶段仍然遵守 B.23 最小干预原则（遇到问题时先引导用户自己解决）
- 执行完成后必须提供变更摘要，等待用户确认后再提交

### F.8.4 子 Agent 的两阶段约束

- 建议阶段可委派子 Agent 做调研/分析，但子 Agent 不得修改代码
- 执行阶段如需委派子 Agent，必须在建议阶段已向用户说明并获批准
- 子 Agent 返回的结果必须经主 Agent 验证后再执行

### F.8.5 例外情况

以下情况不需要走完整两阶段流程：

1. **用户明确说"直接做"**
2. **纯执行性指令**（如"运行测试"、"帮我查下这个变量的类型"）
3. **紧急修复**（如生产环境宕机），但修复后仍需补报变更
4. **默认本地提交** — 根据 A.3，Agent 在修改文件后须自动执行一次本地提交。
   提交行为是两阶段原则之外可自动执行的操作，无需用户确认。
   但 F.8.3 要求的"提供变更摘要"仍需执行，使用户了解已提交的内容。
