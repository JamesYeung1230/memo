## 产品概要

面向非专业编程用户的碎片化学习工具，通过知识卡片、刷题练习与间隔重复记忆强化，帮助 AI 编程学习者建立计算机基础认知，使其更高效地驾驭 AI 工具完成软件开发任务。

**核心闭环**：知识卡片（输入） → 刷题 + 记忆强化（巩固） → AI 编程实践（输出），积分体系贯穿全程。

详细产品定义参见 [PRD.md](docs/PRD.md)。

## 笔记业务关键约束

> 引用自 PRD §2.1.3，开发者实现笔记功能时必须遵守

| 约束项 | 规则 |
|-------|------|
| **默认存储** | 笔记默认仅存储于本地，不上传服务端；卸载小程序后数据丢失 |
| **首次风险告知** | 首次进入笔记功能时弹窗提示风险，用户点击「已知晓」后方可使用 |
| **上传触发** | 仅用户主动点击「提交审核」时才上传服务端 |
| **数量上限** | 单用户笔记上限 500条 |
| **编辑行为** | 编辑操作不触发审核，仅「保存为草稿」 |
| **分享触发审核** | 用户点击「提交分享」触发三级审核流程 |
| **分享权限** | 仅「审核通过」的笔记可分享；审核中/已驳回笔记「分享」按钮置灰 |
| **分享卡片内容** | 展示标题（前20字）、摘要（前50字）、关联知识标签、分享者昵称；不展示完整内容 |
| **已通过笔记编辑** | 已通过笔记被编辑后，分享状态重置，需重新提交审核 |
| **撤回审核** | 审核中的笔记可撤回，恢复为「未提交」状态 |
| **违规处罚** | 累计3次违规 → 限制提审功能7天 |
| **分享冻结** | 连续3次审核驳回 → 分享功能冻结7天 |
| **关联笔记** | 来源知识内容被移除时，保留笔记但去除关联链接 |

### 笔记状态流转

```
草稿 ──提交审核──→ 审核中 ──审查通过──→ 审核通过（可分享）
  ↑                  │                      │
  │                  ├──审查驳回──→ 审核驳回    │ 编辑后
  │                  │                      │ 重置
  │    撤回          │                      ↓
  └──────────────────┘                    草稿
```

## 知识内容体系

PRD §2.2.1 定义七大知识领域，以「领域→章节→知识点」三级结构组织：

| 编号 | 知识领域 | 示例知识点 | 卡片预估 |
|:----:|---------|-----------|:------:|
| K01 | 编程基础概念 | 变量、函数、条件判断、循环、数据类型 | 10~15 |
| K02 | 计算机网络基础 | HTTP/HTTPS、域名与IP、前端与后端、API概念 | 8~12 |
| K03 | 软件工程流程 | 需求分析→设计→开发→测试→部署 | 8~10 |
| K04 | 数据库基础 | 什么是数据库、表与字段、增删改查（CRUD） | 6~10 |
| K05 | 操作系统基础 | 文件系统、进程与线程、环境变量 | 5~8 |
| K06 | AI编程实践技巧 | 提示词结构、需求描述方法、错误排查思路 | 8~12 |
| K07 | AI编程与传统编程 | AI编程vs传统编程差异、AI编程工具链（Cursor/Copilot/Claude等）、从传统开发过渡到AI开发的思维转变、AI编程的优势与局限 | 10~14 |

> K01~K03 免费开放；K04~K07 需消耗积分解锁（30~60 积分/领域），部分进阶知识点需额外积分兑换（20 积分/卡片）。

## 积分体系详情

> 引用自 PRD §2.4，按难度分配积分，降低简单重复行为的收益

### 积分获取

| 行为 | 获得积分 | 每日上限 | 难度等级 |
|------|:------:|:------:|---------|
| 学习1张知识卡片（点「懂了」） | +1 | 10 | ⭐ 低 — 碎片化积累 |
| 完成每日挑战（3~5题全对） | +15 | 15 | ⭐⭐⭐ 高 — 需全对方可获得 |
| 连续打卡第3天 | +15 | — | ⭐⭐ 中 — 里程碑奖励 |
| 连续打卡第7天 | +30 | — | ⭐⭐⭐ 高 — 周里程碑 |
| 连续打卡第14天 | +60 | — | ⭐⭐⭐ 高 — 双周里程碑 |
| 创建1条笔记（字数≥20字） | +5 | 15 | ⭐⭐ 中 — 需有实质内容 |
| 观看激励广告（完整观看） | +10 | 100 | ⭐ 低 — 核心盈利通道 |

> **设计原则**：单纯浏览卡片或刷题不直接给积分；每日挑战必须全部答对才发放积分；笔记需≥20字有效内容；激励广告必须完整观看。

### 积分用途

| 用途 | 消耗积分 | 说明 |
|------|:------:|------|
| 解锁新知识领域（K04~K07） | 30~60 | 运营后台可动态调整定价 |
| 解锁高级知识卡片 | 20 | 部分进阶知识点需要积分兑换 |
| 兑换虚拟成就徽章 | 30~200 | 个人中心展示，纯荣誉性质 |

### 积分规则

- 积分不可转赠、不可提现
- 积分永久有效，不会过期
- 用户卸载后积分数据丢失（v1.0 无云端同步）

## 记忆强化配置

> 引用自 PRD §2.3.3，用户可在设置页自定义以下参数

| 配置项 | 说明 | 默认值 | 可配置范围 |
|-------|------|:------:|-----------|
| **复习节点** | 学习后第N天触发复习提醒 | [1, 2, 4, 7, 15] | 1~5个节点，每节点1~60天 |
| **每日复习上限** | 每日最多推送复习卡片数 | 20张 | 5~50张 |
| **遗忘预警天数** | 连续未复习多少天触发预警 | 7天 | 3~30天 |
| **复习提醒时间** | 每日微信服务通知推送时段 | 20:00 | 08:00~22:00 |
| **周末免打扰** | 周六/周日是否暂停复习推送 | 否 | 开/关 |
| **恢复默认** | 一键恢复系统推荐配置 | — | — |

> **预设方案**：系统提供「推荐配置（标准艾宾浩斯）」「轻松配置（低频）」「强化配置（高频）」三档预设，一键切换。
> 配置页展示当日待复习数量预览。修改配置仅对新学习的知识点生效，已排入复习计划的不受影响。

## 盈利模式

PRD §3 定义两大广告类型：

| 广告类型 | 展示场景 | 频率 | 用户选择权 |
|---------|---------|------|-----------|
| **开屏广告** | 小程序启动时展示 | 每次冷启动 | 3~5秒后可跳过 |
| **激励广告** | 用户主动点击「看广告赚积分」 | 用户自主触发 | 完全自愿，单次约15~30秒，必须完整观看才发放积分（+10/次） |
| **插屏广告** | v1.0 暂不接入 | — | — |

**盈利闭环**：用户观看激励广告 → 获得积分（+10/次）→ 积分解锁新知识（K04~K07）→ 学习更多内容 → 积分稀缺 → 广告成为最稳定积分来源 → 盈利闭环。

## 强制要求

### 1. 上下文加载
每次执行任务前，**必须先加载 [project.md](project.md)** 到上下文中，了解项目背景、当前阶段和技术栈。

### 2. 意图确认
收到任务后，**仔细分析用户意图**。如果存在以下情况，必须**反问用户确认**后再执行：
- 需求描述模糊，存在多种理解方式
- 与现有产品逻辑可能存在冲突
- 技术方案存在多种可选路径
- 任务的边界范围不清晰

### 3. Agent 协同
执行任务时，在可用的 Agent 配置中选取合适的 Agent。当任务可以拆分为多个独立子任务时，**协同调用多个 Agent 并行工作**，提升任务效率。

可用 Agent：
- `frontend-architect` — 前端开发、UI 实现
- `ui-designer` — 交互设计、视觉还原
- `backend-architect` — 后端 API 设计
- `search` — 代码搜索与调研

### 4. Git 本地提交
**每次修改完成后必须维护 git 仓库**，将代码修改记录提交到本地仓库。提交信息需清晰描述本次变更内容。

### 5. 禁止擅自推送远程
**用户未主动要求，不得擅自提交到远程仓库。** 所有 git 操作仅限于本地仓库。

### 6. README 维护
在工作目录维护 [README.md](README.md)，说明该目录下项目内容的情况。项目结构或功能有变更时同步更新。

### 7. 文件修改边界
**所有 Agent 以及所有修改操作，只能修改当前项目文件夹 `d:\workspace\memo\miniapp\` 下的文件，不能修改本项目文件夹外的其他文件。**

## 核心原则：纯前端项目

这是一个**纯粹的前端项目**（微信小程序），不包含后端服务。

### 后端调用规范

在遇到需要调用后端接口的场景时：
1. **严格依照后端 SDK 文档**进行调用
2. 如果发现后端 SDK 文档与后端实际提供的 SDK **不一致**：
   - **坚持以文档为准**
   - **不得**直接使用后端 SDK 中提供的不符合规范的 SDK
   - 将问题原因报告为**后端问题**，由后端团队修正
3. **不要**强行改变前端业务逻辑来适配后端的错误实现

### 设计还原规范

1. 所有 UI 实现严格参照交互设计文档中的设计规范
2. 设计 Token（颜色、圆角、阴影、字体）以交互设计文档定义值为准
3. Pixso 设计稿为视觉还原的最高参照标准
4. 主题色支持管理端动态下发（参见 PRD §2.5.3），默认品牌主色为 #4A90D9（科技蓝）
