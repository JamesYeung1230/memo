## 项目定位

测试工程是「卡片学记」平台的**独立测试项目**，负责对所有子项目的后端接口和前端交互进行测试验证与 Bug 上报。

### 测试范围划分

| 测试对象 | 测试类型 | 测试方式 | 说明 |
|----------|----------|----------|------|
| 后端 SDK API | 接口测试 | 编写测试用例 + 测试代码，自动化执行 | 依照后端 SDK 文档编写测试用例，完成测试并上报 Bug |
| 微信小程序 (miniapp) | 黑盒测试 | 编写测试用例，告知用户执行 | 根据交互文档编写测试用例，由用户手动执行 |
| Web 管理后台 (webapp) | 黑盒测试 | Playwright MCP 自动化测试 | 自主执行测试并完成 Bug 上报 |

## 强制要求

### 1. 上下文加载
每次执行任务前，**必须先加载 [project.md](project.md)** 到上下文中，了解项目背景、当前阶段和测试范围。

### 2. 意图确认
收到任务后，**仔细分析用户意图**。如果存在以下情况，必须**反问用户确认**后再执行：
- 需求描述模糊，存在多种理解方式
- 测试范围边界不清晰
- 测试方式存在多种可选路径（如自动化 vs 手动）
- 与现有测试逻辑可能存在冲突

### 3. Agent 协同
执行任务时，在合适的 Agent 配置中选取 Agent 调用。当任务可以拆分为多个独立子任务时，**协同调用多个 Agent 并行工作**，提升任务效率。

可用 Agent：
- `api-test-pro` — API 接口测试、性能测试、契约测试
- `frontend-architect` — Playwright 自动化测试脚本、前端测试
- `backend-architect` — 后端 API 分析、SDK 接口理解
- `search` — 代码搜索与调研

### 4. BugPack MCP 强制使用
**所有 Bug 信息必须通过 BugPack MCP 服务进行维护。** 包括但不限于：
- 测试过程中发现的 Bug 创建与上报
- Bug 状态更新（pending / annotating / generated / fixed / closed）
- Bug 修复说明的记录
- Bug 截图的上传与管理

### 5. Git 本地提交
**每次修改完成后必须维护 git 仓库**，将代码修改记录提交到本地仓库。提交信息需清晰描述本次变更内容。

### 6. 禁止擅自推送远程
**用户未主动要求，不得擅自提交到远程仓库。** 所有 git 操作仅限于本地仓库。

### 7. README 维护
在工作目录维护 [README.md](README.md)，说明该目录下项目内容的情况。项目结构或功能有变更时同步更新。

### 8. 文件修改边界
**所有 Agent 以及所有修改操作，只能修改当前项目文件夹 `d:\workspace\memo\test\` 下的文件，不能修改本项目文件夹外的其他文件。**

## 核心原则：仅编写测试用例

这是一个**纯粹的测试项目**，核心职责是测试验证与 Bug 上报。

### 工作边界

1. **只负责**根据用户提供的 API 文档和交互设计文档编写测试用例
2. **不涉及**任何问题分析和业务代码修改
3. **只允许**测试用例相关的代码编写和修改
4. **不得**修改被测试项目的业务代码

### 后端 SDK API 测试规范

对于后端 SDK 的 API 测试：
1. **严格依照后端 SDK 文档**编写测试用例及相关的测试代码
2. 完成测试后，将发现的 Bug **通过 BugPack MCP 上报**
3. 如发现 SDK 文档与实际行为不一致，以**文档为准**进行 Bug 报告

### 微信小程序黑盒测试规范

对于微信小程序交互相关的黑盒测试：
1. **仅根据交互设计文档**编写测试用例
2. 将测试用例告知用户，由用户自行执行
3. 用户反馈结果后，通过 BugPack MCP 记录

### Web 管理后台黑盒测试规范

对于 Web 端管理后台交互相关的黑盒测试：
1. 使用 **Playwright MCP 服务**自主进行自动化测试
2. 依据交互设计文档编写测试脚本并执行
3. 测试完成后通过 BugPack MCP 完成 Bug 上报
