# 卡片学记 测试工程 — AI 编程注意事项

> 本文件是对 [project.md](../../project.md) 中「强制要求」的补充，聚焦 AI Agent 在执行测试任务时的行为约束。
> 测试范围、测试方式等具体规范以 `project.md` 为准。

---

## 一、上下文感知

- Agent 在编写测试前，必须先使用 SearchCodebase 或相关搜索工具获取被测试项目的上下文
- 了解被测试项目的 API 文档、交互设计文档后再编写测试用例
- 修改测试代码前，先阅读同目录下已有测试文件，理解现有测试风格和约定
- 每次任务开始前必须加载以下锚点文档：
  1. [project.md](../../project.md) — 项目背景、当前阶段、测试范围
  2. [本文件](project_rules.md) — AI 编程行为约束

## 二、修改验证

- 每次测试代码修改完成后，必须运行对应测试框架验证测试通过
- 确保测试代码本身语法正确、无类型错误
- 多步骤任务中，每完成一步都应验证后再继续下一步

## 三、依赖管理

- 禁止引入项目未使用的新依赖（npm 包、pip 包等），除非用户明确要求
- 使用测试相关依赖前，先检查 `package.json`、`requirements.txt`、`pyproject.toml` 等文件中是否已有替代方案
- 不得使用过时、废弃或不安全的库版本

## 四、安全红线

- 禁止在代码中硬编码任何密钥、Token、密码或敏感信息
- 测试数据必须使用模拟数据，禁止使用生产环境真实数据
- 测试脚本不得对生产环境发起请求或操作

## 五、文件创建约束

- 禁止生成文档类 `.md` 文件（README、CHANGELOG 等），除非用户明确要求
- 优先修改已有测试文件，而非创建新文件
- 除非绝对必要，否则不要创建新文件

## 六、测试编写规范

- 每个测试用例必须包含：测试目的、前置条件、测试步骤、预期结果
- 测试必须覆盖正常路径、边界条件和异常场景
- Bug 修复验证必须先编写复现步骤，确认可复现后再验证修复
- 测试用例标题和描述必须清晰可读，便于人工审查
- 自动化测试脚本应遵循 Page Object 模式（Playwright）或对应的测试设计模式

## 七、Bug 上报规范

- 所有 Bug 必须通过 BugPack MCP 服务上报和管理
- Bug 描述必须包含：复现步骤、实际结果、预期结果、截图/日志
- Bug 分类清晰（前端/后端/接口/UI/逻辑），便于后续追踪
- Bug 状态流转必须及时更新（pending → annotating → generated → fixed → closed）

## 八、AI Agent 协同

- 测试任务涉及以下场景时可调用对应 Agent 并行工作：
  - `api-test-pro` — API 接口测试、性能测试、契约测试
  - `frontend-architect` — Playwright 自动化测试脚本
  - `backend-architect` — 后端 API 分析、SDK 接口理解
  - `search` — 代码搜索与调研

## 九、任务追踪

- 复杂多步骤测试任务必须使用 TodoWrite 工具创建任务列表并跟踪进度
- 测试执行进度和 Bug 状态应及时更新，确保信息同步

## 十、不确定时确认

- 遇到不确定的测试范围、测试方式或 Bug 判定时，使用 AskUserQuestion 与用户确认
- 不要在不确定的情况下「猜」一个测试方案直接执行
- 当测试需求描述模糊时，主动向用户澄清具体测试场景
