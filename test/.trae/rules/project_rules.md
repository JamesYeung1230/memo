## 测试项目核心原则

### 原则 1 — 只做测试，不做修改

- **只负责**根据用户提供的 API 文档和交互设计文档编写测试用例
- **不涉及**任何问题分析和业务代码修改
- **只允许**测试用例相关的代码编写和修改
- **不得**修改被测试项目的业务代码
- 不在被测试项目中修复 Bug，不修改任何被测试项目的源代码
- 发现的问题通过 BugPack MCP 上报，由被测试项目团队处理

### 原则 2 — 以文档为唯一依据

- 后端 SDK API 测试 → 以 SDK 文档为准
- 微信小程序黑盒测试 → 以 PRD 和交互设计文档为准
- Web 管理后台测试 → 以 Web 管理端 PRD 为准
- 文档与实际行为不一致时，**以文档为准**报告 Bug
- 严格依照后端 SDK 文档编写测试用例及相关的测试代码
- 完成测试后，将发现的 Bug 通过 BugPack MCP 上报

### 原则 3 — Bug 全程通过 BugPack 管理

- Bug 的创建、状态更新、截图上传、关闭统一使用 BugPack MCP 服务
- 状态流转路径：pending → annotating → generated → fixed → closed
- 禁止在其他系统或文档中手动记录 Bug 信息

## Part A 扩展：AI 行为准则（测试补充）

> 扩展 core-rules.md §A.6 上下文感知、§A.8 不确定时确认、§A.9 任务追踪、§A.11 边界追问与范围锁定、§A.15 影响面分析、§A.16 模块全局感知。

### A.19 测试上下文加载

每次测试任务开始前，Agent 必须加载：
1. [project.md](../../project.md) — 项目背景、当前阶段、测试范围
2. 被测试模块对应的需求文档（PRD、API 文档、交互设计文档）
3. 同目录下已有测试文件，理解现有测试风格、命名约定和结构模式

### A.20 测试范围严守

- Agent 所有操作仅限于 `d:\workspace\memo\test\` 目录下的文件
- 不得跨项目读取或修改被测试项目的源代码
- 测试发现的问题不得在业务代码中直接修复
- 不得修改本项目文件夹外的其他文件

### A.21 测试方式判定

根据测试对象选择正确的执行方式：

| 测试对象 | 测试方式 | 执行者 | 规范要求 |
|---------|---------|--------|---------|
| 后端 SDK API | 编写自动化测试代码 | Agent 自动执行 | 严格依照 SDK 文档编写，Bug 通过 BugPack MCP 上报 |
| 微信小程序 | 编写测试用例 | 告知用户手动执行 | 仅根据交互设计文档编写，用户反馈后通过 BugPack MCP 记录 |
| Web 管理后台 | Playwright MCP 脚本 | Agent 自动执行 | 严格依据 Web 管理端 PRD，测试脚本按模块组织（登录/内容工作台/内容管理/运营配置/数据看板/系统管理），完成后通过 BugPack MCP 上报 Bug |

### A.22 意图确认

收到测试任务后，先分析用户意图。以下情况必须反问用户确认后再执行：
- 需求描述模糊，存在多种理解方式
- 测试范围边界不清晰
- 测试方式存在多种可选路径（如自动化 vs 手动）
- 与现有测试逻辑可能存在冲突

### A.23 Agent 协同调用

执行测试任务时，在合适的 Agent 配置中选取 Agent 调用：
- `api-test-pro` — API 接口测试、性能测试、契约测试
- `frontend-architect` — Playwright 自动化测试脚本、前端测试
- `backend-architect` — 后端 API 分析、SDK 接口理解
- `search` — 代码搜索与调研

当任务可拆分为多个独立子任务时，协同调用多个 Agent 并行工作。

### A.24 Git 本地提交

每次修改完成后必须将代码修改记录提交到本地仓库。提交信息需清晰描述本次变更内容。

### A.25 禁止擅自推送远程

用户未主动要求，不得擅自提交到远程仓库。所有 git 操作仅限于本地仓库。

### A.26 README 维护

在工作目录维护 [README.md](../../README.md)，说明该目录下项目内容的情况。项目结构或功能有变更时同步更新。

## Part B 扩展：安全基线（测试补充）

> 扩展 core-rules.md §B.1 敏感信息管理、§B.2 输入验证。

### B.4 测试数据安全

- 测试数据必须使用模拟数据（mock / fixture），禁止使用生产环境真实数据
- 测试中的用户身份、Token、密码等必须为虚构数据
- 测试脚本不得对生产环境发起请求或操作

### B.5 测试环境隔离

- 所有测试在开发/测试环境执行，配置指向测试环境地址
- 生产环境连接信息不得出现在测试代码或配置文件中
- 环境切换通过配置文件或环境变量实现，不在代码中硬编码

## Part C 扩展：代码质量（测试补充）

> 扩展 core-rules.md §C.4 测试覆盖、§C.5 代码可解释性、§C.8 模块化设计。

### C.9 测试用例结构规范

每个测试用例必须包含四要素：
1. **测试目的** — 描述要验证什么
2. **前置条件** — 测试开始前的状态要求
3. **测试步骤** — 具体的操作序列
4. **预期结果** — 期望看到的结果

### C.10 测试覆盖要求

每个被测功能点至少覆盖三类场景：
- **正常路径（happy path）** — 核心流程能否走通
- **边界条件（boundary）** — 临界值的处理是否正确
- **异常场景（error/edge cases）** — 错误输入、异常状态的处理

三者缺一不可。

### C.11 测试命名与组织

- 测试文件按模块组织，目录结构与被测试模块对应
- 测试函数/方法命名清晰自解释，包含：被测对象 + 场景 + 预期行为
- 自动化测试脚本遵循对应框架的设计模式（Playwright → Page Object 模式）

### C.12 Bug 复现测试

- Bug 修复验证前，必须先编写可稳定复现的测试用例
- 确认测试用例能稳定复现 Bug 后，再交由开发方修复
- 修复完成后，用同一用例执行回归验证

## Part F 扩展：MCP 使用（测试补充）

> 扩展 core-rules.md §F.3 MCP 操作三不原则。

### F.4 BugPack MCP 强制使用

- 所有 Bug 生命周期管理必须通过 BugPack MCP 服务
- 涵盖：Bug 创建、状态流转、截图上传、修复说明记录
- 禁止在其他系统、代码注释或文档中手动记录 Bug

### F.5 Bug 描述规范

每个 Bug 上报必须包含：
- **标题** — 简明扼要描述问题现象
- **复现步骤** — 逐步说明如何触发 Bug
- **实际结果** — 当前实际看到的行为
- **预期结果** — 按文档应该看到的行为
- **分类标签** — 前端 / 后端 / 接口 / UI / 逻辑
- **附件** — 截图、日志、录屏（如有）
